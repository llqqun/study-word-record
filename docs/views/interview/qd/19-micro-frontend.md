## 第 19 章 微前端

### Q1 微前端（Micro-Frontend）到底解决什么问题？它和路由分包、组件化有什么区别？

**考察点**：考有没有抓住"独立开发、独立部署、运行时组合"三个关键词，而不是背概念。

**参考答案**：

> **一句话结论**：微前端的本质是把一个大型前端应用按业务域拆成多个能独立开发、独立构建、独立部署的子应用，再由主应用（基座）在运行时把它们拼成一个整体；它首先解决的是**组织与发布问题**，不是技术炫技。

1. 核心矛盾在"人"不在"代码"：多团队共用一个仓库时，发布要排队、回归要一起做、一个团队的 bug 会阻塞别人上线，微前端把发布权交还给各团队。
2. 技术手段是"运行时组合"：各子应用技术栈可以不同（Vue2 / Vue3 / React 混用），主应用负责路由分发、生命周期调度、隔离与通信。
3. 与代码分包的区别：路由懒加载、`import()` 都在**同一个构建产物、同一个运行时**里，微前端是多个独立产物在浏览器里拼装，可以分别发布、分别回滚。
4. 与组件化的区别：组件化的边界是 UI 复用，微前端的边界是团队与发布节奏，颗粒度是"一个业务域"而非"一个按钮"。
5. 代价必须前置说清：沙箱、隔离、通信、公共依赖治理都是额外成本，团队少于 3 个、发布不打架时是负收益。

**追问与易错点**：

- 追问：微前端和 iframe 嵌套有什么区别？答：iframe 是天然隔离，但路由不同步、弹窗出不去、通信只能靠 `postMessage`；微前端要的是"用起来像一个应用"的体验加隔离。
- 陷阱：把"用了 qiankun"当成目标，等于承认自己没主导过选型。
- 陷阱：说微前端能让页面更快——恰恰相反，公共依赖重复加载通常是变慢的。

### Q2 什么场景不该上微前端？适用边界在哪里？

**考察点**：这是最能区分"读过文章"和"踩过坑"的一题，考的是拒绝需求的能力。

**参考答案**：

> **一句话结论**：只有一个团队、一套技术栈、发布不互相阻塞的项目不该用微前端；它适合"多团队、异构技术栈、发布节奏独立、存量系统需要渐进式替换"这四类场景。

1. 团队规模不够时不该用：3 个以内的团队用一个仓库加代码评审就能解决协作，微前端带来的沙箱与通信成本远大于收益。
2. 性能敏感的首屏页面不该用：电商首页、活动页这类 LCP 要求苛刻的页面，多一层基座加载 + 子应用串行请求是直接掉分。
3. 强交互强耦合的模块不该拆：同一张表单、同一个画布被拆到两个子应用，通信成本会吞掉所有收益，拆错边界比不拆更糟。
4. 缺乏基建时不建议上：没有统一构建规范、统一发布平台、统一监控，微前端会把混乱放大，先补 CI/CD 与监控再谈拆分。
5. 真正适合的场景：中后台 / 控制台（多业务域）、需要 Vue2 与 Vue3 共存的存量系统、需要整块替换老系统、外包团队与自研团队并行开发。

**追问与易错点**：

- 追问：那只有 2 个团队怎么办？答：用 Monorepo + 独立构建产物 + Nginx 路由分发就够了，先解决发布排队问题。
- 陷阱：把"技术栈不统一"当作上微前端的理由——技术栈不统一更应该先统一规范，微前端只是兜底手段。
- 追问：适用边界怎么量化？答：看三个信号——发布是否互相阻塞、是否有异构技术栈、是否有存量系统要渐进替换，命中两个才值得做。

### Q3 微前端主流方案有哪些？你会怎么选型？

**考察点**：考全局视野与取舍能力，能不能把"隔离 / 成本 / 性能 / 场景"四条线一次讲清。

**参考答案**：

> **一句话结论**：方案有 iframe、Nginx 路由分发、`single-spa` / `qiankun` 类运行时框架、Module Federation（模块联邦）、Web Components、组合式路由六条路线；选型看团队数量、隔离要求和技术栈是否异构，多数中后台选 `qiankun`，同构且用 webpack5 的团队可优先 Module Federation。

1. `iframe`：浏览器级隔离，几乎零改造，但路由不同步、弹窗受限、体验割裂，适合嵌入第三方或安全要求极高的场景。
2. Nginx 路由分发：按路径把不同 HTML 交给不同应用，本质是多页应用（MPA），隔离最彻底，代价是整页刷新、状态无法共享。
3. `single-spa` / `qiankun`：运行时注册子应用并调度生命周期，支持 HTML Entry、JS 沙箱、样式隔离、预加载，是当前中后台主流。
4. Module Federation：webpack 5 的能力，构建期暴露（`exposes`）、运行时消费（`remotes`），共享依赖不必重复打包，但**不做 JS 与 CSS 隔离**。
5. Web Components：`custom element` + 影子 DOM（Shadow DOM）做样式隔离，天然跨框架，但通信、路由、公共依赖都要自己造。
6. 组合式路由：同一 SPA 内按路由懒加载 + 目录规范隔离，严格说属于模块化，成本最低，适合单团队。

| 方案 | 隔离性 | 改造成本 | 性能 | 适用场景 |
| --- | --- | --- | --- | --- |
| `iframe` | 最强（浏览器级） | 最低 | 差（重复加载、通信慢） | 嵌第三方、强安全隔离 |
| Nginx 分发 | 强（整页独立） | 低 | 中（整页刷新） | 技术栈完全异构、弱交互 |
| `qiankun` | 中（JS 沙箱 + 样式隔离） | 中高 | 中（可预加载） | 多团队中后台、异构共存 |
| Module Federation | 弱（无沙箱） | 中 | 好（依赖共享） | 同构团队、组件级复用 |
| Web Components | 较强（样式） | 高 | 中 | 跨框架组件、低代码 |
| 组合式路由 | 弱 | 最低 | 好 | 单团队、无需独立发布 |

**追问与易错点**：

- 追问：为什么把 Module Federation 的隔离性标成弱？答：它只解决代码共享，子应用仍然跑在同一个 `window` 上，全局变量、样式、路由都会互相污染。
- 陷阱：把"隔离性最强"等同于"最好"，面试官接下来一定问你 iframe 的路由与弹窗问题。
- 追问：能混用吗？答：能，常见组合是基座 + `qiankun` 调度 + Module Federation 共享公共依赖，但要先确认 webpack 版本一致。

### Q4 iframe 做微前端到底行不行？它的隔离性和代价分别是什么？

**考察点**：基础题，但答不出"同源 iframe 共享进程"会被认为只背了优缺点清单。

**参考答案**：

> **一句话结论**：iframe 提供最彻底的隔离——独立 `window`、独立 `document`、独立样式作用域，改造几乎为零；但它牺牲了路由、弹窗、通信和性能，适合"嵌进来就行"的场景，不适合要"像一个应用"的场景。

1. 隔离是浏览器给的：JS 全局变量、CSS 选择器、第三方库冲突全部天然消解，不需要沙箱，也不用担心子应用把 `window` 改坏。
2. 但同源 iframe 通常跑在同一个浏览器进程与主线程上：子应用一个死循环照样卡死整个页面；只有跨域（配合站点隔离）才可能分进程。
3. 路由与刷新是硬伤：iframe 的 URL 与主应用不同步，用户刷新后回到主应用首页，前进后退也难对齐。
4. 弹窗与遮罩出不去：模态框（Modal）、下拉、`position: fixed` 的浮层只能在 iframe 区域内显示，无法覆盖整个浏览器窗口。
5. 通信只能用 `postMessage`：异步、要校验 `origin`、数据结构要序列化，接口一多就变成一套自研 RPC。
6. 性能开销明显：每个 iframe 都要重新加载一遍公共依赖，首屏叠加，内存占用也更高。

**追问与易错点**：

- 追问：怎么缓解弹窗问题？答：让子应用通过 `postMessage` 请求主应用渲染弹窗，或在 iframe 内用足够大的高度并禁止滚动，本质都是妥协。
- 陷阱：说"iframe 是独立的进程所以不会互相影响"——同源场景下这个结论是错的。
- 陷阱：用 `window.parent.document` 直接操作主应用 DOM，同源下能跑通，但跨域立刻失效且破坏隔离，属于典型的反面写法。

### Q5 Nginx 路由分发方案怎么做？它和 SPA 微前端差在哪？

**考察点**：考的是有没有把"最土但最稳"的方案纳入选项，以及是否理解 MPA 与 SPA 的本质差异。

**参考答案**：

> **一句话结论**：Nginx 路由分发就是按路径前缀把请求转发到各自独立部署的应用，本质是多个单页应用组成的多页应用；隔离和成本都最优，代价是切换必然整页刷新、状态无法留存。

1. 典型配置：`/order/` 转发到订单应用、`/user/` 转发到用户应用，各应用有自己的 `index.html`、自己的构建与发布流程。
2. 团队自治最彻底：各应用之间没有运行时耦合，A 团队发版不影响 B 团队，技术栈完全自由，甚至可以是服务端渲染（SSR）页面。
3. 用户体验的代价：跨应用跳转是整页刷新，白屏一次；内存态、未提交的表单、播放中的视频都会丢。
4. 没有运行时组合能力：无法在一个页面里同时挂载两个子应用，导航栏、鉴权、埋点等公共能力要么复制多份，要么抽成独立的公共页面。
5. 适用场景：系统之间交互很弱（点个链接就跳走）、遗留系统改造、需要极强隔离的财务 / 审计类后台。

```nginx
location /order/ { proxy_pass http://order_service/; }
location /user/  { proxy_pass http://user_service/;  }
```

**追问与易错点**：

- 追问：那它算微前端吗？答：算，微前端的定义是"独立开发、独立部署、运行时或跳转时组合"，不强制要求单页内挂载。
- 陷阱：说"和 SPA 微前端没有区别"——区别就在整页刷新和状态共享能力，这是选型的分水岭。
- 追问：怎么减轻白屏？答：主应用做导航壳并用同域共享的 `localStorage` 传递登录态，再靠骨架屏过渡。

### Q6 Web Components 能拿来做微前端吗？它的边界在哪？

**考察点**：考对浏览器原生能力边界的认知，以及有没有关注到 micro-app、无界这类方案的实现思路。

**参考答案**：

> **一句话结论**：能，Web Components 用自定义元素（Custom Element）做容器、用影子 DOM（Shadow DOM）做样式隔离，天然跨框架；但它只给了封装能力，路由、JS 沙箱、公共依赖、通信都得自己补，所以更多被当作"渲染层容器"而不是完整方案。

1. 自定义元素负责挂载点：`<micro-app name="order" url="/order/"></micro-app>` 之类，属性变化时触发子应用的挂载与卸载，等价于一个可复用的运行时容器。
2. 影子 DOM 负责样式隔离：子应用的 CSS 进不来也出不去，比动态改写选择器更彻底，代价是全局主题、公共字体、部分 UI 库的弹窗会受影响。
3. 但影子 DOM 不等于 JS 沙箱：脚本仍然跑在主文档的 `window` 上，全局变量照样污染，所以京东 micro-app 用自定义元素做容器、自研沙箱做隔离，无界（wujie）则用 iframe 做 JS 沙箱、用 Web Components 做渲染。
4. 通信与路由要自研：属性和事件派发是原生的，但全局状态、路由联动、鉴权透传没有标准答案。
5. 适用场景：跨框架的组件级复用、低代码平台的物料容器、需要把某块 UI 嵌进任意宿主的技术中立的场景。

**追问与易错点**：

- 追问：影子 DOM 有哪些"漏出来"的地方？答：CSS 自定义属性会继承穿透，`document` 上的全局样式不会作用于影子树，第三方库往 `document.body` 挂的弹窗也不在影子树里。
- 陷阱：以为用了 Web Components 就有 JS 隔离，这是最常见的一句错话。
- 追问：什么时候优先选它？答：宿主框架不确定、要跨框架复用时；如果宿主是同一套框架，直接发 npm 包更省事。

### Q7 qiankun 的核心原理是什么？single-spa 在中间做了什么？

**考察点**：进阶必考。考的是分层理解，能不能说清"single-spa 管调度、qiankun 补隔离"。

**参考答案**：

> **一句话结论**：qiankun 是 single-spa 的二次封装——single-spa 提供路由匹配与生命周期调度，qiankun 在它之上补齐了 HTML Entry、JS 沙箱、样式隔离和资源预加载。

1. 注册：调用 `registerMicroApps(apps, lifeCycles)` 传入应用列表，每项包含 `name`、`entry`、`container`、`activeRule`，全局钩子处理加载前、挂载后、卸载后做埋点或 loading。
2. 路由驱动：调用 `start()` 后，框架监听路由变化，按 `activeRule` 判断哪个子应用该激活，匹配成功就触发该应用的挂载流程。
3. 生命周期：子应用须导出 `bootstrap`、`mount`、`unmount` 三个函数（`unmount` 后再次进入会重新 `mount`），single-spa 负责按序调用；qiankun 用 HTML Entry 让子应用不必改造成 UMD 包，只需给一个 HTML 地址。
4. 加载与执行：qiankun 先 `fetch` 子应用 HTML，解析出脚本与样式，脚本在沙箱里执行，样式注入到 `container` 对应的作用域内。
5. 隔离：JS 侧按环境选择快照沙箱或代理沙箱，CSS 侧提供严格隔离与实验性隔离两种模式，这是 qiankun 相对 single-spa 的核心增量。
6. 额外能力：资源预加载（`prefetch`）、`loadMicroApp` 手动挂载（适合弹窗里嵌一个子应用）、全局状态 `initGlobalState`。

**追问与易错点**：

- 追问：子应用的 HTML 是怎么变成可执行代码的？答：靠 HTML Entry 方案，内部用 `import-html-entry` 抓取并解析 HTML，把外链脚本取回来当字符串执行。
- 陷阱：说"qiankun 是框架无关的，所以子应用什么都不用改"——子应用至少要导出生命周期并配置 `publicPath` 和 CORS。
- 追问：`loadMicroApp` 和 `registerMicroApps` 怎么选？答：路由驱动的页面级应用用注册式，手动控制的（弹窗、局部模块）用 `loadMicroApp`。

### Q8 HTML Entry 是怎么实现的？import-html-entry 做了哪些事？

**考察点**：深挖题，区别"会用 qiankun"和"读过源码"。

**参考答案**：

> **一句话结论**：HTML Entry 让子应用只暴露一个 HTML 地址，qiankun 用 `import-html-entry` 把这个 HTML `fetch` 回来、解析出脚本与样式、按原顺序执行脚本并把样式以 `<style>` 注入，从而免去子应用改造成 UMD 包的负担。

1. 抓取与解析：`import-html-entry` 用 `fetch` 拉取 HTML 文本，用正则提取 `<script>`、`<link rel="stylesheet">`、`<style>` 以及 `<template>` 里的内容，产出模板、脚本列表、样式列表三部分。
2. 样式处理：外链 CSS 被取回文本后，作为 `<style>` 标签插入子应用容器（配合样式隔离加上作用域选择器），所以子应用样式不需要额外构建配置。
3. 脚本处理：外链 JS 被取回源码字符串，逐个用 `eval`（或 `new Function`）在沙箱作用域里执行，执行时机与原 HTML 中的顺序一致，因此内联的入口初始化脚本也能正常工作。
4. 模板处理：HTML 里的 `<body>` 内容被剥离出来作为后续 `mount` 时的容器内容，`<head>` 中的 `<title>`、`meta` 会被丢弃或单独处理。
5. 对外暴露：返回一个对象，包含 `template`、`getExternalScripts`、`execScripts`、`getExternalStyleSheets` 等方法，qiankun 的加载器再据此驱动完整生命周期。

```js
import importHTML from 'import-html-entry'
const { template, execScripts, assetPublicPath } = await importHTML(entry)
// assetPublicPath 用于更正子应用静态资源的 publicPath
```

**追问与易错点**：

- 追问：为什么能拿到脚本内容？答：靠 `fetch`，所以子应用必须配置跨域资源共享（CORS），否则连 HTML 都拿不到。
- 陷阱：以为浏览器缓存会自动生效——HTML 与 JS 都是 `fetch` 回来的，缓存策略要在服务端配好 `Cache-Control`。
- 陷阱：子应用 HTML 里写死相对路径的资源，`assetPublicPath` 修正不到，必须靠运行时 `publicPath` 兜住。

### Q9 qiankun 的 JS 沙箱有哪几种？快照沙箱和 Proxy 沙箱有什么区别？

**考察点**：深挖核心题。考的是"多实例"这个决定性差异，以及 window 污染与还原机制。

**参考答案**：

> **一句话结论**：qiankun 提供快照沙箱（Snapshot Sandbox）与代理沙箱（Proxy Sandbox）两种；快照沙箱通过"挂载前拍照、卸载后还原"复用同一个 `window`，只能支持单实例；代理沙箱用 `Proxy` 给每个子应用伪造一个 `window` 对象，天然支持多实例并存。

1. 快照沙箱的思路：激活时遍历 `window` 存一份快照，运行期把子应用对 `window` 的修改记录成增量；卸载时按快照还原、清除新增属性，再切换回主应用的环境。它直接改真实 `window`，因此**同时只能有一个子应用运行**。
2. 代理沙箱的思路：用 `Proxy` 包一个假的 `window`，子应用读写都落在代理对象上，真实的 `window` 完全不动；子应用越多，各持有自己的代理对象，互不干扰，因此支持多实例。
3. 多实例沙箱还解决了"主子应用共用同一批全局对象"的难题：真实 `window` 作为兜底的原型链，子应用没定义过的属性仍然能从主应用读到（如 `console`、`document`）。
4. 还原的完整性：代理沙箱因为不污染真实 `window`，"还原"这件事基本不需要做；快照沙箱必须严格还原，否则会出现"进过一次 A 应用，主应用就多了几个全局变量"的诡异现象。
5. 选择逻辑：qiankun 在支持 `Proxy` 的环境默认使用代理沙箱，不支持时降级为快照沙箱；`sandbox: false` 可关闭，仅用于子应用已经完全可信且需要极致性能的场景。

**追问与易错点**：

- 追问：为什么快照沙箱不能支持多实例？答：它直接改真实 `window`，两个子应用同时运行时谁还原谁的状态就无法确定。
- 陷阱：说"沙箱把子应用的 `window` 完全隔离了"——子应用依旧能通过原生事件回调里的 `this` 等途径摸到真实 `window`，隔离是"尽量"而非"绝对"。
- 追问：`document` 被代理了吗？答：qiankun 对 `document` 的部分能力（如动态插入的样式与脚本、事件监听）做了劫持以配合隔离和清理，但 `document` 本身不是完整代理。

### Q10 沙箱能百分百隔离吗？子应用有哪些办法"逃逸"出去？

**考察点**：深挖题，考对隔离边界的清醒认知，这也是线上事故的主要来源。

**参考答案**：

> **一句话结论**：不能。JS 沙箱本质是"运行时改写 + 代理"，只要绕过被代理的入口就能摸到真实 `window`；逃逸的常见口子有动态创建的脚本、`eval` / `new Function` 里的 `this`、以及 `window.top` / `document.defaultView` 这类"后门引用"。

1. 动态脚本：`document.createElement('script')` 插入的外链脚本如果没走沙箱的劫持路径，就会在真实全局作用域执行，直接污染 `window`。
2. 函数执行上下文：在非严格模式下，直接调用的函数里 `this` 指向真实 `window`；`(0, eval)('this')` 或 `new Function('return this')()` 也能拿到真实全局对象。
3. 后门引用：`window.top`、`window.parent`、`window.self`、`document.defaultView` 都指向真实的窗口对象，绕开代理易如反掌。
4. 原生引用固化：子应用在加载早期就把 `window.setTimeout` 之类的原生函数存进闭包，之后用这个引用调用，沙箱的劫持就失效了。
5. 工程对策：把子应用当"半可信"而不是"不可信"；真正的安全隔离靠 iframe 沙箱属性（`sandbox`）或独立域名的 iframe，不要指望 `Proxy` 挡住恶意代码。

```js
// 典型逃逸：绕过沙箱拿到真实 window
const realWindow = Function('return this')()
realWindow.__leak = 'escaped'
```

**追问与易错点**：

- 追问：那 qiankun 的沙箱有什么用？答：它防的是"无意的互相污染"，比如同名全局变量、同名样式类，而不是防恶意攻击，这个定位必须说清楚。
- 陷阱：在面试里说"沙箱绝对不会污染 window"，被追问 `new Function` 就当场问穿。
- 追问：真要强隔离怎么办？答：上 iframe（跨域最好），或把不可信子应用部署到独立域名下用 iframe 承载。

### Q11 微前端的样式隔离方案怎么选？qiankun 的两种隔离模式有什么坑？

**考察点**：进阶题，考的是能否把"约定"和"机制"分层，并指出 QIANKUN 两种模式的真实限制。

**参考答案**：

> **一句话结论**：样式隔离按强度从弱到强是 BEM 命名约定、`scoped` 构建期隔离、动态样式表加选择器前缀、影子 DOM（Shadow DOM）；qiankun 提供 `strictStyleIsolation`（影子 DOM）与 `experimentalStyleIsolation`（选择器加前缀）两种，前者隔离强但兼容风险大，后者兼容好但有性能开销。

1. BEM 约定、命名空间前缀：零成本，靠人守规矩，团队一多必然失守，只能当兜底。
2. 构建期 `scoped`：Vue 的 `scoped`、CSS Modules 在编译期给类名加哈希，能隔离普通选择器，但全局样式、`body` 上的样式、第三方组件库的样式照样外泄。
3. 动态样式表：加载子应用的 CSS 时改写选择器，给每条规则加上容器前缀，是"运行期 scoped"，不用改子应用构建配置。
4. 影子 DOM：浏览器级隔离，最彻底；但全局主题变量、字体、`document.body` 上的弹窗挂载点都会失效，UI 库适配成本高。
5. qiankun 两种模式：`strictStyleIsolation: true` 用影子 DOM 包裹容器，`experimentalStyleIsolation: true` 给子应用样式统一加 `div[data-qiankun="应用名"]` 前缀（默认的 `sandbox: true` 只做动态样式隔离，这两种都要显式开启）。

| 方案 | 隔离强度 | 改造成本 | 性能 | 适用场景 |
| --- | --- | --- | --- | --- |
| BEM / 命名前缀 | 弱 | 最低 | 无开销 | 单团队、可控规范 |
| 构建期 `scoped` | 中 | 低 | 无开销 | 单一框架、子应用内隔离 |
| 动态样式表 / 实验性隔离 | 中强 | 低 | 有改写开销 | 兼容优先的存量子应用 |
| 影子 DOM / 严格隔离 | 最强 | 高 | 有渲染开销 | 强隔离、无重型 UI 库 |

**追问与易错点**：

- 追问：`experimentalStyleIsolation` 为什么加"experimental"？答：它要遍历并改写样式规则，还难以完美处理 `@media`、`@keyframes` 与动态插入的样式，属于"能用但要验证"的方案。
- 陷阱：用了 `strictStyleIsolation` 之后发现弹窗样式全丢，因为 UI 库把弹窗节点挂到了 `document.body`，根本不在影子树里。
- 追问：能两个都开吗？答：影子 DOM 已经把样式挡住了，再开前缀隔离没有意义，还会互相干扰。

### Q12 子应用的全局副作用怎么治理？定时器、事件监听、history 补丁怎么办？

**考察点**：深挖题。这是"子应用卸载不干净"的根因，面试官想听治理清单。

**参考答案**：

> **一句话结论**：全局副作用分四类——全局变量、事件监听、定时器、`history` / `location` 补丁；原则是"谁产生谁清理"，沙箱能兜住一部分，剩下的必须在 `unmount` 里显式回收。

1. 全局变量：子应用不要往 `window` 上挂东西，确需共享的走 `initGlobalState`；约定所有挂载都带子应用前缀，卸载时由沙箱统一还原。
2. 事件监听：`window` 上注册的监听，qiankun 沙箱会劫持并在卸载时清理，但挂在 `document`、`document.body` 上，或是先保存了原生函数引用再调用的，清理不到，必须自己 `removeEventListener`，且注意引用一致（不能传匿名函数）。
3. 定时器：`setInterval` 忘记 `clearInterval` 是最常见的内存泄漏；沙箱会记录并清理部分定时器，但 Promise 链、`requestAnimationFrame`、WebSocket、`ResizeObserver`、`IntersectionObserver` 一定要在 `unmount` 里手动销毁。
4. `history` 补丁：single-spa 会劫持 `history.pushState` / `replaceState` 并把路由变化广播给各子应用，因此子应用**不要自己再包一层**，否则会出现路由重复触发或跳转死循环。
5. 治理办法：统一在子应用入口提供一个"待清理资源池"，`mount` 时注册、`unmount` 时统一释放，比指望沙箱兜底靠谱得多。

```js
let stop
export async function mount(props) {
  stop = props.onGlobalStateChange(() => {})
  window.addEventListener('resize', onResize)
}
export async function unmount() {
  stop && stop()
  window.removeEventListener('resize', onResize)
}
```

**追问与易错点**：

- 追问：沙箱到底能自动清理什么？答：主要是它劫持过的 `window` 定时器与 `window` 事件监听、动态插入的样式与脚本；`document` 级别和原生引用调用的都不在其中。
- 陷阱：`removeEventListener` 传了两个长得一样的匿名函数，等于没删，这类 bug 在内存快照里非常难查。
- 追问：怎么验证卸载干净了？答：反复挂载卸载 20 次，看 `performance.memory` 与任务管理器里的内存曲线是否回落，这是最直观的验收手段。

### Q13 主子应用之间怎么通信？几种方案怎么取舍？

**考察点**：进阶高频题。考的是能不能按"耦合度 / 实时性 / 跨技术栈能力"做选型，而不是只报 API。

**参考答案**：

> **一句话结论**：轻量、低频用 `props` 透传，跨应用广播用 qiankun 的 `initGlobalState`，需要解耦多个子应用用自定义事件（`CustomEvent`），共享复杂状态才引入独立状态库；能用单向数据流解决就不要上全局总线。

1. `props` 透传：`registerMicroApps` 或 `loadMicroApp` 时把主应用的函数、token、用户信息以 props 传给子应用的生命周期函数，最直接，适合"主应用给子应用发东西"。
2. `initGlobalState`：主应用创建一个全局状态对象，返回 `onGlobalStateChange`、`setGlobalState`、`offGlobalStateChange`；子应用订阅变化、按需更新，适合用户信息、权限、主题这类全局数据。
3. 自定义事件：用 `window.dispatchEvent(new CustomEvent(...))` 或用发布订阅库解耦，子应用之间不必知道对方存在，代价是事件满天飞难以追踪。
4. 共享状态库：把 Pinia / Redux 实例作为 props 传下去，或通过 Module Federation 共享同一份依赖，能力最强但要求版本严格一致，否则出现"两个 Pinia 实例互不响应"。
5. 取舍原则：优先单向、少用双向；跨技术栈（Vue 与 React 混用）时只传纯数据和函数，不要传框架实例。

| 方案 | 耦合度 | 实时性 | 跨技术栈 | 适用场景 |
| --- | --- | --- | --- | --- |
| `props` | 中 | 即时 | 好 | 主应用下发配置、token |
| `initGlobalState` | 低 | 即时（订阅） | 好 | 用户信息、主题、权限 |
| 自定义事件 | 最低 | 即时 | 好 | 子应用之间解耦通知 |
| 共享状态库 | 高 | 即时 | 差 | 复杂状态、同构技术栈 |

**追问与易错点**：

- 追问：`setGlobalState` 是深拷贝吗？答：它只做浅层合并，改嵌套对象要用新对象替换，否则可能出现"改了但没通知"。
- 陷阱：把 Vuex / Pinia 实例直接透传，子应用版本不一致时响应式直接失效，排查成本极高。
- 追问：通信要不要做类型约束？答：要，用 TypeScript 把全局状态的形状和事件名收敛到一份共享类型声明里，这是多人协作的底线。

### Q14 路由冲突怎么解决？子应用的 base 应该怎么配？

**考察点**：进阶题，考的是"主应用拥有路由主权"这个原则。

**参考答案**：

> **一句话结论**：主应用掌握路由主权，子应用只负责自己那一段前缀；主应用用 `activeRule` 匹配前缀，子应用把路由 `base` 与打包 `publicPath` 都设成同一个前缀，两边对齐就不会冲突。

1. 分层原则：一级路径由主应用定义（如 `/order`、`/user`），子应用内部再用二级路由（`/order/list`），子应用不允许声明不受控的顶级路径。
2. 主应用侧：`registerMicroApps` 里 `activeRule: '/order'`，同时主应用自己的路由表要给这个前缀留出"空壳"路由，只负责渲染容器 `<div id="subapp"></div>`。
3. 子应用侧：Vue Router 用 `createWebHistory('/order')` 或 `base: '/order'`，让子应用路由产生的 URL 天然带前缀，`router.push('/list')` 会变成 `/order/list`。
4. 打包侧：`publicPath` 要与前缀一致，或运行时用 `window.__INJECTED_PUBLIC_PATH_BY_QIANKUN__` 动态设置，否则静态资源会 404。
5. 冲突排查：出现"两个子应用同时激活"或"路由跳转不生效"，先打印 `activeRule` 匹配结果与子应用 `base`，九成是这两处不一致。

```js
// 主应用
registerMicroApps([{ name: 'order', entry: '//localhost:8081', container: '#subapp', activeRule: '/order' }])
// 子应用
const router = createRouter({ history: createWebHistory('/order'), routes })
```

**追问与易错点**：

- 追问：`activeRule` 用字符串和函数有什么区别？答：字符串是前缀匹配，函数可以做多条件判断（如同时看路径和域名 / 环境变量），灰度分流常用函数式。
- 陷阱：子应用用 hash 模式但主应用用 history 模式，URL 会变成 `/order#/list`，刷新与分享链接都会出问题，模式必须统一。
- 追问：主应用自己的路由会被子应用抢走吗？答：会，如果主应用没有为前缀保留路由，子应用激活时主应用的组件也会渲染，页面会出现两套内容。

### Q15 为什么刷新子应用的路由会 404？主子应用之间怎么跳转？

**考察点**：基础但极高频，属于"踩过就知道、没踩过必翻车"的题。

**参考答案**：

> **一句话结论**：因为 history 模式下 `/order/list` 是前端路由，浏览器刷新会拿这个地址去请求服务器，服务器上没有这个文件所以 404；解决办法是服务器把所有未知路径回退到 `index.html`，同时保证主应用与子应用的资源路径正确。

1. 根因：单页应用（SPA）只有一张 `index.html`，`/order/list` 这个路径在服务端物理上不存在。
2. 服务器回退：Nginx 用 `try_files $uri $uri/ /index.html;`，Node 服务在路由末尾加 `app.get('*')` 兜底。
3. 主应用侧同样要配：刷新时主应用必须先加载，再根据路径激活对应子应用，所以主应用的 `index.html` 回退是前提。
4. 子应用独立访问也要能跑：子应用的 Nginx 同样要配回退，且 `base` 与部署前缀一致，否则刷新后白屏或资源 404。
5. 主子跳转的正确姿势：主应用跳子应用用 `history.pushState` 或路由 API，子应用跳主应用同理；**不要用 `location.href`**，那会触发整页刷新，丢失所有运行时状态。

```nginx
location / { try_files $uri $uri/ /index.html; }
```

**追问与易错点**：

- 追问：用了 hash 模式还会有这个问题吗？答：不会，`#` 后面的内容不参与请求，但 hash 模式对 SEO 和分享不如 history 友好。
- 陷阱：只在本地 `devServer` 验证过（开发服务器默认支持回退），上线才发现 404，部署前必须用生产 Nginx 配置自测。
- 追问：子应用跳转后主应用没反应怎么办？答：确认 `activeRule` 能被新路径匹配，且子应用没有自己包一层 `history` 导致广播丢失。

### Q16 子应用的打包配置要注意什么？为什么必须配 CORS 和 publicPath？

**考察点**：进阶实操题，考的是能不能给出可落地的构建配置清单。

**参考答案**：

> **一句话结论**：子应用必须被打成 UMD 库（webpack 4/5 都要配 `library` 与 `libraryTarget`）、运行时能拿到正确的 `publicPath`、并开启跨域资源共享（CORS），三件事缺一不可。

1. 打成库：webpack 4 用 `output: { library: 'orderApp', libraryTarget: 'umd' }`，同时给 `jsonpFunction` 起唯一名字避免多个子应用冲突；webpack 5 对应用 `output.library` 与 `chunkLoadingGlobal`。
2. `publicPath`：必须保证子应用的图片、字体、异步 chunk 都能从自己的域名加载；如果构建时无法确定，就运行时设置 `__webpack_public_path__ = window.__INJECTED_PUBLIC_PATH_BY_QIANKUN__`。
3. CORS 必须开：qiankun 用 `fetch` 抓取子应用 HTML 与 JS，属于跨域请求，服务端要返回 `Access-Control-Allow-Origin`，否则连资源都下载不到。
4. 开发服务器要显式放行：`devServer.headers = { 'Access-Control-Allow-Origin': '*' }`，并允许 `Access-Control-Allow-Credentials`（如果用 Cookie）。
5. 其他：不要用 `historyApiFallback` 之外的重定向配置搞乱 `entry` 路径，`index.html` 里不要硬编码绝对路径，产物目录结构要支持按版本发布。

```js
// webpack5 子应用
output: {
  library: 'orderApp', libraryTarget: 'umd', chunkLoadingGlobal: 'webpackJsonp_orderApp'
}
if (window.__POWERED_BY_QIANKUN__) {
  __webpack_public_path__ = window.__INJECTED_PUBLIC_PATH_BY_QIANKUN__
}
```

**追问与易错点**：

- 追问：为什么多个子应用要改 `jsonpFunction` / `chunkLoadingGlobal`？答：默认名字相同，多个子应用同时加载时会互相覆盖 webpack 的 chunk 加载器，异步加载直接错乱。
- 陷阱：只在主应用里改了 `publicPath`，忘了子应用的图片仍有相对路径，上线后图标全裂。
- 追问：Vite 子应用怎么办？答：qiankun 对 Vite 需要额外插件或改用支持 ESM 的方案，构建产物形态不同，选型时就要确认构建工具。

### Q17 公共依赖要复用还是各打各的？externals 和 Module Federation 的 shared 有什么区别？

**考察点**：进阶题，考的是版本冲突与体积之间的取舍。

**参考答案**：

> **一句话结论**：默认应该"各打各的"换取隔离与独立发布，接受体积代价；当公共依赖体积很大且版本能锁死时，才用 `externals` 外链或 Module Federation 的 `shared` 去复用。

1. 各打各的：每个子应用独立打包 Vue / React 及公共组件库，版本互不影响、发布互不阻塞，是隔离性最好也最省心的做法，代价是首屏体积叠加。
2. `externals` + CDN：主应用在 HTML 里用 `<script>` 引入 Vue / React 并挂到 `window`，子应用构建时 `externals: { vue: 'Vue' }`，所有应用共用一份。缺点是版本被硬锁，升级要全体同时改。
3. `externals` 的坑：依赖挂在全局变量上，多个子应用要求不同大版本时直接冲突，且一旦有人忘了配就会打成两份，排查困难。
4. Module Federation 的 `shared`：构建期声明共享依赖，运行时由联邦运行时选出满足 `requiredVersion` 的那一份，配 `singleton: true` 保证只加载一个实例（框架类库必须单例）。
5. 版本冲突的处理：`shared` 中版本不满足时联邦会回退到各自加载一份并给出警告，所以 `singleton` 场景要把 `requiredVersion` 写宽（如 `^3.0.0`），否则线上会静默出现双实例。

| 方案 | 复用粒度 | 版本灵活性 | 改造成本 | 适用场景 |
| --- | --- | --- | --- | --- |
| 各打各的 | 无复用 | 完全自由 | 最低 | 隔离优先、体积不敏感 |
| `externals` + CDN | 全局唯一份 | 差（锁死） | 中 | 依赖统一、无版本差异 |
| Module Federation `shared` | 运行时仲裁 | 好 | 高 | 同构团队、webpack 5 |

**追问与易错点**：

- 追问：Vue 被共享成两份会怎样？答：`provide` / `inject`、全局组件注册、Pinia 实例都会失效，表现为"状态改了但视图不更新"，非常难查。
- 陷阱：为了省几十 KB 把自己锁死在旧版本依赖上，长期维护成本远超收益。
- 追问：怎么量化该不该复用？答：看该依赖在首屏的关键路径上占多少体积，以及各子应用的版本差异是否可控，两个都乐观才做。

### Q18 登录态和用户信息怎么在主子应用之间同步？退出登录怎么处理？

**考察点**：进阶题，考的是有没有把鉴权当成一个完整的闭环，而不是"传个 token"。

**参考答案**：

> **一句话结论**：登录统一由主应用负责，token 存一处（推荐 `localStorage` 加请求头 `Authorization`），通过全局状态或 `props` 下发给子应用；登出由主应用广播，各子应用自行清理本地缓存与订阅。

1. 统一登录入口：子应用不做登录页，检测到未登录就请求主应用跳转登录，登录成功后主应用再放行路由，避免多套登录逻辑打架。
2. token 存放：跨域场景用 `localStorage` + `Authorization` 请求头比 Cookie 省心（不受 `SameSite` 与跨域限制），子应用从全局状态里取，不各自维护一份。
3. 下发方式：主应用在 `mount` 时通过 `props` 传 `token` 与用户信息，同时用 `initGlobalState` 广播变更，子应用的请求拦截器统一从全局状态读取。
4. 过期与刷新：token 刷新由主应用统一处理，子应用遇到 401 时通知主应用而不是自己弹登录框，避免多个子应用同时跳登录。
5. 登出清理：主应用重置全局状态并通知所有子应用，各子应用清空自己的 store、缓存、定时器；已挂载但未激活的子应用也要收到通知，否则会出现"退出了还能看到数据"。

**追问与易错点**：

- 追问：为什么不让每个子应用自己管 token？答：会出现不一致（A 已刷新、B 还是旧 token）、重复弹登录框、登出漏清理三类问题。
- 陷阱：把 token 放到全局变量上并期望子应用"自己读"，一旦子应用在沙箱里读的是自己代理的 `window`，就会拿到 `undefined`。
- 追问：微前端下的权限怎么做？答：菜单与路由权限由主应用下发，按钮级权限由子应用根据自己的权限码判断，避免主应用承担所有业务细节。

### Q19 微前端怎么做本地开发和联调？

**考察点**：基础实操题，考"能不能让两个团队同时高效工作"，这是落地成败的关键细节。

**参考答案**：

> **一句话结论**：核心是"子应用必须能脱离主应用独立运行"，再加一条按需切换的注册地址：本地开发时把 `entry` 指向本地 `devServer`，联调时指向测试环境，生产用配置接口或构建变量注入。

1. 子应用独立运行：入口判断 `window.__POWERED_BY_QIANKUN__`，为真时导出生命周期等待被挂载，为假时直接 `render()` 自行挂载，这样单跑子应用和嵌进主应用两条路都通。
2. 主应用按环境注册：用环境变量或运行时配置决定 `entry`，例如本地开发 `http://localhost:8081`、测试环境 `http://test-order.example.com`。
3. CORS 放行：子应用 `devServer` 必须设置 `Access-Control-Allow-Origin`，否则主应用 `fetch` 不到子应用的 HTML。
4. 联调顺序：先确认子应用自己的页面正常，再确认 CORS 与 `publicPath`，最后看生命周期是否被正确调用——按这个顺序能排掉绝大多数"白屏"。
5. 提效手段：主应用支持在控制台里切换子应用地址（把注册表挂到 `window` 上开发环境可用），或用一个本地代理服务把域名映射到各团队机器。

**追问与易错点**：

- 追问：主应用本地起、子应用也本地起，跨域怎么彻底解决？答：让子应用 `devServer` 返回跨域头，或用主应用的 `devServer.proxy` 把子应用路径代理到本地端口。
- 陷阱：子应用写死了 `publicPath: '/'`，主应用本地访问时静态资源全指向主应用，页面一片空白。
- 追问：怎么让子应用也能单独发版联调？答：子应用部署到独立测试域名并保持历史版本目录，主应用配置指向对应版本即可，不需要重新构建主应用。

### Q20 微前端有哪些性能问题？prefetch 有用吗？颗粒度怎么把握？

**考察点**：进阶题，考的是能否诚实面对"微前端通常更慢"这件事，并给出优化手段。

**参考答案**：

> **一句话结论**：微前端的性能代价来自"串行加载 + 公共依赖重复 + 运行时开销"；`prefetch`（预加载）能缓解首屏串行，颗粒度与共享策略才是决定上限的关键。

1. 串行加载：主应用 JS 执行完 → 路由匹配 → `fetch` 子应用 HTML → 再 `fetch` 子应用 JS → 才渲染，链路天然比单应用长，表现为二次白屏。
2. 预加载：qiankun 的 `prefetch` 默认为 `true`，会在第一个子应用挂载后利用空闲时间预取其他子应用的资源；可设为 `'all'` 或函数按需预取，但要注意别把首屏带宽抢光。
3. 资源重复：各子应用各打一份 Vue / React / UI 库，幸存的体积叠加；用 `externals` 或 Module Federation 共享能显著瘦身，代价是版本被约束。
4. 运行时开销：沙箱的 `Proxy` 拦截、样式改写、路由广播都有成本，子应用数量与嵌套深度越大越明显。
5. 颗粒度：子应用不是越多越好，一个子应用至少对应一个能独立发布的业务域；拆到十几个微应用会带来大量重复依赖和加载次数，反过来拖慢性能。

**追问与易错点**：

- 追问：`prefetch: 'all'` 有什么风险？答：会在首屏后立刻并发下载所有子应用资源，弱网或首屏资源紧张时反而更慢，通常按热门路由预取更稳。
- 陷阱：把微前端当性能优化方案，上线后看到首屏指标变差却找不到原因，本质是架构选错了用途。
- 追问：怎么优化二次白屏？答：主应用做骨架屏、子应用容器预设高度、预取常用子应用，三者组合基本能把体验拉回可接受区间。

### Q21 子应用怎么独立发布？怎么做版本管理、灰度和回滚？

**考察点**：进阶题，考有没有把微前端当成"发布体系"来设计，而不是只做技术接入。

**参考答案**：

> **一句话结论**：每个子应用独立构建、独立部署，产物按版本目录存放并附带一份清单（manifest）；主应用运行时读配置决定加载哪个版本，灰度靠这份配置分流，回滚就是把配置指回上一个版本。

1. 独立发布：子应用有自己的 CI 流水线，构建产物上传到自己的路径（如 `/order/1.4.2/`）并配好回退规则，与主应用发布完全解耦。
2. 版本清单：产物目录里放一份 `manifest.json` 记录版本、入口路径、是否兼容当前基座版本，主应用的注册表引用这份清单而不是写死地址。
3. 灰度分流：主应用根据用户标识（ID 尾号、白名单、请求头、环境变量）决定 `entry` 指向稳定版还是灰度版，qiankun 的 `activeRule` 支持函数式判断，天然适合做这层分流。
4. 兼容性约束：子应用要声明依赖的基座 API 版本，基座升级前先跑兼容性回归，避免"基座一升级，老版本子应用全白屏"。
5. 回滚：保留最近若干个版本的目录（不要覆盖式发布），出问题只改配置不改代码，秒级生效；主应用自身的回滚同样依赖配置而非重新构建。

**追问与易错点**：

- 追问：为什么强调"不要覆盖式发布"？答：覆盖后无法回滚，也做不到灰度共存，微前端的独立发布价值会损失一半。
- 陷阱：主应用里硬编码各子应用地址，导致加一个环境就要改一次主应用代码并发一次版，等于把耦合又搬回来了。
- 追问：版本不一致怎么排查线上问题？答：把各子应用当前版本打印到日志与页面底部，配合监控就能快速定位"是哪个版本出的问题"。

### Q22 Module Federation 的原理是什么？"运行时共享依赖"的价值在哪？

**考察点**：深挖题，面试官想听"构建期声明、运行时协商"这层机制，而不是背配置项。

**参考答案**：

> **一句话结论**：Module Federation 让应用在构建时声明"我暴露什么（`exposes`）"和"我用别人的什么（`remotes`）"，并生成一个 `remoteEntry.js` 作为运行时入口；消费方在运行时通过它协商加载远程模块与共享依赖，因此不必重新构建、也不必发 npm 包。

1. 两个角色：宿主（Host）在 `remotes` 里声明远程应用的名称与 `remoteEntry.js` 地址，远程（Remote）在 `exposes` 里声明对外暴露的模块路径。
2. 运行时加载：宿主通过脚本标签加载 `remoteEntry.js`，拿到一个容器对象，再调用它的 `get` / `init` 接口按需异步加载远程模块，模块边界天然就是异步边界。
3. `shared` 机制：所有应用把公共依赖登记到 `shared`，联邦运行时在启动时收集各方的版本与作用域，按 `requiredVersion` 协商出最终加载哪一份，`singleton: true` 时保证全局只有一个实例。
4. 核心价值：依赖从"构建期锁定"变成"运行时共享"，避免了重复打包，也让应用之间可以互相消费代码而不经过包管理器的发布流程。
5. 边界要说清：它解决的是**代码复用与共享**，不解决 JS 沙箱与样式隔离；两个远程应用仍跑在同一个 `window` 上，全局污染、样式冲突、路由冲突照样要自己处理。

```js
// 远程应用
new ModuleFederationPlugin({
  name: 'order', filename: 'remoteEntry.js',
  exposes: { './Panel': './src/Panel.vue' },
  shared: { vue: { singleton: true, requiredVersion: '^3.4.0' } }
})
```

**追问与易错点**：

- 追问：`singleton` 什么时候必须开？答：Vue、React、Pinia 这类有全局状态的库必须开，否则出现双实例，响应式与依赖注入全部失效。
- 陷阱：以为 Module Federation 就是微前端的完整答案，追问"样式怎么隔离"就答不上来。
- 追问：和 npm 私有包比优势在哪？答：省掉了"改依赖 → 发版 → 各应用升级 → 重新构建"的链路，消费方无需重新构建即可拿到最新模块，代价是运行时的稳定性要额外保障。

### Q23 微前端和 Monorepo 是什么关系？能互相替代吗？

**考察点**：基础概念题，考的是能否区分"构建期组织"和"运行部署期组织"。

**参考答案**：

> **一句话结论**：两者正交且互补——Monorepo 是"代码放在一起、构建期统一管理"，微前端是"运行时独立部署、团队自治"；Monorepo 解决复用与依赖统一，微前端解决独立发布与隔离。

1. 层次不同：Monorepo 是一个仓库里放多个包（package），共享工具链、统一版本、方便复用；微前端关注的是产物如何在浏览器里组合与隔离。
2. 解决的问题不同：Monorepo 让"改一处、全量回归"变得容易，也统一了依赖版本；微前端让"各团队按自己的节奏发布"成为可能。
3. 典型组合：一个 Monorepo 里放主应用、各子应用与公共组件库，构建时统一规范、统一依赖，运行时各子应用仍独立部署并保留沙箱隔离，这是目前最省心的落地形态。
4. 只用 Monorepo：做不到独立发布和运行时隔离，适合单团队；只用微前端：公共代码要靠 npm 包或联邦共享，协作链路偏长。
5. 判断标准：团队是否能"各自发版不互相阻塞"。能，则微前端有价值；只是为了少建几个仓库，那就用 Monorepo。

**追问与易错点**：

- 追问：Monorepo 会不会导致构建越来越慢？答：会，需要任务编排与增量构建（如 Turborepo、Nx）配合，否则 CI 时间会失控。
- 陷阱：说"上了 Monorepo 就不需要微前端了"，两者解决的不是同一层问题。
- 追问：Monorepo 里还能用 qiankun 吗？答：完全可以，仓库合并与运行时拆解互不冲突，公共依赖还可以通过工作区统一版本。

### Q24 组件级的微前端怎么做？Web Components 和低代码场景怎么用？

**考察点**：进阶题，考认知广度，能否把"应用级"和"组件级"复用区分开。

**参考答案**：

> **一句话结论**：应用级微前端拆的是"页面与发布边界"，组件级复用的是"UI 与逻辑能力"；后者优先用 npm 包或 Module Federation 共享模块，只有需要跨框架或宿主不可控时才用 Web Components 这类原生封装。

1. npm 包：最常规也最稳定，有版本语义、有类型声明，适合同一技术栈内部的组件复用。
2. Module Federation：适合"组件运行时要与宿主共享框架实例"的场景，能避免打两份 Vue / React，还能做到宿主不重新构建就拿到新组件。
3. Web Components：`custom element` 加影子 DOM（Shadow DOM），宿主是 Vue、React 还是原生页面都能用，适合低代码平台把物料封装成框架无关的组件。
4. 低代码场景的特殊要求：物料需要声明式描述（属性、事件、插槽 schema），微件要能在画布中动态挂载卸载，还要处理样式隔离与主题变量的穿透。
5. 选择原则：宿主可控就用 npm / 联邦，宿主不可控或需要跨框架才上 Web Components；引入 Web Components 就要接受 `document` 级弹窗、全局主题、无障碍属性穿透等适配成本。

**追问与易错点**：

- 追问：Web Components 的样式怎么继承主题？答：用 CSS 自定义属性（`--primary-color`）向下继承，它是少数能穿透影子 DOM 的机制。
- 陷阱：把一个复杂业务组件封装成 Web Component 后又频繁跨边界传大数据，属性序列化的成本会变成瓶颈。
- 追问：微件和微应用能混用吗？答：能，常见形态是主应用调度子应用，子应用内部再消费若干联邦微件，关键是别让边界混乱到没人说得清依赖关系。

### Q25 微前端落地最常见的坑有哪些？线上出过事故的话是哪类？

**考察点**：进阶题，考的是真实经验。面试官想听具体场景，不是泛泛而谈。

**参考答案**：

> **一句话结论**：高频坑集中在五处——基座升级破坏子应用、沙箱逃逸污染全局、内存泄漏、卸载不干净、以及"开发环境正常、生产环境白屏"的构建配置差异。

1. 版本升级破坏：主应用升级 qiankun 或公共库后，老版本子应用因为 API 变化直接白屏。对策是子应用声明兼容的基座版本，灰度先跑一批用户。
2. 沙箱逃逸：子应用通过动态脚本或 `new Function` 摸到真实 `window`，污染主应用或其他子应用。对策是不把沙箱当安全边界，关键全局变量加前缀并在验收时检查。
3. 内存泄漏：定时器、`WebSocket`、`ResizeObserver`、事件监听没清理，反复切换后内存持续上涨。对策是建"资源池"并在 `unmount` 统一释放，用反复挂载卸载做压测。
4. 卸载不干净：子应用卸载后残留 DOM、残留样式、残留全局状态，表现为"第二次进来样式变了"或"数据是上一次的"。对策是样式必须带作用域，状态必须每次 `mount` 重新初始化。
5. 构建与环境差异：本地 `devServer` 有回退和跨域头，生产没有，导致上线 404 或拿不到资源。对策是上线前用生产配置在测试环境完整走一遍刷新与跨应用跳转。

**追问与易错点**：

- 追问：怎么提前发现卸载不干净？答：写一个自动化冒烟用例，反复进出每个子应用 20 次，断言关键 DOM 数量与全局变量快照是否回到初值。
- 陷阱：只在主应用里做了兜底清理，忽略了子应用自己挂到 `document` 上的节点，卸载后留下隐形遮罩层。
- 追问：为什么微前端的坑比普通项目多？答：因为它把"一个团队内部的隐式约定"变成了"跨团队的显式契约"，任何没写下来的约定都会变成线上问题。

### Q26 如果让你给 3 个团队协作的系统做微前端改造，你会怎么设计？

**考察点**：开放设计题。考的是架构、路由、通信、发布、监控五条线能不能串成一个完整方案。

**参考答案**：

> **一句话结论**：以"主应用做壳、子应用按业务域拆、约定优于配置"为主线：一个基座负责登录、菜单、路由分发与监控，三个子应用各自独立仓库与流水线，通信只走全局状态与单向 props，发布走版本清单加灰度，监控按子应用维度打标。

1. 架构与拆分：三个团队分别负责订单、商品、用户三个业务域，各是一个独立子应用、独立仓库、独立 CI；公共 UI 与工具抽成 npm 包放私有源，跨框架共享的重组件用 Module Federation。主应用只做壳：布局、登录、菜单权限、路由容器。
2. 路由约定：主应用统一分配一级前缀 `/order`、`/goods`、`/user`，`activeRule` 与之对齐；子应用路由 `base` 与打包 `publicPath` 保持同一前缀；统一 history 模式，服务器统一配置 `try_files` 回退，杜绝刷新 404。
3. 通信与隔离：用户信息、权限、主题通过 `initGlobalState` 广播，组件级数据用 `props` 单向传入；子应用之间禁止直接依赖，需要联动就发自定义事件；JS 用代理沙箱，样式开实验性前缀隔离，子应用自身按 BEM 规范命名做兜底。
4. 发布与灰度：三个子应用按版本目录发布并生成清单，主应用读配置决定加载版本；灰度按用户 ID 尾号分流，回滚只改配置不动代码；主应用与子应用之间的基座 API 版本要显式声明并做兼容回归。
5. 监控与兜底：埋点与错误上报都带上"子应用名 + 版本号"，主应用对子应用加载失败做降级（提示 + 重试 + 可跳独立域名），子应用 `unmount` 统一走资源释放，压测项是反复进出 20 次的内存曲线。
6. 推行节奏：先拆一个边缘业务试水（不改核心链路），跑通发布、监控、回滚后再推广到另两个团队，避免一次性大改造带来的全局风险。

**追问与易错点**：

- 追问：如果其中一个团队坚持用自己的框架怎么办？答：技术上允许（微前端本就是为此而生），但要约束在"只传纯数据、不传框架实例"的通信协议上，公共能力以 npm 包形式提供。
- 追问：这套方案的成本谁来承担？答：主应用团队承担基建成本（基座、发布平台、监控接入），子应用团队承担接入成本，这部分必须提前讲清楚，否则推广时一定扯皮。
- 陷阱：一上来就把核心交易链路拆成微前端，任何一次基座变更都可能影响营收，正确做法是从边缘业务开始验证。
- 追问：怎么证明改造有价值？答：用"发布是否还需排队、单次发布耗时、线上事故定位时长"三个指标前后对比，比说"架构更先进"有说服力。

## 本章小结

- 微前端解决的是多团队独立开发、独立部署与运行时组合的问题，本质是组织与发布问题，不是性能优化方案。
- 单团队、同技术栈、发布不阻塞、首屏敏感的项目不该上微前端，拆错边界的成本远大于收益。
- 选型看四条线：隔离性、改造成本、性能、适用场景；中后台多数选 qiankun，同构且用 webpack 5 可优先 Module Federation。
- qiankun 等于 single-spa 的路由与生命周期调度，加上 HTML Entry、JS 沙箱、样式隔离和预加载。
- 沙箱防的是"无意的互相污染"，防不住恶意逃逸；要真隔离就上 iframe。
- 样式隔离按强度递进：BEM 约定、构建期 scoped、动态样式表加前缀、影子 DOM，qiankun 的严格隔离兼容风险最大。
- 子应用接入的三条硬要求：UMD 打包、正确的 publicPath、开启 CORS；刷新的 404 要靠服务器回退 `index.html`。
- 落地成败取决于发布体系与副作用治理：版本目录 + 清单 + 灰度回滚，加上卸载时统一释放定时器、监听与全局状态。
