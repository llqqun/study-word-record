## 第 20 章 前端监控、异常捕获与线上问题排查

### Q1 你们项目的监控体系是怎么搭的？都监控些什么？

**考察点**：能否把监控拆成清晰分类并说出每类的价值，而不是只答"接了个 Sentry"。答出三类 + 各自回答什么问题 + 怎么联动才算过关。

**参考答案**：

> **一句话结论**：前端监控分三块——错误监控回答"哪里坏了"、性能监控回答"哪里慢了"、行为埋点回答"用户做了什么"，三者靠同一个用户 ID 与时间轴串起来才能定位问题。

1. 错误监控（Error Monitoring）：采集 JS 运行时错误、未捕获 Promise、资源加载失败、接口异常、框架层错误，价值是主动发现"线上坏了"，而不是等用户投诉。
2. 性能监控（Performance Monitoring）：采集 LCP/INP/CLS 等核心指标、白屏时间、接口耗时、长任务，价值是把"体验变差"量化，并且必须看 P75/P95 分位而不是平均值。
3. 行为埋点（Tracking）：PV/UV、点击、曝光、表单转化、路由跳转，价值是回答"用户在哪一步流失"，也是排障时的操作路径证据。
4. 三块共享同一套标识：userId/deviceId、sessionId、release 版本、页面路径、时间戳；缺了这些就无法把"错误 + 卡顿 + 用户操作"拼成一条时间线。
5. 再叠一层告警与看板：错误率、接口失败率、白屏数、P95 耗时按版本/页面/机型聚合，超阈值触发分级告警。
6. 落地顺序：先错误监控（投入最小收益最快），再性能与埋点，最后做告警收敛与自动归因。

**追问与易错点**：

- 追问：只有错误监控够不够？答：不够。错误监控看不到"没报错但很卡"和"用户压根没进来"这两类问题，白屏有可能一条错误都不上报。
- 追问：为什么反复强调 release 版本？答：没有版本维度就无法把错误曲线对齐发布记录，也就无法在 1 分钟内判断"是不是刚发的版本有问题"。
- 陷阱：把监控等同于"接了第三方 SDK"，说不出自己项目采集了哪些字段、阈值怎么定，会显得没真正参与过。

### Q2 `window.onerror` 和 `window.addEventListener('error')` 有什么区别？

**考察点**：考两套错误捕获入口的捕获范围差异，尤其是"`onerror` 抓不到资源加载错误"这一点。

**参考答案**：

> **一句话结论**：`window.onerror` 只能抓 JS 运行时错误且只能挂一个；`addEventListener('error', fn, true)` 用捕获阶段能同时抓 JS 错误和资源加载失败，且可挂多个。

1. 绑定方式：`onerror` 是属性，重复赋值会互相覆盖；`addEventListener` 可注册多个监听器，互不干扰。
2. 捕获范围：`onerror` 只接收脚本运行时抛出的 `ErrorEvent`；资源加载失败触发的是普通 `Event`（`IMG`/`SCRIPT`/`LINK`/`VIDEO`），它发生在目标元素上、不冒泡，所以只有捕获阶段才能拦到。
3. 参数差异：`onerror(message, source, lineno, colno, error)` 是五个参数；`addEventListener` 的回调用一个 `ErrorEvent` 对象，取 `event.message`、`event.error`、`event.filename`。
4. 返回值语义：`onerror` 里 `return true` 会阻止浏览器默认的控制台输出；`addEventListener` 要用 `event.preventDefault()`。
5. 都不能捕获的东西：未捕获的 Promise 拒绝（要单独监听 `unhandledrejection`）、框架内部吞掉的错误、跨域脚本的具体信息。
6. 生产实践：两个都挂，`onerror` 作为兜底，`addEventListener('error', fn, true)` 处理资源失败，并用 `event instanceof ErrorEvent` 区分两类事件。

```js
window.onerror = (msg, src, line, col, err) => {
  report({ type: 'js', msg, src, line, col, stack: err && err.stack });
  return false; // 不阻止默认输出，便于本地调试
};

window.addEventListener('error', (e) => {
  if (e instanceof ErrorEvent) return; // JS 错误交给 onerror
  const el = e.target;
  report({ type: 'resource', tag: el.tagName, url: el.src || el.href });
}, true); // 必须捕获阶段
```

**追问与易错点**：

- 追问：为什么资源错误一定要 `true`？答：资源错误事件不冒泡，只在捕获阶段经过 window，去掉 `true` 就永远收不到。
- 陷阱：说"`onerror` 能捕获图片加载失败"是错的，这是最常见的当场被问穿的点。
- 陷阱：`onerror` 里 `return true` 会吞掉控制台报错，开发阶段别乱用。

### Q3 怎么监控图片、脚本、样式这些资源加载失败？

**考察点**：考资源错误监控的具体实现与坑：捕获阶段、`e.target` 判断、与 JS 错误区分、上报去重。

**参考答案**：

> **一句话结论**：在 `window` 上用捕获阶段监听 `error`，通过 `event.target` 拿到失败的元素，再用 `instanceof ErrorEvent` 把资源失败和 JS 错误分开上报。

1. 监听方式：`window.addEventListener('error', handler, true)`，资源加载失败不会冒泡，必须捕获阶段。
2. 取信息：`e.target.tagName` 区分 IMG/SCRIPT/LINK/VIDEO/AUDIO，`e.target.src || e.target.href` 取失败 URL，`e.target.currentSrc` 处理 `srcset`。
3. 区分类型：`e instanceof ErrorEvent` 为真说明是 JS 错误，直接 return；否则按资源失败处理。
4. 过滤噪声：上报前过滤埋点 GIF、`data:` 与 `blob:` URL、广告与第三方域名，否则日志会被噪声淹没。
5. 上报字段：资源 URL、类型、页面路径、页面版本、资源版本、是否重试、`navigator.connection.effectiveType`（判断是否弱网）。
6. 兜底价值：资源 404/超时往往是白屏与样式错乱的第一现场，比 JS 错误更早暴露，比如新版本 JS chunk 404。

**追问与易错点**：

- 追问：图片懒加载失败（还在 `data-src`）算不算资源错误？答：不算，此时还没真正发起请求；懒加载自身失败要用 `img.onerror` 单独兜底。
- 追问：怎么判断是弱网还是资源真挂了？答：结合 `effectiveType`、同批次失败率、CDN 回源日志看，失败集中在单个版本/单个文件通常是发布问题。
- 陷阱：把 `error` 监听写在 `document` 上也能收到大部分资源错误，但脚本错误事件目标是 window，写 `window` 更统一。

### Q4 未捕获的 Promise 失败怎么监控？`unhandledrejection` 有什么坑？

**考察点**：考 Promise 拒绝不在 try/catch 与 `onerror` 覆盖范围内这个事实，以及 `reason` 可能不是 Error 的坑。

**参考答案**：

> **一句话结论**：`Promise` 的拒绝不会触发 `error` 事件，必须监听 `window.addEventListener('unhandledrejection')`，而且它的 `reason` 可能只是字符串甚至 undefined，不能直接当 Error 用。

1. 注册方式：`window.addEventListener('unhandledrejection', (e) => report(normalize(e.reason)))`，`e.promise` 能拿到那个 Promise，`e.reason` 是拒绝原因。
2. 序列化坑：`reason` 可能是字符串、对象、`undefined`、带循环引用的对象；要写 `normalize()` 做安全转换，循环引用用 `JSON.stringify` 的 replacer 或 `WeakSet` 处理。
3. 阻止默认输出：`e.preventDefault()` 可以阻止浏览器控制台打印，但排障阶段建议保留。
4. 补偿事件：`rejectionhandled` 表示"后来才被 catch"，可用于给之前的上报打标记，减少误报率。
5. 兼容兜底：部分老版本 Safari 不支持 `unhandledrejection`，兜底是统一约定业务层 `catch` 后手动上报，或用 `window.onerror` 兜住能冒泡的部分。
6. 环境区分：Node 端是进程级 `unhandledRejection`，跟浏览器事件不是一回事，别答混。

**追问与易错点**：

- 追问：为什么加了 `unhandledrejection` 还是漏报？答：常见的漏点是 `then` 链中间被吞、`async` 函数里忘了 `await`、以及第三方库自己 catch 后只 `console.log`。
- 陷阱：把 `e.reason.stack` 直接上报，`reason` 不是 Error 时得到 undefined，堆栈丢了反而更难定位。
- 陷阱：区分 `unhandledrejection`（未处理）与 `rejectionhandled`（事后处理），别答成一个。

### Q5 `console.error` 劫持有什么用？Vue 和 React 的错误怎么统一收口？

**考察点**：考"框架层错误捕获"的两套机制，以及为什么必须同时做全局兜底。

**参考答案**：

> **一句话结论**：`console.error` 劫持只是采集补充（框架捕获后打印的错误能被它捡到），真正的收口靠 Vue 的 `app.config.errorHandler` 与 React 的错误边界（Error Boundary）。

1. `console.error` 劫持：重写 `console.error`，把参数序列化后上报，再调用原始方法；能捡到第三方库"只打印不抛出"的错误，但抓不到没打印的异常，且注意防重复上报。
2. Vue3：`app.config.errorHandler = (err, instance, info) => {}`，能捕获组件渲染、生命周期钩子、事件回调、`watch` 里的错误；Vue2 对应 `Vue.config.errorHandler`，另有 `warnHandler` 处理警告。
3. React：错误边界需类组件实现 `static getDerivedStateFromError`（渲染降级 UI）加 `componentDidCatch`（上报），React 16 起支持；错误边界只能捕获其子树中渲染期与生命周期里的错误。
4. React 的能力边界：事件回调、`setTimeout`、`Promise`、服务端渲染、边界自身抛出的错误都抓不到；React 18 起未捕获错误会卸载整棵树，所以边界是防白屏的必需品。
5. 统一收口：框架层 handler 上报业务上下文（组件名、`info`），全局 `onerror`/`unhandledrejection` 兜底，两者用同一个上报函数与指纹去重。
6. 上报要带组件栈：`instance.$options.name` 或 React 组件栈，否则只有一行堆栈无法定位到业务模块。

```js
// Vue3 全局收口
app.config.errorHandler = (err, instance, info) => {
  report({ type: 'vue', msg: err.message, stack: err.stack,
    component: instance && instance.$options.name, info });
};

// React 错误边界（类组件）
class Boundary extends React.Component {
  state = { broken: false };
  static getDerivedStateFromError() { return { broken: true }; }
  componentDidCatch(err, info) {
    report({ type: 'react', msg: err.message, stack: err.stack, info: info.componentStack });
  }
  render() { return this.state.broken ? <Fallback /> : this.props.children; }
}
```

**追问与易错点**：

- 追问：有了错误边界就不会白屏了吗？答：不会。边界只覆盖子树渲染错误，接口挂了、静态资源 404、根组件之外抛错仍会白屏，还要配合白屏检测。
- 陷阱：`componentDidCatch` 和 `getDerivedStateFromError` 混着答——前者做事（上报/副作用），后者返回 state 做降级渲染。
- 陷阱：劫持 `console.error` 后忘了处理原始调用与重复上报，导致同一条错误报两遍。

### Q6 一条错误日志应该带哪些字段？

**考察点**：考采集字段的完整性。字段不全，后面所有定位都会缺证据。

**参考答案**：

> **一句话结论**：一条能用的错误日志 = 错误本身 + 环境 + 用户 + 版本 + 现场，缺任何一类都会让定位从"看日志"退化成"猜"。

1. 错误本身：`message`、`stack`、错误类型（JS/资源/Promise/接口/框架）、文件名与行列号、错误指纹（用于聚合）。
2. 版本与环境：`release`（版本号或 commit sha）、`environment`（prod/pre/staging）、构建时间、`dist`（灰度分支标识）。
3. 用户与设备：`userId`、匿名 `deviceId`、`sessionId`；UA、浏览器与版本、操作系统、屏幕尺寸与 DPR、网络类型；注意做脱敏。
4. 页面现场：当前 URL 与路由参数、referrer、是否首屏、页面停留时长、上一页来源。
5. 上下文链路：`traceId`/`requestId` 用于和后端日志对齐，最近 N 条用户操作（breadcrumbs），最近的接口调用与耗时。
6. 时间与计数：客户端时间戳 + 服务端接收时间（客户端时间不可信），同一指纹的累计次数与首次/末次发生时间。

**追问与易错点**：

- 追问：为什么客户端时间不可信？答：用户可能改系统时间或时区错乱，做趋势分析必须以服务端接收时间为准。
- 陷阱：上报原始 URL 时带上 token、手机号等敏感参数，是合规事故，必须统一在 SDK 里做参数脱敏。
- 陷阱：堆栈被压在一行（未还原 source map）就丢失了文件与行列信息，光有 message 基本无法定位。

### Q7 埋点里的 PV、UV 到底怎么算？点击埋点怎么做？

**考察点**：考埋点最基础的口径问题，以及 SPA 场景下路由监听与事件委托的实现。

**参考答案**：

> **一句话结论**：PV 是页面被打开/被路由切到的次数，每切一次加一；UV 是按人（userId 优先，其次匿名 ID）去重后的独立访客数，通常按天去重。

1. PV 口径：传统多页应用每次请求算一次；SPA 要在路由切换时手动上报，并且要明确"同一页面 5 秒内来回切算几次"这类规则，口径不定就会前后数据打架。
2. UV 口径：登录用户用 `userId`，未登录用 `deviceId`/cookie 匿名 ID，都没有才退化到 IP+UA（很不准）；登录后要做一次 ID 关联（identify），把匿名行为归到用户身上。
3. 滑动去重：UV 依赖稳定的设备标识，cookie 被清、无痕模式、跨端同一用户都会导致重复计数，要写明口径而不是宣称"精确"。
4. 点击埋点三种做法：手动调用 `track()`；全局事件委托按 `data-track` 属性匹配；封装指令/组件声明式埋点（如 `v-track`）。
5. 事件委托的实现要点：SPA 要额外监听 `popstate` 与 monkey patch `history.pushState/replaceState` 才能抓到路由变化。
6. 数据质量要点：埋点 ID 用常量枚举避免手写字符串；输入框内容一律不采集；埋点要跟业务需求一起评审，补埋点比改代码更容易漏。

```js
// SPA 路由变化上报 PV（监听 history 前后都覆盖）
const trackPV = () => track('pv', { path: location.pathname, title: document.title });
['pushState', 'replaceState'].forEach((k) => {
  const raw = history[k];
  history[k] = function (...args) { raw.apply(this, args); trackPV(); };
});
window.addEventListener('popstate', trackPV);

// 声明式点击埋点：事件委托
document.addEventListener('click', (e) => {
  const el = e.target.closest('[data-track]');
  if (el) track('click', { id: el.dataset.track });
}, true);
```

**追问与易错点**：

- 追问：PV 和 UV 谁大？答：大多数场景 PV ≥ UV，但不做去重或口径混乱时会出现 UV 虚高，面试里要主动说明去重依据。
- 陷阱：只答"PV 是访问量、UV 是访客数"太浅，必须带出"SPA 怎么切、UV 靠什么去重"两个抓手。
- 陷阱：全局监听点击时忘了用 `closest` 处理事件代理链，导致子元素点击采集不到埋点 ID。

### Q8 线上出问题，你的排查思路是什么？

**考察点**：考是否具备"止血优先"的工程意识。只讲怎么找根因、不讲先恢复服务，是典型的不合格回答。

**参考答案**：

> **一句话结论**：标准顺序是"先止血、再定位、再修复、最后复盘"——恢复服务永远优先于查清根因，因为用户损失是按分钟算的。

1. 第一步止血：按影响面选最小代价手段——回滚版本、关闭灰度、切 Feature Flag 开关、降级非核心功能、限流或下线入口，目标是 5-10 分钟内让用户可用。
2. 第二步定位：先确认影响面（全量还是部分版本/机型/地域/运营商），再把错误曲线、接口成功率、性能指标的时间点对齐发布记录与配置变更记录。
3. 第三步定根因：从监控拿到指纹和堆栈，用 source map 还原到源码，结合操作路径与 `traceId` 查后端链路，能复现就本地复现。
4. 第四步修复：小改动走热修 + 灰度验证，大改动走正常发布；修复后必须验证监控曲线回落，而不是只看自己电脑好了。
5. 保留现场：排查期间先截图、导出错误列表与用户 ID 样本，别急着清缓存、重发版本，证据被覆盖会让复盘变成猜谜。
6. 复盘：写清楚时间线、影响面、根因、止血动作、改进项（含责任人与截止时间），并把"这次为什么没被监控提前发现"作为必答项。

**追问与易错点**：

- 追问：还没定位就能回滚吗？答：能，而且应该。回滚是可逆动作，先恢复再在预发环境复现定位，这是标准做法。
- 追问：如果回滚也来不及（比如问题在服务端）？答：用 Feature Flag 或网关开关关闭故障功能，前端做降级兜底页，同时推动后端止血。
- 陷阱：一上手就去翻源码、加断点，把止血拖到半小时以后，面试官基本会直接判定不合格。

### Q9 时区与时间问题在前端有哪些坑？

**考察点**：考 `Date` 的解析规则、时区处理原则，以及跨时区业务的时间口径约定。

**参考答案**：

> **一句话结论**：前端时间问题的根源是"不带时区的时间字符串"和 `Date` 的解析规则不一致，正确做法是服务端统一传时间戳或带时区的 ISO 字符串，前端只负责按需格式化。

1. 解析规则差异：`new Date('2024-01-01')` 按 UTC 解析（东八区会显示为 1 月 1 日 08:00），而 `new Date('2024-01-01 10:00')` 按浏览器本地时区解析，两者混用必然出错。
2. 兼容性坑：`new Date('2024-01-01 10:00')` 这种带空格的形式在部分 Safari 上返回 `Invalid Date`，要换成 `2024/01/01 10:00` 或直接传时间戳。
3. 序列化坑：`toISOString()` 永远输出 UTC（带 `Z`），`toString()` 输出本地时区带偏移量的字符串，日志里混用会让时间线错乱。
4. 服务端约定：接口统一传 10 位/13 位时间戳；必须传字符串时用带时区的 ISO 8601，禁止传"2024-01-01 10:00:00"这种无时区裸串。
5. 业务判断：倒计时、活动开始/结束这类判断要用服务端下发的剩余时间或绝对的 UTC 时间戳，不要用本地 `Date.now()` 和本地格式化结果做比较。
6. 展示与工具：展示层用 `Intl.DateTimeFormat` 或 dayjs/date-fns 指定 `timeZone` 转换；跨时区用户的时间展示要明确是"用户本地时间"还是"业务统一时间"，这属于产品口径，必须写进文档。

**追问与易错点**：

- 追问：为什么线上会出现"时间差 8 小时"？答：服务端返回 ISO 字符串被当成本地时间解析，或前端用 `toISOString()` 直接展示 UTC，两者都会整体偏移一个时区。
- 陷阱：用 `new Date().getTimezoneOffset()` 手算偏移量做转换，遇到夏令时（DST）地区会算错，应该用 `Intl` 或成熟库。
- 陷阱：把"时间差不等于时区问题"搞混，先确认是偏移固定 8 小时（时区）还是随机偏差（客户端时间不准）。

### Q10 跨域脚本报错为什么变成 `Script error.`？怎么解决？

**考察点**：考同源策略对错误信息的抹除机制，以及 `crossorigin` 属性与 CORS 响应头的配套要求。

**参考答案**：

> **一句话结论**：浏览器对跨域脚本抛出的错误只保留"发生了错误"这一事实，把消息和堆栈抹成 `Script error.`、行列号归零；解决办法是 `<script crossorigin="anonymous">` 加上 CDN 返回 `Access-Control-Allow-Origin`。

1. 触发条件：脚本文件与页面不同源（含 CDN、子域名），且标签上没有 `crossorigin`，脚本内部抛错就会被抹除信息。
2. 抹除内容：`message` 变成 `Script error.`，`filename`/`lineno`/`colno` 为空或 0，`error.stack` 拿不到。
3. 解决方案：给 `<script>` 加 `crossorigin="anonymous"`，同时 CDN 必须返回 `Access-Control-Allow-Origin`（通常为 `*` 或页面域名）；两个条件缺一不可。
4. 构建工具配置：webpack 的 `output.crossOriginLoading: 'anonymous'`，Vite 的 `build.rollupOptions.output.crossOriginLoading`，这样动态加载的 chunk 也带 crossorigin。
5. 不受影响的情况：同源脚本、内联脚本、`<script>` 里的内联代码报错都能拿到完整信息；这说明"只有静态资源上 CDN 才会被抹"。
6. 排查意义：线上错误里 `Script error.` 占比很高时，第一反应就是查 CDN 的 CORS 头是否配置或是否被网关改写，而不是去猜业务代码。

**追问与易错点**：

- 追问：只加 `crossorigin` 不加 CORS 头会怎样？答：脚本直接加载失败（被 CORS 拦截），比报错信息被抹更严重，所以头必须一起配。
- 追问：`crossorigin="use-credentials"` 和 `anonymous` 区别？答：前者会带 cookie，此时响应头不能用 `*`，必须回具体域名；监控场景一般用 `anonymous`。
- 陷阱：以为"改成同源部署"就没事了，实际上静态资源走 CDN + 独立域名是常态，必须从 CORS 上解决。

### Q11 错误上报怎么设计？采样、去重、限流、批量分别怎么做？

**考察点**：考上报通道的工程化设计。能说出"防止上报把自己打挂"的思考才算合格。

**参考答案**：

> **一句话结论**：上报设计的目标是"关键错误不丢、重复错误不爆、上报本身不拖慢页面"，手段是分级采样、指纹去重聚合、队列限流、批量发送。

1. 采样：错误默认全量（量可控且每条都重要），性能与埋点按比例采样（如 10%-30%）；采样用 `userId` 哈希而非纯随机，保证同一用户行为可完整还原。
2. 去重聚合：用"错误消息 + 文件 + 行列 + 浏览器 + release"生成指纹，相同指纹在时间窗内只上报一次并累加计数，把 N 条日志压成 1 条。
3. 限流队列：内存里放定长队列（如 30 条），超出丢弃并打标记 `dropped: n`；同时限制单位时间上报请求数，防止错误风暴把上报接口也打挂。
4. 批量上报：事件先进队列，定时（如 3-5 秒）或达到条数阈值时合并成一个请求发送，减少请求数；单条也要能立即发（严重错误优先）。
5. 失败重试：上报失败先存 `localStorage`（带过期时间与容量上限），下次进入页面补发；注意补发要带原始时间戳，否则时间线错乱。
6. 自我保护：上报逻辑全程 `try/catch`，SDK 自身报错绝不能影响业务；上报接口用独立域名或独立路径，避免与业务接口共享受限的并发连接。

**追问与易错点**：

- 追问：为什么错误不采样？答：错误量级远小于埋点，且每条错误可能代表一个未覆盖的场景，采样会漏掉低频但致命的错误；量大的项目可对"已知噪声"单独降采样。
- 陷阱：只答"攒一批一起发"，说不出指纹去重与队列上限，会在追问"错误风暴时怎么办"时卡住。
- 陷阱：把埋点和错误的采样率设成同一个，导致低频错误全被采掉。

### Q12 页面卸载时的埋点怎么保证发出去？`sendBeacon` 有什么限制？

**考察点**：考 `sendBeacon` 的适用场景与限制，以及"用 `visibilitychange` 而不是 `unload`"这个现代实践。

**参考答案**：

> **一句话结论**：结算类数据（停留时长、最终 CLS、离开前的错误）用 `navigator.sendBeacon` 在 `visibilitychange` 进入 hidden 时发送，它由浏览器在页面销毁后继续投递，比在 `unload` 里发 `fetch` 可靠。

1. 为什么 `unload`/`beforeunload` 不可靠：移动端浏览器经常不触发这两个事件（切后台直接被回收），而且 `unload` 里的同步 XHR 已被规范废弃。
2. 推荐时机：监听 `document.addEventListener('visibilitychange')`，当 `document.visibilityState === 'hidden'` 时上报；这个时机的数据损失远小于 `unload`。
3. `sendBeacon` 特性：以 POST 异步发送，不阻塞卸载，返回布尔值表示是否成功入队；浏览器保证尽力投递，页面关闭后仍然发送。
4. 主要限制：不能自定义请求头，只能发 `text/plain`、`application/x-www-form-urlencoded`、`multipart/form-data` 三类；用 `Blob` 指定 `application/json` 会触发 CORS 预检，实践中多数团队直接发 `text/plain` 再让后端按 JSON 解析。
5. 容量限制：单次载荷有大小上限（常见约 64KB），超限会抛异常，所以别把大段日志一把梭，要分批或截断。
6. 兜底策略：`sendBeacon` 返回 false 或浏览器不支持时，退化用 `fetch(url, { method: 'POST', keepalive: true })`，再不行退化为 `img` GET 打点。

```js
function flush() {
  if (!queue.length) return;
  const payload = JSON.stringify(queue.splice(0));
  const ok = navigator.sendBeacon
    && navigator.sendBeacon('/log/report', new Blob([payload], { type: 'text/plain' }));
  if (!ok) fetch('/log/report', { method: 'POST', body: payload, keepalive: true });
}
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flush();
});
```

**追问与易错点**：

- 追问：为什么不用 `beforeunload`？答：它只在用户主动关闭/刷新时触发，且会干扰用户操作；移动端切后台后再也不回来的场景它完全覆盖不到。
- 陷阱：在 `sendBeacon` 里自定义 `Content-Type: application/json`，结果触发预检、预检失败导致数据全丢，这是高频踩坑。
- 陷阱：把 CLS 在 `load` 时就上报，此时页面还没隐藏，得到的是不完整的 CLS 值。

### Q13 Source Map 怎么用来还原线上错误？生产环境要注意什么？

**考察点**：考"线上堆栈为什么不能用"以及 map 的私有化流程：不公开、按版本归档、按行列还原。

**参考答案**：

> **一句话结论**：生产不部署可见的 `.map`，而是用 `hidden-source-map` 生成后私有上传到监控平台，上报时带上 release 与文件路径，平台按行列号从归档的 map 还原出源码位置。

1. 生产为什么不暴露 map：`.map` 里的 `sourcesContent` 会包含完整源码，公网可访问等于源码泄露；同时攻击者能据此分析逻辑。
2. `hidden-source-map` 的作用：照常生成 `.map` 文件，但不在 bundle 末尾写 `sourceMappingURL` 注释，浏览器不会自动去取，只有持有 map 的平台能还原。
3. 相关模式对照：`source-map` 公开可用（适合内网/预发）、`hidden-source-map` 生成但不引用、`nosources-source-map` 保留行列映射但去掉源码内容，是折中方案。

| devtool（webpack） | 是否生成 map | 是否自动引用 | 是否含源码内容 |
| --- | --- | --- | --- |
| `source-map` | 是 | 是 | 是 |
| `hidden-source-map` | 是 | 否 | 是 |
| `nosources-source-map` | 是 | 否 | 否 |

4. 上传与关联：用 Sentry 的构建插件或自研 CI 步骤，把 map 以 `release + 文件路径` 为键传到监控平台；Vite 对应 `build.sourcemap: 'hidden'`，同样在上传插件里处理。
5. 还原实现：服务端用 `source-map` 库的 `SourceMapConsumer.originalPositionFor({ line, column })`，把压缩后的行列映射回源文件、原始行号与函数名；注意浏览器上报的 `colno` 从 1 开始，还原时要对应处理，差一位常常就定位到错误的上一行。
6. 最常见的失败原因：版本对不上（发布后 map 被覆盖或删除）。必须以 hash 目录或 release 维度长期归档，禁止"发完就删"，同时保证上报里的文件路径与上传键一致。

**追问与易错点**：

- 追问：为什么线上堆栈经常只有一行？答：代码被压缩成一行，没有 map 就只能看到压缩后的列号，无法对应业务代码。
- 陷阱：以为把 `.map` 免费放 CDN 就"解决"了还原问题，这是把源码直接给了所有人。
- 陷阱：用 `SourceMapConsumer` 时传的行列来自压缩代码没错，但忘了减列号偏移，导致定位总是偏一列。

### Q14 Sentry 这类平台的核心能力是什么？接入要注意什么？

**考察点**：考对成熟监控平台能力项的理解（不只是"能看报错"），以及 release、source map、采样这些接入必需配置。

**参考答案**：

> **一句话结论**：Sentry 的价值是"错误自动分组 + 上下文时间线 + 版本关联 + 性能与回放"，接入的关键是把 release、source map 上传、采样率和脱敏配好。

1. 错误分组（Grouping）：按归一化后的堆栈与错误信息生成指纹，把同一 bug 的上万条日志聚成一个 issue，并对相似错误做合并；支持自定义 `fingerprint`。
2. Breadcrumbs（面包屑）：自动采集 `console`、DOM 交互、路由切换、`fetch`/`XHR` 请求等事件，形成错误发生前的操作时间线，是"还原用户操作路径"的现成能力。
3. Release 与版本关联：初始化时传 `release`（版本号或 commit sha）和 `environment`、`dist`，就能按版本看错误、区分回归与存量问题，并在 issue 里看到"首次出现在哪个版本"。
4. Source Map：通过构建插件上传 map，堆栈直接显示源码文件与行号，还支持显示错误代码上下文片段。
5. 性能监控：`tracesSampleRate` 开启事务采样，看页面加载、接口与慢事务；`replayIntegration`（会话回放）可录制用户操作，配合 `maskAllInputs` 做隐私脱敏。
6. 用户与反馈：`Sentry.setUser({ id })` 关联用户，`ignoreErrors`/`beforeSend` 过滤噪声与脱敏，`showReportDialog` 提供用户主动反馈入口。接入注意：上报域名要能连通（必要时自建或走反向代理），采样率与配额要算成本。

**追问与易错点**：

- 追问：错误分组分错了怎么办？答：先看是不是堆栈被压缩导致归一化失败（map 没传），再考虑给该错误设置自定义 `fingerprint`，或调整 `ignoreErrors`。
- 陷阱：不配 `release` 直接接入，事后无法判断"这个错误是新版本引入的还是历史存量"，等于丢掉了最关键的判断依据。
- 陷阱：把 `tracesSampleRate` 设成 1.0 上线，量大时配额瞬间打满，性能数据全被丢弃。

### Q15 接口异常怎么监控？502 和超时具体怎么处理？

**考察点**：考请求层监控的落地点（拦截器、错误码分类、失败率），以及线上 502/超时的完整处理动作。

**参考答案**：

> **一句话结论**：接口监控统一收口在请求拦截器里，按"网络层 / HTTP 状态码 / 业务码"三类分级上报并统计失败率；遇到 502 和超时先判断影响面，再决定降级、重试还是止血回滚。

1. 拦截器收口：封装 `axios` 拦截器或 `fetch` 包装，在响应与错误分支统一上报，字段含接口路径、方法、状态码、业务码、耗时、是否超时、`traceId`；请求参数要脱敏。
2. 错误码分类：网络层错误（断网、DNS、CORS 拦截、超时）说明请求没到或没回；HTTP 4xx 多为参数/鉴权问题（401 要触发登出跳登录）；5xx 是服务端问题；业务码（`code !== 0`）属于业务规则失败，不应计为"接口故障"。
3. 失败率与耗时：失败率 = 失败数 / 总数，按接口 + 版本 + 地域维度聚合；耗时看 P95/P99 而不是平均，并区分服务端耗时与网络耗时。
4. 重试策略：只对幂等的 GET 或显式幂等接口重试，用指数退避 + 抖动，限制次数（1-2 次）；POST 提交类接口严禁自动重试，否则会产生重复下单。
5. 处理 502 的动作序列：先看是不是全站所有接口都 502（网关层问题，立即联系运维/后端止血）还是单接口（后端实例挂了），同时前端切降级数据或关闭该模块，并给出可重试的友好提示，而不是白屏或无限 loading。
6. 处理超时的动作序列：确认是全部接口变慢还是个别接口；先看服务端 P95 是否同步上涨（是则后端问题），只有网络层慢则查 CDN/DNS/运营商；前端提高超时阈值、给慢接口加骨架屏与取消逻辑，必要时限制并发。

**追问与易错点**：

- 追问：接口全挂但页面是白屏，算接口问题还是前端问题？答：算前端问题。接口失败必须被前端兜住并渲染兜底 UI，白屏说明缺少错误态设计。
- 陷阱：把所有 `code !== 0` 都上报为接口错误，导致失败率虚高、告警噪声大，业务码和故障必须分开统计。
- 陷阱：给所有请求无脑加重试，POST 重复提交的线上事故就是这么来的。

### Q16 性能指标怎么采集上报？为什么看 P95 不看平均值？

**考察点**：考 Core Web Vitals 的采集方式、`PerformanceObserver` 的使用、长任务与采样分位这几个工程点。

**参考答案**：

> **一句话结论**：用 `web-vitals` 或 `PerformanceObserver` 采集 LCP/INP/CLS/TTFB 与长任务，页面进入 hidden 时上报最终值，服务端按天聚合并以 P75 作为核心指标口径、同时看 P95 尾部。

1. 核心指标：LCP（最大内容绘制，加载性能）、INP（交互到下一次绘制，响应性）、CLS（累积布局偏移，视觉稳定性）是当前 Core Web Vitals；CLS 是全生命周期累积值、INP 会随后续交互不断刷新，两者都必须在页面隐藏时才上报最终结果。
2. INP 的版本注意：Chrome 从 2024 年 3 月起用 INP 取代 FID 作为响应性核心指标，`web-vitals` 库相应提供 `onINP`；答 FID 时要说明这是旧指标。
3. 采集方式：优先用 `PerformanceObserver` 监听 `largest-contentful-paint`、`layout-shift`、`event`、`longtask`、`navigation`、`resource` 等 entryType；`web-vitals` 是对这些的封装，能自动处理部分兼容与计算细节，业务项目直接用它更省事。
4. 长任务：`longtask` 条目指主线程被占用超过 50ms 的任务，是卡顿的直接证据；上报时要带 attribution（归属元素/脚本）才能定位到具体代码。
5. 采样率：性能数据按 10%-30% 采样即可，错误数据全量；采样按 `userId` 哈希做，避免同一用户时采时不采导致行为链断裂。
6. 为什么看 P95：平均值会被大量快页面拉平，掩盖慢用户的真实体验；P95/P99 才能反映"最差的那批用户有多差"；但对外达标口径仍以官方的 P75 为准。

```js
import { onLCP, onINP, onCLS, onTTFB } from 'web-vitals';

const send = (m) => queue.push({ name: m.name, value: m.value, rating: m.rating });
[onLCP, onINP, onCLS, onTTFB].forEach((fn) => fn(send, { reportAllChanges: false }));

new PerformanceObserver((list) => {
  list.getEntries().forEach((e) => {
    if (e.duration > 100) report({ type: 'longtask', duration: e.duration });
  });
}).observe({ type: 'longtask', buffered: true });
```

**追问与易错点**：

- 追问：CLS 为什么不能一加载完就上报？答：用户可能继续滚动、图片继续加载导致新的布局偏移，只有页面隐藏时的值才是最终 CLS。
- 追问：FID 和 INP 区别？答：FID 只测首次交互的输入延迟，INP 覆盖整页所有交互并算到绘制完成，更贴近真实卡顿感受，所以取代了 FID。
- 陷阱：只采集不上报维度（页面、机型、版本），拿到一个 P95 数字也没法定位是哪一页慢。

### Q17 曝光埋点怎么做？为什么不能"可见就算曝光"？

**考察点**：考 `IntersectionObserver` 的使用与曝光判定规则（可见比例 + 停留时长 + 去重）。

**参考答案**：

> **一句话结论**：曝光埋点用 `IntersectionObserver` 观察目标元素，只有"可见面积达到阈值并持续足够时长"才算一次有效曝光，且同一元素在同一会话内只上报一次。

1. 判定规则：通常要求可见比例 ≥ 50%（`threshold`）且持续 ≥ 1 秒，避免快速滑过、闪现的元素被算成曝光，否则数据会虚高几倍。
2. 基础实现：`new IntersectionObserver(cb, { threshold: [0.5], rootMargin: '0px' })`，在回调里用 `entry.intersectionRatio` 和 `isIntersecting` 判断。
3. 停留时长：`isIntersecting` 为真时记开始时间，为假时结算时长；不足阈值的丢弃，跨过阈值的才上报。
4. 去重：用一个集合或元素上的标记位记录已曝光的 ID，同一元素同一会话不再重复上报；列表复用（虚拟滚动）时要按数据 ID 而不是 DOM 节点去重。
5. 生命周期：组件卸载时要 `observer.unobserve(el)` / `disconnect()`，否则会造成内存泄漏和"幽灵曝光"；动态插入的节点要补观察。
6. 兼容与兜底：`IntersectionObserver` 兼容性已经很好，极老环境可退化用 `scroll` + `getBoundingClientRect` 并做节流，但成本高，优先要求降级不采集而不是硬实现。

```js
const seen = new Set();
const io = new IntersectionObserver((entries) => {
  entries.forEach((entry) => {
    const id = entry.target.dataset.exposeId;
    if (entry.isIntersecting) {
      entry.target._t = Date.now();
    } else if (entry.target._t && Date.now() - entry.target._t >= 1000 && !seen.has(id)) {
      seen.add(id);
      track('expose', { id, ratio: entry.intersectionRatio });
      entry.target._t = null;
    }
  });
}, { threshold: [0.5] });
```

**追问与易错点**：

- 追问：为什么用 `IntersectionObserver` 而不是监听 `scroll`？答：`scroll` 回调在主线程高频触发、要手动算位置，容易引起卡顿；`IntersectionObserver` 由浏览器异步调度，性能与代码复杂度都更优。
- 陷阱：把 `threshold: 0` 当成默认合理值，只要露出 1 像素就上报，曝光量会严重虚高。
- 陷阱：用 DOM 节点做去重键，列表复用后节点被重新赋值，导致同一商品的曝光被重复计或漏计。

### Q18 无埋点（全埋点）的原理是什么？和手动埋点怎么选？

**考察点**：考无埋点的实现原理与真实代价，能说出"不是银弹"才算过关。

**参考答案**：

> **一句话结论**：无埋点靠全局事件委托自动采集所有点击/浏览行为并记录元素路径，再由配置平台圈选定义有效事件；它降低开发成本，但数据量大、语义弱、路径不稳定。

1. 采集原理：在 `document` 上代理 `click`、`change`、`input` 等事件，命中后采集元素路径（标签 + id + class + `nth-child`，或优先取 `data-track` 语义标记）、页面、用户、时间。
2. 上报与圈选：SDK 先全量上报"原始行为流"，产品在可视化平台圈选某个按钮，平台生成配置下发，SDK 再按配置产出正式事件；也有 SDK 侧只上报被配置命中的行为以节省流量。
3. 优点：新增功能自动有数据、可回溯历史行为（今天能圈选上周的按钮）、埋点需求不占用发版周期。
4. 缺点一：数据量远大于手动埋点，成本与噪声都高；缺点二：路径表达式依赖 DOM 结构，改一次样式/换一次框架结构，历史配置就失效。
5. 缺点二延伸：语义弱，`nth-child(3)` 说不出业务含义；动态列表、弹窗、Canvas、跨端组件里的行为难以准确归属。
6. 实践取舍：核心业务指标（下单、支付、关键转化）用手动埋点保证准确与口径稳定，通用行为分析用无埋点补充；两者必须共用同一套用户标识与事件模型，否则数据无法对齐。合规上要默认不采集输入内容并支持一键关闭。

**追问与易错点**：

- 追问：无埋点能替代手动埋点吗？答：不能。核心口径要求稳定可审计，DOM 路径漂移会让历史数据断裂，关键指标必须手动埋。
- 陷阱：把无埋点说成"零成本"，实际是成本从开发期转移到了数据治理与平台建设期。
- 陷阱：忽略元素路径在 Vue/React 组件复用下的不稳定性，圈选配置在发版后集体失效。

### Q19 线上日志与用户反馈渠道怎么设计？

**考察点**：考移动端调试与"用户侧证据链"的搭建，重点在 ID 关联和操作路径回放。

**参考答案**：

> **一句话结论**：线上日志渠道 = 可开关的调试面板 + 统一的用户标识 + 操作路径时间线 + 低门槛的反馈入口，核心目标是"用户一句话，我们能还原他面前的屏幕和操作序列"。

1. 调试面板：移动端用 vConsole 或 eruda，但必须做开关——URL 带 `debug=1`、指定用户白名单或后端下发配置，禁止对全体用户默认开启（既影响性能也有信息暴露风险）。
2. 用户 ID 关联：登录后调用 `setUser({ id })`，未登录用匿名 `deviceId`；从匿名变已登录时上报一次关联事件（identify/alias），否则同一用户的行为被拆成两段。
3. 操作路径回放：靠 breadcrumbs 记录"路由切换 + 点击 + 接口请求与响应码 + 错误"的带时间戳序列；更完整的是 DOM 录制回放（如 rrweb 或 Sentry Replay），但必须做隐私脱敏，输入框内容一律 mask。
4. 日志关联后端：所有请求带 `traceId`/`requestId`，前端错误日志里保存该 ID，排障时用它在服务端日志里拉出完整调用链。
5. 用户反馈入口：在页面内提供低门槛反馈（一键反馈自动附带当前页面、版本、用户 ID、最近错误），Sentry 的 `showReportDialog` 可以让用户补充"我做了什么"；客服系统要与监控打通，避免反馈与日志两套孤立数据。
6. 移动端与桌面端补充手段：iOS 用 Safari 开发菜单、Android 用 Chrome `chrome://inspect` 远程调试；不方便连线的场景用 vConsole + 上报截图/录屏，客服侧收集机型和系统版本作为兜底证据。

**追问与易错点**：

- 追问：为什么 vConsole 一定要开关？答：全量开启会拖慢首屏、暴露接口参数与存储内容，还可能被恶意用户当作调试入口利用。
- 陷阱：只做错误上报不做操作路径，拿到堆栈也只能知道"哪个函数炸了"，说不出"用户在做什么操作时炸的"。
- 陷阱：忽略匿名到登录的 ID 关联，导致同一个用户被算成两个 UV，转化漏斗也对不上。

### Q20 样式错乱、兼容性崩溃、`localStorage` 写满这几种事故怎么快速处理？

**考察点**：考三类高频"非崩溃型"事故的判断顺序与止血动作，重点是有没有可执行动作。

**参考答案**：

> **一句话结论**：三类事故的共同处理逻辑是"先判断是不是刚发的版本引起的，是就立即回滚或切开关，再在预发复现定位"，而不是先改代码。

1. 样式错乱的判断顺序：先看是不是 HTML 与 CSS 版本不匹配（HTML 已更新、CSS 还是 CDN 缓存的旧文件，或反之），再看是否灰度/AB 导致新旧样式共存，最后才怀疑选择器冲突与 CSS-in-JS 顺序。
2. 样式错乱止血动作：回滚发布；无法回滚时临时在 CDN 刷新/加版本号参数强制更新；长期修法是 HTML 用 `no-cache`、静态资源用内容哈希长缓存、发布顺序先传资源后切 HTML，并让 CSS 优先级规则统一到构建层。
3. 兼容性崩溃的典型形态：低版本浏览器不支持可选链、空值合并、`BigInt`、私有字段等新语法，解析阶段就抛 `SyntaxError`，整包不执行直接白屏。
4. 兼容性处理动作：确认报错是 `SyntaxError` 且集中在特定浏览器版本后，立即回滚；根治靠构建 target 降级 + polyfill（`core-js`）+ 语法检查（在入口用一小段独立脚本探测能力，给出升级浏览器提示而不是白屏）。
5. `localStorage` 写满：写入超限抛 `QuotaExceededError`（部分浏览器是 `NS_ERROR_DOM_QUOTA_REACHED`，老版 Safari 无痕模式下甚至直接抛异常），表现为功能静默失效、登录态写不进去。
6. `localStorage` 处理动作：所有读写统一走封装并 `try/catch`；设容量与键数量上限，用类似 LRU 的策略清理过期键；大对象改用 IndexedDB；同时给写入失败一条降级路径（内存缓存），并上报"存储写入失败"这个事件本身，否则这类故障永远是静默的。

**追问与易错点**：

- 追问：为什么样式错乱要优先怀疑缓存？答：代码本身没变、只是资源版本不一致时，回滚代码是无效动作；而缓存不一致恰恰是发布流程问题，能一次修好。
- 陷阱：把 `QuotaExceededError` 当成"浏览器不支持 localStorage"，不去做容量治理，问题会周期复现。
- 陷阱：兼容性崩溃不看浏览器版本分布就改代码，结果改了也用不上——用户根本升不了浏览器，正确做法是先提示升级再逐步降级支持。

### Q21 上线后 CDN 缓存不更新、旧版本资源 404 怎么解决？

**考察点**：考缓存策略与发布顺序的配合，以及 "Loading chunk failed" 这类典型故障的前端兜底。

**参考答案**：

> **一句话结论**：入口 HTML 必须不缓存、带内容哈希的静态资源才长缓存，发布时先传资源再切 HTML；旧版本 chunk 404 要保留多版本资源并在前端做加载失败自动重试或提示刷新。

1. 缓存策略分工：`index.html` 用 `Cache-Control: no-cache`（或不缓存）保证入口永远最新；JS/CSS/图片用文件名内容哈希 + 一年长缓存，靠换名实现"更新"。
2. 发布顺序：先把新版本静态资源全量上传到 CDN，确认可访问，再更新 HTML 入口；顺序反了就会出现"新 HTML 引用不存在的资源"，也就是白屏。
3. 旧版本资源 404 的成因：用户停留在旧页面，此时发新版把旧 chunk 删了，用户点击跳转再懒加载旧 chunk 就 404，报 `Loading chunk N failed` 或 `Failed to fetch dynamically imported module`。
4. 止血动作：立即恢复被删的旧版本资源目录（保留 N 个版本或 N 天），这是最快的恢复手段；无法恢复时让用户刷新页面拿到新版本。
5. 前端兜底：在路由层或动态导入处捕获加载失败，自动重试一次（换 cache-busting 参数），仍失败则提示"版本已更新，请刷新页面"并调用 `location.reload()`；Vite 可监听 `vite:preloadError` 事件，webpack 可捕获 `chunk` 加载失败。
6. 长期机制：CDN 保留多个版本目录、构建产物按 release 分目录归档、Service Worker 缓存要随版本更新（`skipWaiting` + `clients.claim`），并在监控里对 `chunk` 加载失败单独设告警——它是"缓存/发布流程坏了"的第一信号。

**追问与易错点**：

- 追问：为什么不能只靠刷新 CDN 解决？答：用户本地和中间节点的缓存不可控；正确做法是改动文件名，而不是指望所有缓存被刷掉。
- 陷阱：把 HTML 也设成长缓存，结果用户永远停在旧版本，是典型的版本不更新事故。
- 陷阱：`service worker` 缓存了旧 HTML 又没做版本更新，导致强制刷新都无效，排查时容易漏掉这一层。

### Q22 白屏怎么检测？有哪些方案，各有什么取舍？

**考察点**：考白屏检测的多种实现思路与误判控制，能否给出可落地的组合方案。

**参考答案**：

> **一句话结论**：白屏检测没有单一可靠指标，生产上通常组合"关键节点探针 + 一段时间内 DOM 是否有变化 + 屏幕采样点命中判断"，并要求上报时附带足够现场信息。

1. 关键节点探针：约定根容器（如 `#app`），在 `load` 后延迟 2-3 秒检查它是否存在、`innerHTML` 长度是否为 0、宽高是否为 0；最便宜，但换框架或改根节点就失效。
2. 关键接口/就绪标记：在首屏数据渲染完成后打一个全局标记（如 `window.__PAGE_READY__`），超时未打标即判定异常；最贴近业务真实可用状态，误判率最低。
3. `MutationObserver`：监听根容器在观察窗口内的变更次数，一次都没有说明页面根本没渲染出内容；能区分"渲染太慢"和"完全没渲染"。
4. 屏幕采样点：用 `document.elementsFromPoint(x, y)` 在屏幕上按九宫格或网格取十几个点，如果绝大多数点命中的都是根容器、`body` 或 `html`，判定为白屏；这是最能反映"用户眼里真的是一片白"的方案。

```js
function isBlank() {
  const pts = [[0.5, 0.5], [0.2, 0.2], [0.8, 0.2], [0.2, 0.8], [0.8, 0.8], [0.5, 0.3], [0.5, 0.7]];
  const w = innerWidth, h = innerHeight;
  const blank = pts.filter(([rx, ry]) => {
    const el = document.elementsFromPoint(w * rx, h * ry)[0];
    return !el || ['HTML', 'BODY'].includes(el.tagName) || el.id === 'app';
  });
  return blank.length / pts.length >= 0.9; // 九成采样点都空
}
```

5. 截图/骨架对比：在小程序容器或客户端 WebView 里可以截图与上一版本基准图做像素差异，准确但成本高、需要端上配合；Web 端一般不做实时截图。
6. 误判与上报：加载中的骨架屏、全屏弹窗、深色主题都会干扰判断，所以要在"页面进入 hidden 或超时后"再判定，并且上报时带上 DOM 快照、资源失败列表、最近错误与接口状态——只报一句"白屏"等于没有信息量。

**追问与易错点**：

- 追问：为什么不能只看 `#app.innerHTML === ''`？答：接口挂掉时框架可能渲染了一个空的容器或错误占位，`innerHTML` 不为空但用户看到的仍是白屏，所以要叠加屏幕采样。
- 陷阱：在 `load` 事件里立刻判断，慢网用户的正常首屏会被误报成白屏，必须给足等待时间并区分首屏与二次进入。
- 陷阱：白屏上报不带当时的资源与接口状态，定位时还得再复现一次，浪费最宝贵的止血时间。

### Q23 埋点 SDK 的设计要点有哪些？怎么保证埋点数据质量？

**考察点**：深挖题。考 SDK 的架构取舍（体积、性能、可靠性、可维护性）与数据治理，不是只写一个 `track()` 函数。

**参考答案**：

> **一句话结论**：埋点 SDK 的设计围绕四条线展开——统一事件模型、队列与可靠投递、对业务性能影响最小、数据质量可校验；任何一条缺失，数据迟早不可信。

1. 事件模型：统一为"事件名 + 公共属性 + 自定义属性 + 上下文"，公共属性包含 `appId`、`userId`/`deviceId`、`sessionId`、页面、`release`、渠道、时间戳；事件名用常量枚举集中管理，禁止散落字符串。
2. 投递可靠性：内存队列 + 批量上报 + 失败本地缓存补发；每条事件生成唯一 `eventId` 用于服务端幂等去重；时间戳以服务端接收时间为准，客户端时间仅作参考。
3. 性能与体积：SDK 异步加载，首屏关键路径上只保留极少量逻辑（或先入队后加载真正 SDK 再补发）；上报用 `sendBeacon`，空闲时用 `requestIdleCallback` 处理序列化；gzip 后控制在十几 KB 量级。
4. 可维护性：提供 `debug` 模式在控制台打印即将上报的事件，便于联调与验收；对外 API 保持稳定（`init`/`track`/`setUser`/`setSuperProperties`/`flush`/`disable`）。
5. 数据质量校验：埋点要有规范文档与命名约定（如 `模块_动作`），并在 CI 或测试环境加校验脚本，缺埋点、参数类型错误直接失败；关键漏斗要有人工对账（前端事件数 vs 后端业务订单数）来发现漏报与重复。
6. 治理与合规：埋点有生命周期，下线功能要同步下线埋点，否则表越来越脏；不采集输入内容与敏感信息，支持一键关闭采集以应对合规要求。

**追问与易错点**：

- 追问：怎么发现埋点漏报？答：两条对账思路——前端事件量与服务端业务量比对（差异超阈值告警），以及用同一事件的 `eventId` 查重；再加上预发环境的自动化校验。
- 追问：SDK 报错会不会影响业务？答：必须全程 `try/catch` 且永不抛出，SDK 内部的异常只能自己吞掉并打日志，绝不能阻断业务流程。
- 陷阱：把 `track()` 写成同步发请求，用户快速点击时产生大量请求，既拖慢页面也把上报接口打挂。

### Q24 线上非常卡、疑似内存泄漏，怎么定位？

**考察点**：深挖题。要求给出可执行的动作序列与判断依据，而不是罗列名词。

**参考答案**：

> **一句话结论**：卡顿先看主线程有没有长任务、有没有频繁重渲染；内存泄漏先用性能监视器看内存曲线是否只涨不落，再用三次堆快照对比找出未释放对象。

1. 第一步确认影响面：用长任务与 INP 的上报数据，定位是全局卡还是特定页面、特定机型、特定版本；这一步决定后面是"改代码"还是"先回滚"。
2. 卡顿定位动作序列：打开 Performance 面板录一段（至少包含一次卡顿）→ 看 Main 轨道上的长任务 → 展开调用树找到耗时函数 → 判断属于哪一类：大列表渲染、单次超大计算、频繁重渲染（React/Vue 的响应式触发过密）、还是强制同步布局（读写 `offsetHeight` 交替导致的重排）。
3. 常见修法：长列表用虚拟滚动或分页；大计算搬进 Web Worker；高频事件防抖节流；避免在循环里读写布局属性；React 用 `memo`/`useMemo` 收敛重渲染，Vue 控制响应式粒度和 `v-once`/`v-memo` 的使用。
4. 内存泄漏判断：用 Performance Monitor 看 JS Heap 与 DOM Nodes 曲线，反复进出同一页面若干次，如果每次回来内存台阶都上升、GC 后不回落，就基本确认泄漏。
5. 内存泄漏定位动作序列：进入页面 → 手动 GC → 拍第一个堆快照 → 反复进出页面 3-5 次 → 再 GC 拍第二个快照 → 用 Comparison 视图对比新增对象；重点看 Detached DOM tree、持续增长的数组/Map、以及通过闭包或全局缓存被引用的对象。
6. 高频泄漏源清单：未清理的 `setInterval`/`setTimeout`、未解绑的全局事件监听与 `resize`/`scroll` 监听、未 `disconnect` 的 `IntersectionObserver`/`MutationObserver`、未退订的事件总线或 WebSocket、挂在 `window` 上的大对象缓存、以及定时器或请求回调里闭包持有的旧组件实例。

**追问与易错点**：

- 追问：单次快照能看出泄漏吗？答：不能，必须做"多次操作 + GC + 快照对比"的增量分析，单张快照只能看当前占用。
- 追问：为什么反复进出页面必须是多次？答：一次进入的占用可能被浏览器缓存复用，重复几次后仍单调上升才是泄漏特征。
- 陷阱：只凭"用户说卡"就改代码，没有先确认影响面与版本，改完也无法验证是否修好。

### Q25 灰度发布和 Feature Flag 的价值是什么？代价是什么？

**考察点**：深挖题。考察的是变更风险控制思维，以及能否说出它的成本，避免把它讲成万能药。

**参考答案**：

> **一句话结论**：灰度发布把"一次性全量变更"变成"小流量试探"，把故障影响面从全量压到 1%-5%；Feature Flag 进一步把代码发布与功能上线解耦，让止血变成"关开关"而不是"发版本"。

1. 灰度的维度：按用户 ID 哈希百分比、地域、渠道、设备类型、内部员工白名单，通常先内测用户再 1% → 10% → 50% → 100%，每一档观察错误率与核心指标再放量。
2. 核心价值：故障只影响小流量；能拿到新旧版本的真实数据对比（性能、转化），而不是只靠预发环境猜。
3. Feature Flag 的价值：代码已经发布但功能未开启，出问题秒级关停，不需要重新构建与发布；配合开关可以实现新老逻辑并行、AB 实验和"随时回退"。
4. 关键前提：开关必须能动态下发 + 本地缓存兜底（下发失败时用缓存值，避免全量用户都拿不到配置）；开关的默认值要选"安全侧"。
5. 代价一：分支逻辑变多，代码可读性下降，需要维护开关清单与清理计划，否则会积累成"flag 债务"，几年后没人敢删。
6. 代价二：多版本共存会带来兼容问题（旧页面引用新接口、新老数据结构不一致），灰度期间的接口必须前后兼容，不能只靠前端开关；灰度也会让监控分析变复杂，必须按版本维度看数据。

**追问与易错点**：

- 追问：开关配置服务挂了怎么办？答：必须本地缓存 + 默认关闭（安全侧）兜底，并且开关只用于"关掉新功能"，不能把核心链路可用性押在开关服务上。
- 陷阱：把灰度当成"不用测试"的免死金牌，灰度只是缩小影响面，回归测试仍然必须做。
- 陷阱：忘记清理过期开关，导致分支爆炸，后续改动越来越不敢动——这是灰度最常见的长期成本。

### Q26 线上不能连调试器，有哪些调试手段？

**考察点**：深挖题。考对真实线上调试渠道的掌握程度，包括安全边界的把握。

**参考答案**：

> **一句话结论**：线上调试靠"可开关的日志面板 + 代抓包 + URL 调试参数 + 录制回放 + 远程调试"五件套，共同原则是只对授权用户开放、不暴露敏感信息。

1. 远程日志开关：URL 参数（如 `?debug=1`）或后端配置下发的开关控制日志等级，日志既打印到面板也上报；问题排查完必须能远程关闭，避免长期开启。
2. 移动端面板：vConsole/eruda 提供 Network、Storage、Console、Elements 视图，是端内最快的手段；配合"一键复制日志/导出截图"给客服或研发。
3. 代理抓包：Charles、Fiddler、mitmproxy 配置中间人证书，可以看到完整请求响应；手机端要装证书并信任，HTTPS 抓包要注意证书固定（SSL Pinning）的 App 抓不到。改包 mock 响应还能验证"是不是接口数据问题"。
4. URL 调试参数：除了 `debug`，常用 `mock=1` 走本地假数据、`sw=off` 关闭 Service Worker、`nocache=1` 强制拉新资源；这些参数要在代码里集中管理，并限制只对白名单/内网生效。
5. 录制回放：Sentry Replay 或 rrweb 录制 DOM 变化与操作序列，可以像看视频一样重放用户操作，是复现"偶现问题"最有效的手段，前提是做好输入脱敏与合规告知。
6. 远程调试：Android 用 `chrome://inspect` 连真机，iOS 用 Safari 的开发菜单；无法连线时用"用户反馈附带日志与截图"兜底，同时带上 `traceId` 到服务端日志里查完整链路。

**追问与易错点**：

- 追问：`?debug=1` 会不会有安全风险？答：会。必须限制为白名单用户或内网，调试面板里的接口参数、存储内容、接口地址都属于敏感信息。
- 陷阱：用线上真实数据直接改包 mock，忽略后端可能因此产生的脏数据，mock 只应用于确认问题边界。
- 陷阱：忘记关调试开关，日志量和上报量暴增，成本与性能双双受损。

### Q27 告警应该怎么设计？为什么告警多了反而没人管？

**考察点**：深挖题。考告警分级、抑制收敛与响应机制，核心是"告警要被信任"，答出告警疲劳的成因才算深入。

**参考答案**：

> **一句话结论**：告警设计的目标是"该响的必响、不该响的不响"，靠分级定响应时效、靠抑制与收敛防风暴、靠定期治理保持信噪比。

1. 分级：P0 全站不可用（白屏率飙升、核心接口全挂）电话 + 群 @全员；P1 核心链路受损（下单失败率超阈值）立即通知值班；P2 局部功能异常当日处理；P3 体验指标劣化进日报。级别直接绑定响应时效与升级路径。
2. 阈值设计：用"错误率 + 持续时间 + 影响用户数"三个条件组合，例如核心接口 5 分钟内失败率 > 1% 且影响用户 > 100 才触发，避免瞬时抖动误报；基线取自历史分位数而不是拍脑袋。
3. 抑制（Suppression）：同一指纹在窗口期内只告警一次，静默期内只累计不重复通知；维护发布期静默名单（发布后 10 分钟内的已知错误不告警），但要标注"静默不等于不记录"。
4. 收敛（Aggregation）：按根因聚合而不是按条数告警，一次事件只发一条；错误风暴时自动降级为"汇总告警 + 看板链接"，避免群里几百条消息把真正的问题淹没。
5. 值班与响应：明确值班人与备份人、响应时效（如 P0 5 分钟响应、15 分钟止血）、超时自动升级到主管；告警必须可认领、可标记"处理中/已恢复"，形成闭环。
6. 告警治理：定期复盘告警准确率与无效告警占比，删除长期无人处理的告警项，补充缺失的监控项；告警数量不是越多越好，能被人信任的少量告警才有效。

**追问与易错点**：

- 追问：为什么告警多了等于没有告警？答：人会对持续噪声脱敏，最终所有告警都被忽略；一条真实 P0 混在几百条噪声里，响应时间会显著变长。
- 陷阱：只按"单条错误出现"就告警，没有窗口期与影响面条件，一有抖动就响，这就是告警疲劳的根源。
- 陷阱：告警只发到一个没人看的邮件列表，缺少值班与升级机制，等同于没告警。

### Q28 怎么做复盘和预防，让同类事故不再发生？

**考察点**：深挖题。考工程闭环能力：从"修好这一个 bug"升级到"让这一类 bug 进不来"。

**参考答案**：

> **一句话结论**：复盘要产出可验证的改进项，预防要把卡口前移——监控前置、E2E 覆盖核心链路、预发与线上同构、发布可回滚可灰度。

1. 复盘文档四要素：时间线（首次发生、发现、止血、恢复）、影响面（用户数、订单/金额、时长）、根因（连续追问"为什么"直到流程或设计层面）、改进项（每条必须有责任人和截止时间，且可验证）。
2. 复盘必须回答的一个问题：这次为什么没有被监控提前发现？答案通常指向"缺埋点/缺白屏检测/告警阈值太松"，这些比 bug 本身更值得修。
3. 监控前置：新功能上线时同步上线错误监控、关键埋点与告警，把监控纳入开发完成定义（DoD），而不是等出事后补。
4. E2E 兜底：用 Playwright/Cypress 覆盖登录、下单、支付这类核心链路，在预发与发布后各跑一次冒烟，把"用户能走通主流程"变成自动化断言。
5. 预发与线上同构：预发必须包含 CDN、网关、真实构建产物与缓存策略，否则"预发好的、线上一发布就白屏"会反复出现；差异越大，预发越没有价值。
6. 发布卡口：CI 强制类型检查与构建检查、灰度分批放量、一键回滚预案、发布窗口避开业务高峰、发布后 10 分钟内专人盯监控看板；变更与错误曲线的关联分析要成为固定动作。

**追问与易错点**：

- 追问：复盘会不会变成追责会？答：定位到人的复盘会让人隐瞒信息，正确做法是对事不对人，关注流程与系统缺陷，才能拿到真实时间线。
- 陷阱：改进项写成"加强测试意识""提高代码质量"这种无法验证的口号，等于没有改进。
- 陷阱：只修 bug 不做卡口，同类问题会在下一次发布时以另一种形式复发，这是最典型的"假闭环"。

## 本章小结

- 监控三块各有分工：错误监控回答"哪里坏了"，性能监控回答"哪里慢了"，行为埋点回答"用户做了什么"，三者必须共用 userId、sessionId、release 才能拼出时间线。
- `window.onerror` 只抓 JS 运行时错误且只能挂一个；资源加载失败必须在 `window` 上以捕获阶段监听 `error`，并用 `instanceof ErrorEvent` 区分两类事件。
- Promise 拒绝要用 `unhandledrejection` 兜住，且 `reason` 可能不是 Error；框架层错误靠 Vue 的 `app.config.errorHandler` 与 React 错误边界的 `componentDidCatch` 收口，但它们都抓不到事件回调与异步错误。
- 跨域脚本报错被抹成 `Script error.`，解决方案是 `<script crossorigin="anonymous">` 与 CDN 的 `Access-Control-Allow-Origin` 同时具备，缺一不可。
- 上报设计记住四件事：错误全量、性能与埋点采样、指纹去重聚合、队列限流加批量；页面卸载时的数据用 `sendBeacon` 在 `visibilitychange` 转 hidden 时发。
- 生产环境用 `hidden-source-map` 生成 map 并私有上传，按 release 归档，用 `originalPositionFor` 按行列还原，版本对不上是还原失败的头号原因。
- 排查线上问题永远是"先止血（回滚/降级/开关）→ 再定位 → 再修复 → 复盘"，恢复服务优先于查清根因。
- 白屏检测没有单一指标，生产上用关键节点探针 + 就绪标记 + `MutationObserver` + `elementsFromPoint` 屏幕采样组合判断，并在上报时附带 DOM 快照、资源失败与最近错误。
