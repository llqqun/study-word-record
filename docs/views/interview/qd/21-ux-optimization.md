## 第 21 章 用户体验优化与交互细节

### Q1 接口很慢的时候，你怎么让用户不觉得卡、不以为页面死了？

**考察点**：考"等待期管理"的成套手段，能不能说出四类可执行技术手段并讲清各自代价，而不是只会说"加个 loading"。

**参考答案**：

> **一句话结论**：用户的等待体感等于"真实耗时减去预期管理"，所以优化分两步——先用骨架屏、乐观更新、任务分片把等待藏起来，再用进度、文案、可取消的操作把预期讲清楚。

1. 即时反馈：任何点击在 100ms 内必须有视觉变化（按压态、loading、乐观更新），超过 1s 才出现"正在处理"，超过 10s 必须给进度或可取消入口，否则用户就会重复点击。
2. 骨架屏（Skeleton Screen）：只用于有稳定结构的内容区，用与真实内容一致的布局占位，内容到达后原地替换，不产生跳跳；不确定有没有内容的区域不要用骨架屏。
3. 乐观更新（Optimistic UI）：点赞、勾选、删除这类高成功率操作用户动完立即出结果，失败再回滚并提示，代价是必须实现回滚与并发保护，详情见 Q4。
4. 感知性能：先渲染后计算（首屏只渲染可见区域）、长任务分片（`requestIdleCallback`、`scheduler.postTask`、`requestAnimationFrame` 切片）、预取下一页数据，让主线程始终留给交互。
5. 文案与可取消：把"加载中"换成"正在为你生成报告，约 10 秒"；能取消的请求挂 `AbortController`，让用户有控制感。

**追问与易错点**：

- 追问：先做哪个？答：先做前端能立刻改的（骨架屏、乐观更新、分片、防重复提交），再推后端优化接口耗时，因为前者当周就能上线验证。
- 陷阱：把体验优化等同于"加动画"。动画不缩短时间，如果 loading 逻辑没做，光加过渡动画反而掩盖问题。

### Q2 loading 态怎么设计？按钮防重复提交有哪几层保障？

**考察点**：考 loading 的分级与防重复提交的完整落点，面试官想听的是"每一层各解决什么"，不是"把按钮 disabled"。

**参考答案**：

> **一句话结论**：loading 要分级（按钮级、区域级、全局级、进度型），防重复提交要做四层——UI 禁用、逻辑锁、请求取消、服务端幂等，只做 UI 禁用是防不住的。

1. 分级原则：按钮级 loading 用于提交类操作，区域级用于局部刷新，全局 loading 只用于页面初始加载；全局遮罩滥用是体验大忌，它会让用户以为整个应用卡死。
2. UI 禁用：请求前置 `pending = true` 并给按钮加 `disabled`，同时把文案换成"提交中"，按钮宽度用 `min-width` 固定，避免文案变化导致布局跳动。
3. 逻辑锁：`disabled` 的原生提交按钮会被浏览器拦住回车隐式提交，但挡不住代码里主动调用 `form.submit()`、非原生按钮以及快速连点带来的竞态队列，所以在处理函数入口要用同步标志位或 `Promise` 状态提前 `return`。
4. 请求取消：新请求发起前用 `AbortController.abort()` 取消上一个未完成的同类请求，防止旧响应后到覆盖新数据（竞态）。
5. 服务端幂等：网络重试、用户刷新页面、多端同时操作都会绕过前端锁，真正的兜底是后端按幂等键（Idempotency-Key）去重，前端为每次提交生成唯一键。
6. 时间细节：spinner 延迟约 300ms 再显示并设最短展示时间（约 300ms），否则快速返回的请求会闪一下，比不显示更刺眼。

```js
let pending = false;
async function submit() {
  if (pending) return;              // 逻辑锁：挡住键盘与连点
  pending = true;
  try {
    await api.submit(payload, { idempotencyKey: uuid() });
  } finally {
    pending = false;
  }
}
```

**追问与易错点**：

- 追问：防抖能不能防重复提交？答：能减少但不能保证，用户等 2 秒没反应会再点，防抖窗口过后照样发第二个请求。
- 追问：为什么 loading 要延迟显示？答：本地或边缘节点 50ms 返回的请求闪一下 spinner 反而割裂，延迟加最短展示能让状态变化稳定。
- 陷阱：只给按钮加 `disabled` 就交差，被追问"用户按回车提交两次怎么办"时答不上来。

### Q3 骨架屏和普通 loading 转圈怎么选？骨架屏最容易踩什么坑？

**考察点**：考骨架屏的适用边界与实现要点，重点是它"不是视觉装饰，而是防抖动和建立预期的工具"。

**参考答案**：

> **一句话结论**：结构可预知的内容区用骨架屏（它能让用户提前知道"这里会出现什么"，并把版式提前占好）；结构不可预知的操作用转圈或文字提示。

1. 选型依据：列表、卡片、详情页这类布局稳定的场景用骨架屏；按钮提交、未知数量的动态卡片、只有一行的简短内容用转圈或按钮 loading，硬套骨架屏反而制造噪声。
2. 结构一致：骨架块的宽高比例、间距、圆角必须与真实内容一致，否则内容到达时整页重排，骨架屏就成了 CLS（Cumulative Layout Shift，累积布局偏移）的来源。
3. 尺寸预留：外层容器用 `aspect-ratio` 或写死最小高度，保证骨架与真图的占位高度完全相同。
4. 动效：只用透明度呼吸或背景位置平移的微光动画，必须遵守 `prefers-reduced-motion`，避免大面积高频闪烁引发不适。
5. 收尾：数据到达后原地替换，不要再插入一次入场动画；加载失败要切换成错误态，不能让骨架屏无限循环（否则用户会一直等）。

```css
.skeleton { aspect-ratio: 16 / 9; border-radius: 8px; background: linear-gradient(90deg, #eee, #f7f7f7, #eee); background-size: 200% 100%; animation: sk 1.4s infinite; }
@keyframes sk { from { background-position: 200% 0 } to { background-position: -200% 0 } }
@media (prefers-reduced-motion: reduce) { .skeleton { animation: none } }
```

**追问与易错点**：

- 追问：骨架屏能提升性能吗？答：不能，它只改变感知。真实指标（LCP、INP）不会因为骨架屏变好，但它能降低跳出率并减少"以为坏了"的重复点击。
- 陷阱：骨架屏和内容布局不一致，加载完成后页面整体下移，被问"那你这骨架屏有什么用"就答不上来。
- 陷阱：把骨架屏做成全局遮罩，用户看不见页面结构，反而不如直接渲染静态框架。

### Q4 乐观更新怎么做？失败了怎么回滚？

**考察点**：考乐观更新的完整实现链路，核心是回滚、并发与幂等，面试官常追问"用户连点三次怎么办"。

**参考答案**：

> **一句话结论**：乐观更新是"先改本地状态、再发请求、失败回滚并提示"，前提是操作成功率高、失败可恢复，并且你为每次操作留了回滚快照。

1. 适用范围：点赞、收藏、勾选、删除列表项这类高频低风险操作适合；支付、下单、转账这类不可逆操作绝对不能用乐观更新。
2. 快照回滚：发起请求前记录被改动数据的前值（或整条记录副本），失败时精准还原这一条，不要整体刷新列表——整体刷新会让用户看到闪烁和位置跳动。
3. 并发保护：用请求序号（`seq`）或 `AbortController` 丢弃过期响应；连点同一个开关时只保留最后一次意图，中间结果不落地。
4. 幂等键：为每次操作生成 `idempotencyKey` 随请求发给后端，避免"其实成功但响应丢了"导致重试写入两次（例如重复扣款、重复点赞计数）。
5. 失败提示：回滚后必须给可见反馈（轻提示 + 该条目的错误态），否则用户以为操作生效了；网络类失败给"重试"入口，业务类失败说明原因。
6. 状态归一：回滚后要让服务端数据成为唯一真相，收到后续查询结果时以服务端为准，避免本地快照与服务端长期不一致。

```js
async function toggleLike(item) {
  const prev = item.liked;           // 1. 拍快照
  item.liked = !prev;                // 2. 先改 UI
  try {
    await api.like(item.id, { idempotencyKey: `${item.id}-${Date.now()}` });
  } catch (e) {
    item.liked = prev;               // 3. 失败精准回滚
    toast.error('操作失败，请重试');
  }
}
```

**追问与易错点**：

- 追问：用户在飞行模式下点赞，回滚会闪一下，怎么优化？答：检测离线状态时不发请求，把操作放进离线队列，UI 标记为"待同步"，联网后按序重放。
- 追问：断网重试会不会重复执行？答：会，除非有幂等键或服务端按业务唯一键去重，这是乐观更新必须配套的一环。
- 陷阱：失败时直接整体 `refetch` 列表，用户会看到刚点的内容跳回去甚至顺序变化，体验比不加乐观更新更差。

### Q5 首屏总是白屏，SSR 怎么改善？它有哪些坑和代价？

**考察点**：考 SSR（Server-Side Rendering，服务端渲染）到底改善了什么、代价是什么，能不能讲清"SSR 不解决 hydration（注水）之后的卡顿"。

**参考答案**：

> **一句话结论**：SSR 让首屏 HTML 直接带内容，用户不用等 JS 下载执行就能看到页面，改善的是"首次可见"；它不改善交互速度，交互仍要等 hydration 完成，而且带来服务端成本和两类典型 bug。

1. 解决什么问题：由服务端把组件渲染成 HTML 返回，浏览器收到即可绘制，因此白屏时间从"HTML + JS + 接口"缩短为"HTML"，同时利于 SEO 与社交卡片抓取。
2. 三种形态：SSR（每次请求动态渲染）、SSG（Static Site Generation，构建期生成静态页，最便宜）、ISR/流式渲染（`renderToPipeableStream`，边渲染边吐出 HTML，首字节更快）。
3. 实现选择：Nuxt、Next.js 等框架已封装同构数据获取与路由级渲染策略，自研的成本远高于收益。
4. 代价：服务端要背渲染压力（QPS 高时要用缓存、CDN、降级到 CSR），页面逻辑必须同构（`window`、`document`、`localStorage` 只能在 `onMounted`/`useEffect` 里访问）。
5. 典型坑一：hydration 不匹配（Mismatch）。服务端与客户端首帧输出必须完全一致，`Date.now()`、随机数、时区差异都会触发告警和重渲染，要放在挂载后再计算。
6. 典型坑二：SSR 只是首屏快照，之后的列表刷新、权限判断仍走客户端，所以它常与骨架屏配合，而不是替代骨架屏。

**追问与易错点**：

- 追问：SSR 之后首屏还是卡？答：瓶颈在下游——服务端接口 RTT、HTML 体积过大、hydration 阻塞主线程，要做数据预取并行化与 hydration 前的内容可交互化。
- 陷阱：说"SSR 能提升首屏渲染性能"。它提升的是首屏可见时间（FCP/LCP），服务器需要额外花时间渲染 JSON 数据，TTFB 可能变差。
- 陷阱：SSR 与 SSG/CSR 混为一谈。面试常要求对比三者，必须说清"渲染发生在哪、何时生成、适合什么内容"。

### Q6 渐进式图片和模糊占位（LQIP）怎么做？

**考察点**：考渐进式加载的完整链路：占位 → 懒加载 → 响应式选图 → 防抖动，重点是每一环都有取舍。

**参考答案**：

> **一句话结论**：先用几 KB 的占位图（LQIP，Low Quality Image Placeholder，低质量图像占位）或主色块顶住位置，真图加载完成再淡入替换，配合 `srcset` 与懒加载，让图片既不白也不跳。

1. 占位方案：主色块（最省，体感一般）、LQIP 模糊小图（约 20px 再模糊放大，观感自然）、BlurHash/ThumbHash（把占位编码成字符串内嵌在接口里，无需额外请求）。ThumbHash 体积约 30 字节，明显优于 Base64 内嵌 JPEG 的 LQIP。
2. 防抖动：容器提前写死 `aspect-ratio` 或宽高，占位图与真图共用同一容器，否则图片到达会把下面内容顶下去，直接拉高 CLS。
3. 懒加载：用 `IntersectionObserver` 在进入视口前约 200-400px 触发加载；原生 `loading="lazy"` 更省代码，但它不能自定义预加载边距，且首屏图不要加。
4. 响应式：`srcset` + `sizes` 让浏览器按视口宽度和 DPR（Device Pixel Ratio，设备像素比）选最合适的资源，配 `loading="lazy"`、`decoding="async"`，并在 `fetchpriority="high"` 上给首屏主图。
5. 兜底：`onerror` 换成占位图并上报，避免出现破图；必须有尺寸与 `alt`，否则既抖动又不可访问。

```html
<img src="thumb-20.jpg" data-src="hero-1200.webp"
     srcset="hero-800.webp 800w, hero-1200.webp 1200w"
     sizes="(max-width: 768px) 100vw, 800px"
     width="1200" height="675" alt="产品主图"
     loading="lazy" decoding="async" class="lqip">
```

**追问与易错点**：

- 追问：LQIP 和 Base64 内联占位有什么区别？答：Base64 内联省一次请求但会让 HTML 变大且无法缓存，BlurHash 体积更小但要 JS 解码，首屏关键图用内联更稳。
- 追问：用 CSS 背景图做占位行不行？答：可以，但背景图无法参与 `srcset` 响应式选图，也拿不到 `alt`，只适合纯装饰图。
- 陷阱：给首屏最大的一张图加 `loading="lazy"`，直接把 LCP 拖慢，这是最常见的自伤优化。

### Q7 字体加载引起的 FOIT 和 FOUT 怎么处理？

**考察点**：考 `font-display` 各取值的语义差异与"字体引起的布局抖动"这一层，能说出子集化和度量匹配就是加分。

**参考答案**：

> **一句话结论**：FOIT（Flash of Invisible Text，文字不可见闪烁）是字体没到之前什么都不显示，FOUT（Flash of Unstyled Text，无样式文字闪烁）是先显示系统字体、字体到达后替换；用 `font-display: swap` 优先保证可读，再用 `size-adjust` 和子集化把替换时的抖动压到最小。

1. `font-display` 取值：`auto`（浏览器默认，多数实现接近 block）、`block`（约 3s 内不可见，之后回退，FOIT 最严重）、`swap`（立即用回退字体，字体到达后替换 → FOUT）、`fallback`（约 100ms 不可见期后先用回退字体，字体在约 3s 内到达仍会替换，超过就不再替换）、`optional`（网络好才用，否则本次不加载）。
2. 选型判断：正文优先 `swap` 或 `optional`（可读性优先）；图标字体不要用 `swap`，回退时字码点错位会显示成方框，应改用内联 SVG 图标。
3. 减少抖动：用 `@font-face` 的 `size-adjust`、`ascent-override`、`descent-override` 调整回退字体的字面度量，让替换前后的行高与换行位置接近，这是目前最有效的手段。
4. 加快到达：对首屏字体加 `preload`（要用 `crossorigin`，否则会重复下载）；用 `unicode-range` 做子集化，只下发用到的字符集（中文动辄几 MB，子集化收益最大）。
5. 数量控制：中文字体建议只保留 1-2 个字体、每个不超过 100KB 级别（子集后），`font-weight` 不要全靠合成加载多套字重。

**追问与易错点**：

- 追问：为什么 `preload` 字体要加 `crossorigin`？答：字体请求按 CORS 规则发起，属性不一致会被当成两次不同请求，导致下载两份。
- 陷阱：把 FOIT 当成正常现象。用户看到的是"页面先白一下"，在弱网下可能长达数秒，是实打实的体验问题。
- 陷阱：用 `swap` 又不做子集化。中文全量字体在慢网下替换来得极晚，页面文字会"跳两次"。

### Q8 表单校验应该在什么时机做？错误提示放在哪里？

**考察点**：考校验时机的节奏设计与错误提示的可访问性关联，这是最容易被答成"失焦校验"的浅层题。

**参考答案**：

> **一句话结论**：原则是"别在用户还没写完时就报错，也别等到提交才报错"——首次失焦（blur）校验、已出错字段改为输入实时校验、提交时全量校验并定位到第一个错误。

1. 三种时机：失焦校验（新手友好，避免打字过程中被打断）、输入实时校验（只用于格式约束强的字段，如手机号、验证码）、提交全量校验（兜底，不可省）。
2. 渐进策略：字段首次校验后标记 `touched`，之后该字段的每次输入都实时校验并即时消除错误提示，让用户马上看到"改对了"。
3. 提交行为：全量校验后聚焦第一个错误字段并滚动到可见区域，同时给错误摘要或全局提示，不要让用户自己四处找。
4. 提示位置：错误文案紧贴对应字段下方，通过 `aria-describedby` 与输入框关联，配 `aria-invalid="true"`；不要只用 Toast 报错，Toast 会消失且读屏软件关联不上字段。
5. 可访问性：错误不要只用红色区分（色盲用户看不出来），要配图标或文字；错误出现时用 `aria-live="polite"` 让屏幕阅读器播报。
6. 提交失败：服务端返回字段级错误时映射回对应字段而不是弹一个"操作失败"，同时保留用户已填内容（这是最容易被忽略也最伤人的点）。

```html
<input id="phone" aria-invalid="true" aria-describedby="phone-err" />
<p id="phone-err" role="alert">手机号应为 11 位数字，请检查后 4 位</p>
```

**追问与易错点**：

- 追问：输入实时报错会不会让用户暴躁？答：会，所以首次不报错、只在失焦后开启动态校验，这就是"延迟首次校验"的节奏设计。
- 陷阱：提交按钮一直灰着，让用户不知道哪里不合格；正确做法是按钮可点，点击后定位并说明问题。
- 陷阱：错误文案只说"格式错误"。要说清"错在哪、怎么改"，例如"手机号应为 11 位数字"。

### Q9 长表单和分步表单怎么设计？填到一半刷新了怎么办？

**考察点**：考长表单的结构化拆分、草稿保存与防误触，重点是"用户已经填的内容永远不能丢"。

**参考答案**：

> **一句话结论**：长表单用分步（每步一个主题）降低认知负担，用自动保存草稿兜住中断，用明确的进度与返回能力消除"填了看不到头"的焦虑。

1. 分步策略：3-6 步为宜，每步只问同一主题；步骤过多用户会放弃，因此把可选项后置或折叠，别平均分割。
2. 进度可见：显示"第 2 步 / 共 4 步"、步骤标题和完成标记，允许点回上一步修改；只校验当前步骤就放行，避免最后一步一次性爆出全部错误。
3. 草稿保存：表单变更后防抖 300-500ms 存入 `localStorage`（含表单版本号与时间戳）；内容大或含文件时改用 `IndexedDB`（`localStorage` 只有约 5MB 且同步阻塞主线程）。
4. 恢复策略：进入页面发现草稿要显式提示"检测到未提交的草稿，是否恢复"，不要静默覆盖或静默丢弃；提交成功后清空草稿。
5. 防误触：离开有改动的页面时用 `beforeunload` 提示（注意：只有用户有过交互才会触发）；单页内的大表单配"暂存"按钮，让主动保存成为可能。
6. 边界：手机号、身份证号、支付信息等敏感字段不写入草稿；`localStorage` 在隐私模式下可能不可用，写入要 `try/catch` 并降级为内存保存。

**追问与易错点**：

- 追问：为什么草稿要带版本号？答：表单结构改版后旧草稿字段对不上，会把 A 字段的值填到 B 字段，必须按版本判断是否可用。
- 追问：跨设备续填怎么办？答：本地存储做不到，需要服务端草稿接口按用户 ID 保存，前端在进入时拉取并合并。
- 陷阱：提交失败后清空表单。这是最严重的体验事故，用户重填的成本极高，必须保留输入并聚焦到出错字段。

### Q10 SPA 路由切换后滚动位置丢失，怎么恢复？

**考察点**：考"保存/恢复的时机"，面试官真正想听的是"数据没渲染完就恢复必然失败"。

**参考答案**：

> **一句话结论**：进入路由前把容器的 `scrollTop` 按 key 存下来，返回该路由且数据渲染完成、DOM 高度稳定后再恢复，否则恢复必然失效。

1. 保存：路由离开前（`beforeRouteLeave`、`onBeforeUnmount`）记录滚动容器与 `scrollTop`，key 用路由路径加查询参数，列表页要额外记录已加载页数与筛选条件。
2. 恢复时机：在数据请求完成且 DOM 高度稳定后恢复，Vue 用 `nextTick` 加一帧，必要时用 `ResizeObserver` 确认高度已到位；数据没回来就恢复，列表高度不够，`scrollTop` 会被夹到最大值。
3. 关键前置条件：列表项必须有稳定高度或占位高度，图片要预留尺寸，否则恢复的位置会随时间漂移；用虚拟列表时恢复的是"数据索引"而不是像素，靠 `scrollToIndex` 定位。
4. 框架支持：Vue Router 的 `scrollBehavior(to, from, savedPosition)` 与 React Router 的 `ScrollRestoration` 已封装基础行为，但要处理"异步数据晚到"的场景。
5. 冲突处理：浏览器的 `history.scrollRestoration = 'manual'` 与 SPA 自定义恢复可能打架，接管时要显式设置为 `manual`。

```js
// Vue Router 4
scrollBehavior(to, from, savedPosition) {
  if (savedPosition) return savedPosition;        // 前进/后退恢复
  if (to.hash) return { el: to.hash, behavior: 'smooth' };
  return { top: 0 };
}
```

**追问与易错点**：

- 追问：为什么"返回"能恢复，"点链接前进"是回到顶部？答：只有 history 的后退可依赖 `savedPosition`，新进入的页面语义上应从顶部开始，需要额外缓存的情况自己维护 key。
- 陷阱：在 `onMounted` 里立即恢复。此时列表还是空的，`scrollTop` 直接归零，这是最典型的实现错误。
- 陷阱：恢复时用 `setTimeout(..., 0)` 赌数据已到。弱网下必然失败，必须挂载到数据就绪的回调上。

### Q11 下拉刷新和上拉加载怎么实现？有哪些坑？

**考察点**：考滚动事件、触摸手势与分页状态的组合正确性，重点是"防抖、防重入、防无限触发"。

**参考答案**：

> **一句话结论**：下拉刷新判断"已到顶部 + 下拉位移超过阈值 + 未在刷新中"，上拉加载用 `IntersectionObserver` 监听底部哨兵元素，两者都必须有"加载中"锁和"没有更多"终止条件。

1. 下拉刷新判定：`scrollTop === 0` 且触摸下拉位移超过阈值（约 60px）才触发；过程中用 `transform: translateY()` 跟手给反馈，松手后回弹并进入刷新态。
2. 事件细节：`touchmove` 若阻止默认滚动必须是 `passive: false` 且只在水平滑动时 `preventDefault()`，否则整页滚动被锁死；更稳妥的做法是让 CSS 的 `overscroll-behavior` 与原生滚动承担回弹。
3. 上拉加载：用 `IntersectionObserver` 监听列表底部的哨兵元素，靠 `rootMargin: '0px 0px 200px 0px'` 提前一屏加载，避免用 `scroll` 事件加计算。
4. 状态机：至少四个状态——idle / loading / finished / error，`loading` 期间必须拒绝重复触发；`finished` 后再也不请求；`error` 要给出"点击重试"而不是无限自动重试。
5. 数据正确性：翻页时带 `page` 或游标（cursor）并配请求序号或 `AbortController`，丢弃过期响应，防止快速滑动造成的数据错乱或重复项，列表渲染要用稳定 ID 做 key。
6. 经典坑：加载完成后列表总高度小于容器高度，哨兵元素一直可见，于是无限请求同一页；解决方式是先禁止触发，数据不足一屏时直接一次性加载完或提示"没有更多"。

**追问与易错点**：

- 追问：为什么用 `IntersectionObserver` 而不是监听 `scroll`？答：`scroll` 事件高频触发且要读写布局，容易掉帧；`IntersectionObserver` 由浏览器异步回调，不阻塞滚动。
- 陷阱：监听 `scroll` 时用 `scrollTop + clientHeight >= scrollHeight - 10` 判断到底。图片或字体异步加载时会改变 `scrollHeight`，造成误判重复请求。
- 陷阱：桌面端没实现下拉刷新就直接用移动端手势组件，PC 上重载页面靠原生刷新，反而弹出一个无效交互。桌面端应改为显式"刷新"按钮。

### Q12 返回顶部按钮和锚点跳转要注意什么？

**考察点**：考细节正确性：固定头部遮挡、平滑滚动的降级、性能与事件解绑，属于"小功能见基本功"的题。

**参考答案**：

> **一句话结论**：锚点跳转必须给目标元素加 `scroll-margin-top`，否则会被固定头部挡住；返回顶部按钮的显隐判断要节流/被动监听，并在组件卸载时解绑。

1. 锚点遮挡：固定导航栏高度约 60px 时给所有锚点目标加 `scroll-margin-top: 72px`，这是 CSS 原生方案，比 JS 里手动算偏移量（`element.offsetTop - 60`）稳健得多（后者依赖布局与嵌套定位）。
2. 平滑滚动：`scrollTo({ top: 0, behavior: 'smooth' })` 或 `scroll-behavior: smooth`；尊重 `prefers-reduced-motion`，用户要求减弱动效时直接瞬时跳转。
3. 监听优化：判断按钮显隐的滚动监听要加 `{ passive: true }`，并节流到约 100-200ms；不要每帧读 `scrollTop` 触发同步布局。
4. 语义与可达性：返回顶部用 `button` 而不是 `div`，给 `aria-label="返回顶部"`，固定定位要避开移动端安全区（`env(safe-area-inset-bottom)`）。
5. 事件清理：Vue 在 `onUnmounted`、React 在 `useEffect` 的清理函数里 `removeEventListener`，否则路由切换反复注册会累积内存泄漏与重复执行。

```css
[id] { scroll-margin-top: 72px; }          /* 固定头部下的锚点兜底 */
@media (prefers-reduced-motion: reduce) {
  html { scroll-behavior: auto; }
}
```

**追问与易错点**：

- 追问：`scroll-behavior: smooth` 和 JS 的 `behavior: 'smooth'` 冲突吗？答：不冲突，但 JS 传参优先级更高；同时存在时以 JS 调用为准，且在减弱动效偏好下要主动关闭。
- 陷阱：用 `location.hash = '#id'` 跳转后，页面在 Safari 与 Chrome 的滚动行为不一致，且重复设置同一个 hash 不会再触发滚动。
- 陷阱：按钮固定定位在移动端被底部工具栏或安全区盖住，被追问"iPhone 上能用吗"时露怯。

### Q13 弹窗（Modal）要处理哪些细节？焦点和滚动锁怎么做？

**考察点**：考无障碍与交互细节的完整清单，焦点管理与滚动锁是两个必答项，很多人只会说"点遮罩关闭"。

**参考答案**：

> **一句话结论**：弹窗要管住四件事——焦点进得去出得来、Esc 能关闭、背景不跟着滚、层级不打架，再叠加 `role="dialog"` 等无障碍语义。

1. 焦点管理：打开时记录触发元素并把焦点移入弹窗首个可聚焦元素；Tab 键在弹窗内部循环（焦点陷阱），关闭后焦点必须回到原触发元素，否则键盘用户会"丢失位置"。
2. Esc 关闭：监听 `keydown` 判断 `e.key === 'Escape'`；有表单未保存内容或二次确认时不要直接关，要弹二次确认。
3. 滚动锁：给 `body` 加 `overflow: hidden` 并补偿滚动条宽度（`padding-right: calc(100vw - 100%)` 或用 `scrollbar-gutter: stable`），否则内容会横向抖动；移动端要防"穿透滚动"，用 `overscroll-behavior: contain` 阻止滚动链；注意 iOS Safari 上单给 `body` 加 `overflow: hidden` 常常锁不住背景滚动，需要在打开时把 `body` 设为 `position: fixed` 并记录 `top` 偏移（或用原生 `<dialog>`），关闭时还原。
4. 层级管理：`z-index` 集中定义层级变量（如 toast 3000 > modal 2000 > dropdown 1000），避免各组件随手写 `9999`；嵌套弹窗用栈结构管理，只让最上层响应 Esc。
5. 无障碍属性：`role="dialog"`、`aria-modal="true"`、`aria-labelledby` 指向标题；关闭按钮要有 `aria-label`，不要只放一个图标。
6. 交互细节：遮罩点击关闭只适用于非关键弹窗，涉及输入或支付确认的弹窗必须点关闭按钮才关，防止误触丢数据。

**追问与易错点**：

- 追问：焦点陷阱怎么实现？答：监听弹窗内 Tab，在首个和末个可聚焦元素之间循环；也可以用原生 `<dialog>` 元素加 `showModal()`，浏览器已内建焦点与背景惰性（inert）。
- 陷阱：只写 `overflow: hidden` 不加滚动条补偿。弹窗一打开，底层页面横向跳一下，是肉眼可见的低级问题。
- 陷阱：用 `document.body.style.overflow` 但不还原，关闭弹窗后整个页面再也滚不动。

### Q14 键盘可达性和快捷键要注意什么？

**考察点**：考"键盘用户能不能完整使用应用"，重点是语义标签、焦点可见与快捷键冲突这三件事。

**参考答案**：

> **一句话结论**：所有可点击元素都要能用 Tab 聚焦、用 Enter/Space 激活，焦点顺序与视觉顺序一致，焦点样式清晰可见，快捷键不能与浏览器和输入法冲突。

1. 用原生元素：能点就用 `<button>` / `<a>`，天然带键盘语义和焦点能力；用 `div` 加 `onclick` 必须补 `tabindex="0"`、`role="button"` 并手动处理 Enter 与 Space，而这几乎总会被做漏。
2. 焦点可见：绝不写 `outline: none` 而不给替代样式；用 `:focus-visible` 只在键盘聚焦时显示轮廓，兼顾鼠标体验与键盘可达性。
3. 焦点顺序：`tabindex` 只用 0 与 -1，正值会强行打乱 DOM 顺序；弹窗、抽屉这类浮层打开后要限制焦点范围。
4. 快捷键设计：避开浏览器已占用的组合（`Ctrl+W`、`Ctrl+T`），也要避开中文输入法激活状态；输入框聚焦时禁用全局单键快捷键，否则打字会误触发。
5. 可发现性：提供 `?` 打开快捷键说明面板，或在菜单项旁边标注快捷键，用户不会用等于没做。
6. 跳过导航：长页面（尤其是后台系统）在页面顶部提供"跳到主内容"链接，键盘用户可跳过整个导航区。

```css
:focus-visible { outline: 2px solid #2563eb; outline-offset: 2px; }
```

**追问与易错点**：

- 追问：为什么不推荐 HTML 的 `accesskey`？答：它与浏览器、系统和读屏软件的快捷键大量冲突，各语言键盘映射也不一致，现代项目基本不用。
- 陷阱：把 `outline: none` 当成"美化"。这是无障碍审核里最高频的失败项，也直接导致键盘用户无法操作。
- 陷阱：快捷键绑定在 `document` 上却不判断事件源，用户在输入框里打字就触发了功能键。

### Q15 无障碍（Accessibility）在前端要做到什么程度？`axe` 扫描能扫出什么？

**考察点**：考无障碍落地的优先级与工具边界，回答必须落到"语义、对比度、键盘、读屏、自动化 + 人工"这条链。

**参考答案**：

> **一句话结论**：无障碍按优先级做四件事——语义化标签、对比度达标、键盘可达、读屏可读（`alt` 与 `aria-live`）；`axe-core` 这类扫描工具只能自动发现约三分之一的问题，其余必须人工测键盘与读屏。

1. 语义化：用 `<nav>`、`<main>`、`<button>`、`<label>` 表达结构；表单控件必须与 `label` 关联（`for`/`id` 或包裹），图标按钮必须有可读名称。
2. 对比度：正文文字对比度至少 4.5:1，大号文字（约 18.66px 粗体或 24px 常规）至少 3:1；非文本的边框、图标、图表色至少 3:1。
3. 屏幕阅读器：图片给有意义的 `alt`，纯装饰图用 `alt=""`；动态内容（提交结果、加载完成、错误提示）用 `aria-live` 区播报，`polite` 用于普通提示、`assertive` 只用于严重错误；避免整页 `aria-live` 造成播报风暴。
4. 自动化扫描：`axe-core` 能查出缺 `alt`、对比度不足、`label` 缺失、`aria` 属性用法错误、重复 ID 等，成本低，适合接入 CI 每次构建跑；但它判断不了焦点顺序是否合理、"关闭"这类 `aria-label` 是否真的表意清晰。
5. 人工测试：只用键盘走完主要流程（注册、下单、提交表单），再用 NVDA 或 VoiceOver 实际听一遍，这是判断"能不能用"的唯一标准。
6. 落地策略：从组件库层面把无障碍属性做进基础按钮、弹窗、表单控件里，比每个页面各自补要可靠得多。

**追问与易错点**：

- 追问：`aria-live` 什么时候用 `assertive`？答：只在必须立刻打断用户时（如会话即将过期、提交失败且数据可能丢失）；普通提示用 `polite`，滥用会打断读屏的正常朗读。
- 陷阱：加一堆 `aria-*` 却不用语义标签。`role="button"` 的 `div` 仍不响应键盘，会自动扫描通过但实际不可用。
- 陷阱：认为"我们用户里没有盲人"就不做无障碍。键盘可达、对比度、语义化同时也是给弱视用户、临时受伤用户、自动化测试和 SEO 的收益。

### Q16 国际化（i18n）和本地化（l10n）在前端要注意什么？

**考察点**：考"翻译不等于本地化"这一层，重点看能否说出参数化文案、`Intl` 格式化与 RTL 三个可执行点。

**参考答案**：

> **一句话结论**：文案不要用字符串拼接，要用带具名参数的占位符加复数规则；日期、数字、货币、相对时间一律交给 `Intl`；RTL（Right-to-Left，从右到左）要用 CSS 逻辑属性而不是镜像一套样式。

1. 文案组织：键值化并参数化，用"共 {count} 条"而不是 `'共 ' + n + ' 条'`；语序随语言变化，拼接必然出错。
2. 复数与性别：用 `Intl.PluralRules` 判断复数形式（英文 one/other，阿拉伯语有六种），或用 ICU MessageFormat 在文案里表达。
3. 格式化 API：日期用 `Intl.DateTimeFormat`、数字与货币用 `Intl.NumberFormat`、相对时间用 `Intl.RelativeTimeFormat`，都比手写 `toFixed` 加字符串拼更正确；时区要明确存储基准（通常存 UTC）与展示时区，跨时区业务必须显式标注时区。
4. RTL：`dir="rtl"` 加 CSS 逻辑属性（用 `margin-inline-start` 代替 `margin-left`、`padding-inline`、`inset-inline-start`），布局自动翻转；但图标方向、进度条方向、动画方向、代码与数字不反向，这些要单独处理。
5. 布局弹性：同一文案在不同语言长度差异可达 30%-100%（德语、俄语偏长），按钮和卡片不能写死宽度，要允许换行、截断加 `title`，或用 `:lang()` 微调字号。
6. 工程化：文案抽离为语言包按需加载，避免首屏加载全部语言；缺失键要有兜底（回落默认语言并上报，而不是显示原始 key）。

```js
const fmt = new Intl.DateTimeFormat(locale, { dateStyle: 'medium', timeZone: userTz });
fmt.format(new Date(order.createdAtUtc));   // 存 UTC，按用户时区展示
```

**追问与易错点**：

- 追问：为什么不能用 `toLocaleDateString()`？答：它确实走 `Intl`，但每次调用都新建实例、无法复用配置，且默认时区是运行环境时区，在 SSR 上会用服务器时区渲染导致 hydration 不匹配。
- 陷阱：以为 `t('key')` 就完成了国际化。文案长度变化、复数、日期格式、RTL 这四样不做，多语言上线必然崩版式。
- 陷阱：在 SSR 里按服务器时区渲染时间，客户端按本地时区再渲染一次，直接触发 hydration 不一致告警。

### Q17 深色模式怎么适配？为什么不能只是反色？

**考察点**：考的是"语义化颜色变量 + 持久化 + 首屏防闪白"这套可执行方案，而不是换个背景色。

**参考答案**：

> **一句话结论**：用语义变量（`--bg-surface`）而不是颜色名变量（`--gray-100`）组织色板，配两套色值，通过 `prefers-color-scheme` 跟随系统、通过 `data-theme` 支持手动切换，并把用户选择在首屏脚本中提前应用以防闪白。

1. 变量分层：第一层是原始色板（`--blue-500`），第二层是语义变量（`--color-bg`、`--color-text`、`--color-border`、`--color-primary`），组件只引用语义变量。这样深色模式只需改第二层，不用改组件。
2. 触发方式：`@media (prefers-color-scheme: dark)` 响应系统偏好；手动切换则在 `<html>` 上写 `data-theme="dark"`，`html[data-theme='dark']` 覆盖语义变量，手动的优先级要高于媒体查询。
3. 防闪白（FOUC）：主题判断必须放在首屏内联脚本（在 CSS 之前同步执行），读 `localStorage` 后立即设置 `data-theme`；放到 Vue/React 的挂载钩子里会让用户先看到一帧白屏再看深色。
4. 视觉调整：深色不能简单反色。深色下要降饱和、降亮度（纯白文字在深灰上太刺眼，常用 `#E5E7EB` 这类灰白），边框比背景略亮而不是用纯黑阴影（深色里阴影几乎不可见，改用边框区分层级）。
5. 资源适配：插画、截图、白底图片在深色下刺眼，用 `filter: brightness(.85)` 做兜底或准备深色版本；`<meta name="color-scheme" content="light dark">` 让原生控件（滚动条、输入框、下拉）跟随主题。
6. 持久化与系统监听的取舍：用户手动选定后就不要被系统变化覆盖；未手动选定时监听 `matchMedia('(prefers-color-scheme: dark)')` 的 `change` 事件实时跟随。

```html
<script>
  // 必须在 CSS 之前同步执行，否则闪白
  var t = localStorage.getItem('theme') ||
    (matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light');
  document.documentElement.dataset.theme = t;
</script>
```

**追问与易错点**：

- 追问：为什么不能只靠 `prefers-color-scheme`？答：它只反映系统偏好，用户想单独给站点设深色时无法表达；而且 SSR 场景下服务端不知道用户偏好，必须靠客户端脚本补齐。
- 陷阱：在组件挂载后才设置主题类名，用户会看到明显的白闪（尤其在深色系统上），这是最常见的实现缺陷。
- 陷阱：深色下直接 `filter: invert(1)` 全页反色。图片和品牌色会全废，是明显的偷懒方案。

### Q18 弱网和离线体验怎么做？缓存、重连、队列重发各要注意什么？

**考察点**：考离线能力的工程实现与边界，重点是"离线不能假装在线"，以及队列重发的幂等与顺序问题。

**参考答案**：

> **一句话结论**：用 Service Worker 缓存应用外壳保证离线可开，用离线队列暂存写操作、联网后按序重发，用主动探测代替 `navigator.onLine` 判断真实连通性，并全程让用户知道"现在是离线的"。

1. 缓存策略：应用外壳（HTML、JS、CSS、图标）用预缓存（precache）并在激活时更新；接口数据用 stale-while-revalidate（先给缓存再后台刷新）；图片走 Cache Storage 并限制容量。Workbox 已封装这些策略，比自研可靠。
2. 更新策略：新版本用 `skipWaiting` + 提示"发现新版本，点击刷新"；直接强制刷新会打断正在填表或下单的用户，属于体验事故。
3. 离线感知：`navigator.onLine` 是"有没有网卡"的粗略信号，连上 Wi-Fi 但无外网时它仍返回 true；真正可靠的判断是主动探测（请求一个极小接口看耗时与结果）加上请求失败的分类统计。
4. 离线队列：写操作入队（`IndexedDB`），每条带唯一 ID、时间戳与幂等键；联网后按序重放，跳过已过期或与后序操作冲突的项（例如先加购物车后退款）。
5. 重连策略：指数退避加抖动（如 1s、2s、4s、8s 加随机数）避免惊群；连续失败要给手动重试入口，不能安静地一直重试。
6. 用户可见性：离线时用常驻顶部提示条而不是每个页面弹窗；恢复联网后提示"已恢复，正在同步 2 项操作"，同步完成再给结果反馈。

**追问与易错点**：

- 追问：Service Worker 有哪些坑？答：只在 HTTPS（或 localhost）生效；`fetch` 拦截处理不当会让接口缓存住旧数据；用户需要至少访问过一次页面它才能接管。
- 追问：为什么重发必须带幂等键？答："发出去了但响应没回来"与"没发出去"在客户端无法区分，没有幂等键就会重复下单、重复提交。
- 陷阱：离线时直接隐藏入口或显示空白页。用户会以为应用坏了，正确做法是明确告知离线状态并展示缓存内容。

### Q19 接口失败和断网，用户在感知上分得清吗？你的错误态怎么分级？

**考察点**：考"用户体感"视角的错误分层设计——超时、失败、离线的处理方式必须不同，且都要给出下一步动作。

**参考答案**：

> **一句话结论**：对用户来说"有网但接口 502"和"真的断网"体感一样，都是"点了没反应"，所以错误态要按"用户能否自己解决"分成可重试、需改动、需等待、需联系客服四种，每种配不同 UI 和文案。

1. 首层是超时感知：请求超过 5-8 秒给 loading 文案加长、给取消按钮，绝不无限转圈；超时后明确告知"请求超时"，并保留重试入口。
2. 第二层按错误类型分流：网络类（断网、超时）→ 轻提示加重试；业务类（参数错误、库存不足）→ 就地提示说清原因与改法；系统类（5xx、维护中）→ 页面级错误态加状态说明；
3. 拒用模态框报错：网络抖动是高频事件，用模态框会打断用户操作流。轻量错误用可自动消失的 Toast 加页面内错误占位，只有阻塞整个流程时才用全屏错误态。
4. 升级机制：同一请求连续失败 2-3 次后，从 Toast 升级为页面内错误占位（带重试按钮、错误码、客服入口），把"偶发失败"和"持续不可用"区分开。
5. 离线兜底：`navigator.onLine === false` 时直接给离线横幅加缓存内容，不发请求，避免无意义的等待和失败上报噪声。
6. 文案与排查：不要展示原始技术错误（`TypeError: Cannot read...`），映射成用户能懂的话；同时把请求 ID、状态码、时间戳记录下来并展示一小段，方便用户报障时对照。

**追问与易错点**：

- 追问：错误码要不要展示给用户？答：要展示一小段（如"错误码 500-3f2a"）但不是主角。它让客服与技术支持能直接定位，比让用户描述"就是不行"高效得多。
- 陷阱：所有错误都用一个"操作失败，请稍后重试"。用户不知道是自己的问题还是系统问题，会反复点击。
- 陷阱：断网时仍然发送请求并等 30 秒超时再报错，浪费用户时间，应先判断离线状态。

### Q20 动效时长和缓动曲线怎么定？`prefers-reduced-motion` 要处理什么？

**考察点**：考动效参数化的判断力与无障碍义务，面试官想听"哪些属性能动、哪些一动就掉帧"。

**参考答案**：

> **一句话结论**：反馈类动效 100-200ms、入场 200-300ms、退场比入场更快；缓动用 `ease-out`；只动 `transform` 与 `opacity` 以走合成层；在 `prefers-reduced-motion` 下把位移与时长降到接近零。

1. 时长依据：动效时长应与位移距离正相关（大范围移动可到 300-400ms），但界面反馈类不能超过 200ms，否则会感觉"迟钝"；超过 400ms 的动画在用户高频操作中会变成阻碍。
2. 缓动曲线：入场用 `ease-out`（先快后慢，符合"立刻响应"的心理预期），出场用 `ease-in`（快速离场），位置移动用 `ease-in-out`，避免 `linear`（机械）与过于夸张的回弹（`cubic-bezier` 跃出边界）。
3. 性能约束：只动画 `transform`、`opacity`、`filter`，它们能被合成器处理；动 `width`、`height`、`top`、`left`、`margin` 会触发布局重排，导致掉帧。必要时加 `will-change: transform`，但用完要移除，滥用会占用大量显存。
4. 无障碍：`@media (prefers-reduced-motion: reduce)` 下把时长压到 0.01ms 或只保留透明度过渡，因为前庭功能障碍用户会因位移动画产生眩晕甚至不适。
5. 一致性：把时长与曲线定义为 CSS 变量（`--dur-fast: 150ms`、`--ease-out`），全项目统一，避免同一产品里每个页面快慢不一。

```css
:root { --dur-fast: 150ms; --dur-base: 240ms; --ease-out: cubic-bezier(.2, .8, .2, 1); }
.card { transition: transform var(--dur-base) var(--ease-out), opacity var(--dur-base) linear; }
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation-duration: .01ms !important; transition-duration: .01ms !important; }
}
```

**追问与易错点**：

- 追问：为什么退场要比入场快？答：退场不承载新信息，用户此时注意力已经转移，快一点反而让操作显得干脆；反之入场太快会让用户来不及理解发生了什么变化。
- 陷阱：用 `setTimeout` 配合 CSS 动画，动画时长改了就不同步。应该监听 `transitionend` / `animationend`，或直接用 CSS 变量驱动。
- 陷阱：把长动画加在列表或表格的增删上。高频操作区域任何位移动画都会被抱怨"卡"。

### Q21 微交互是什么？怎么保证反馈的一致性？

**考察点**：考"反馈体系"而非单个动画，核心是状态枚举与组件化的治理能力，也是"回答逻辑发散"的人最容易答散的题。

**参考答案**：

> **一句话结论**：微交互是用户每个操作后那一小段即时反馈（按压、状态切换、成功提示），保证一致性的办法是把它固化成状态机加统一组件，而不是每个页面各写一套。

1. 状态枚举：任何异步操作都要有 `idle`、`loading`、`success`、`error` 四种明确状态，UI 上都要有对应表现，缺 `success` 或 `error` 是最常见的遗漏。
2. 组件化：把按钮的 loading、Toast 的调用、空状态、错误占位做成基础组件，业务层只传语义（成功/失败/进行中），样式由组件统一，避免每个页面重写一遍。
3. 反馈分级：轻量、可撤销的操作使用 Toast（自动消失，不打断）；需要用户决策的用模态框；破坏性操作（删除）用二次确认并说明后果（"将同时删除 12 条关联数据"）。
4. 位置一致：成功与失败提示在同一位置出现（例如统一右上角或统一底部），用户形成肌肉记忆后就不会到处找提示。
5. 时机一致：Toast 停留约 3-5 秒，含操作按钮（撤销/重试）时延长到 5-8 秒或改为不自动消失，保证用户来得及操作。
6. 撤销优于确认：删除、归档这类操作优先做"先执行 + 可撤销"（Toast 里放撤销按钮），比重型确认框打断更顺畅，但不可逆操作仍必须确认。

**追问与易错点**：

- 追问：Dropdown、Select 这类浮层点击外部关闭有什么坑？答：关闭监听的触发事件与打开事件如果是同一类型（都是 `click`），会在同一事件循环里"开了立即关"，要用 `mousedown` 判断外部点击或做一帧延迟。
- 追问：为什么删除提供撤销比弹确认框好？答：确认框打断所有用户（包括 99% 没点错的人），撤销只影响点错的人，整体成本更低，但涉及资金、数据不可恢复的场景必须用确认。
- 陷阱：把微交互理解成"炫酷动画"。微交互的目的是让用户确认"我的操作被接收了"，动画只是手段。

### Q22 Toast、Modal、通知三者的使用边界在哪？设计规范怎么定？

**考察点**：考"该用哪种反馈载体"的判断力，这是体验设计里最常被混用、面试官最爱问对比的一道题。

**参考答案**：

> **一句话结论**：Toast 用于不需要用户决策的轻量结果反馈，Modal 用于必须让用户立即决策且阻断操作的场景，通知（Notification/站内信）用于用户不在当前上下文时也要知道的事，三者按"是否阻断 + 是否需决策"区分。

1. Toast（轻提示）：自动消失、不阻断、不抢焦点，适合"已保存""已复制""网络异常，点击重试"；绝不能用它传递必须被读到的关键信息（比如密码修改成功凭证）。
2. Modal（模态框）：阻断背后操作、强制决策，适合二次确认、支付、表单编辑；滥用会导致"弹窗套弹窗"，层级和焦点管理迅速失控。能用抽屉或行内展开解决的不要用 Modal。
3. 通知：跨页面、离线也要送达，适合订单状态变更、被评论、审核结果；Web 端用 Notification API 需要用户授权，授权前必须解释用途，被拒绝后不要反复骚扰。
4. 无障碍要求：Toast 要挂在 `aria-live="polite"` 的容器里让读屏播报；Modal 要 `role="dialog"` 加 `aria-modal="true"`，打开时移入焦点、关闭后归还焦点（详见 Q13）。
5. 规范落地：定义层级顺序（toast 最高）、位置策略（Toast 统一右上或底部居中，移动端避免被键盘和手势区遮挡）、最长文案行数与超长截断规则、同一时刻最多显示条数与堆叠方式（超过就合并为"3 条新消息"）。
6. 反模式清单：用 Toast 报表单校验错误（用户看不到具体哪个字段）、用 Modal 报成功提示（打断且需要多点一次）、用原生 `alert`（阻塞主线程且样式不可控）。

**追问与易错点**：

- 追问：Toast 为什么不能承载表单校验错误？答：它 3 秒后消失且与字段位置脱钩，用户回到字段时已经不记得错在哪；错误必须就地贴在字段旁。
- 陷阱：Toast 显示时长固定 3 秒。文案长的、带"撤销"按钮的必须延长或改为不自动消失，否则用户根本来不及点。
- 陷阱：通知权限一进页面就弹。用户还不知道应用价值就被要求授权，绝大多数会拒绝，应该在有明确场景（如"开启后订单状态变更及时通知你"）时再申请。

### Q23 移动端手势怎么做？双击缩放和长按有哪些冲突？

**考察点**：考触摸事件与浏览器默认行为的博弈，重点是 `touch-action` / `passive` 与无障碍取舍，属于典型的深挖题。

**参考答案**：

> **一句话结论**：手势实现必须先和浏览器谈好"哪些方向归你"——垂直滚动交给浏览器，横向滑动才 `preventDefault()`，并且用 `touch-action` 在 CSS 层声明；禁止缩放虽然能消除 300ms 延迟，但会伤害无障碍，应改用 `touch-action: manipulation`。

1. 事件选择：优先用 Pointer Events（`pointerdown/move/up`）统一鼠标、触摸与触控笔；移动端老 Android 需回退到 Touch Events，`changedTouches` 取当前触点。
2. `touch-action`：在滑动手势容器上写 `touch-action: pan-y`（横向由脚本处理、纵向归浏览器），比在 `touchmove` 里 `preventDefault()` 更可靠，也不会打断原生滚动惯性。
3. `passive` 取舍：`touchstart`/`touchmove` 监听默认是 `passive: true`（Chrome 56+ 起对 `document`/`body` 的 `touchstart`/`touchmove` 默认被动），此时 `preventDefault()` 会被忽略并报警告，必须显式 `{ passive: false }` 才有拦截能力，但会阻塞滚动，只应加在真正需要的手势容器上。
4. 双击缩放冲突：300ms 点击延迟源于浏览器等待判断是否是双击；`user-scalable=no` 能消除它但会让弱视用户无法放大页面，正确做法是 `touch-action: manipulation` 或设置 `<meta name="viewport" content="width=device-width, initial-scale=1">`（现代浏览器在移动端已基本消除延迟）。
5. 长按冲突：长按会触发系统文本选择、图片保存菜单和 `contextmenu`；自定义长按要用 `touchstart` 记时间戳、`touchmove` 判断位移阈值（超过约 10px 视为滑动而非长按）、`touchend` 清理定时器，并在长按生效后 `preventDefault()` 阻止 `contextmenu`。
6. 手势的取舍与兜底：自定义手势（左滑删除等）没有视觉提示，用户发现不了，必须同时提供显式按钮入口；同时要遵守 `prefers-reduced-motion` 与系统字体缩放，手势不能成为唯一操作路径。

```js
el.addEventListener('touchstart', onStart, { passive: true });
el.addEventListener('touchmove', onMove, { passive: false }); // 只在需要拦截时
// CSS: .swipe-item { touch-action: pan-y; }
```

**追问与易错点**：

- 追问：`user-scalable=no` 到底能不能用？答：不建议。它违反 WCAG 1.4.4（内容可缩放），Lighthouse 无障碍审核会直接扣分；用 `touch-action: manipulation` 达到同样效果且不牺牲可缩放性。
- 陷阱：在 `window` 上给 `touchmove` 加 `preventDefault()`。结果整页滚不动，移动端页面直接废掉，这是最典型的手势事故。
- 陷阱：只做手势不做按钮。习惯键盘或读屏的用户完全无法使用左滑删除。

### Q24 感知性能还能怎么优化？假进度条合法吗？

**考察点**：考"先渲染后计算"的具体技术手段与假进度的使用边界，重点看能否给出可执行方案而不是空谈心理。

**参考答案**：

> **一句话结论**：感知性能的核心是"先给反馈、再干活"——优先渲染可见内容、把长任务切成分片让主线程喘气、提前预取下一步资源；假进度条只在无法获得真实进度时使用，且必须单调递增、永不倒退。

1. 先渲染后计算：首屏只渲染可见区域（虚拟列表、按需展开折叠面板），把重计算（大数组排序、复杂表单 schema 解析）延后到空闲时段或用 `requestIdleCallback`。
2. 任务分片：把超过 50ms 的长任务切成小块，用 `scheduler.postTask`（可设 `user-blocking`、`user-visible`、`background` 三级优先级）、`requestIdleCallback` 或 `requestAnimationFrame` 循环分片。分片的目的不是更快，而是让主线程有机会响应输入，直接改善 INP（Interaction to Next Paint）。
3. 预取与预热：页面空闲时 `prefetch` 下一屏的 JS chunk 和数据、`preconnect`/`dns-prefetch` 提前建连；用 `rel="prefetch"` 或路由级预取。
4. 假进度条：当后端只有"开始/结束"没有中间进度时可用，但要按预估耗时推进到约 90% 后放缓，完成时补到 100%，绝不能倒退或卡住不动——倒退比慢更伤信任。
5. 真进度优先：能拿到真实进度（上传字节数、批量任务已完成条数、WebSocket 推送）时一定要用真的，假进度只作为兜底。
6. 视觉权重分配：把用户最关心的信息第一时间渲染出来（订单状态、金额、剩余时间），次要信息（推荐、广告、统计）延后，让用户认为"页面已经好了"。

```js
// 分片处理大列表，避免一次同步渲染阻塞输入
async function renderInChunks(list, renderChunk) {
  for (let i = 0; i < list.length; i += 50) {
    renderChunk(list.slice(i, i + 50));
    await new Promise(r => setTimeout(r, 0));  // 让出主线程
  }
}
```

**追问与易错点**：

- 追问：分片会不会让总耗时更长？答：总 CPU 时间可能略增（多了调度开销），但最大单帧耗时显著下降，用户感知为"不卡"，这是明确划算的交换。
- 追问：为什么假进度到 90% 要放缓？答：到 100% 后还不动，用户会认为卡死；停在 90% 附近缓慢前进的状态最容易被接受。
- 陷阱：用 `setInterval` 无条件推进假进度，结果接口失败时进度条还在跑，用户看到 100% 却什么都没发生，信任直接崩塌。

### Q25 错误文案和引导怎么写？为什么"操作失败"是坏文案？

**考察点**：考"错误文案三要素"与引导设计，答案要能直接迁移到真实需求评审里。

**参考答案**：

> **一句话结论**：好的错误文案必须回答三件事——发生了什么、为什么、现在能做什么；只有一个"操作失败，请稍后重试"等于把责任推给用户。

1. 三要素结构：现象（"图片上传失败"）加原因（"文件大于 5MB"）加下一步（"请压缩后重试"或直接给"选择其他文件"按钮）。
2. 语言规则：说人话，不用技术术语（`500`、`null`、`undefined`、`Network Error`）；用肯定句和主动语态，不要"您的操作不被允许"，要"当前账号没有编辑权限，请联系管理员开通"。
3. 就近原则：字段级错误就在字段下方；区域级错误就在该区域内空态位置展示；只有全局性故障（整站不可用）才用全屏错误页。
4. 行动嵌入：每个错误都要给一个可执行动作——重试、返回上一页、联系客服、切换网络。错误提示里没有按钮，用户只能自己乱试。
5. 空状态与降级设计：空状态要区分"本来就没有数据"（配上引导动作，如"还没有项目，新建一个"）与"加载失败或没有权限"（必须区分，否则用户会以为自己被清空了数据）；降级时把非核心模块隐藏或换成静态占位，保住主流程可用。
6. 防重复与安抚：告诉用户数据是否安全（"你的修改已保存，仅提交失败"），明确数据不丢能大幅降低投诉率。

**追问与易错点**：

- 追问：技术错误要不要暴露？答：不暴露堆栈与内部术语，但要保留可检索的标识（错误码、请求 ID），并接入监控（见第 20 章），让排查有据可依。
- 陷阱：把"无数据"和"加载失败"渲染成同一个空状态。用户无法判断是自己没数据还是系统坏了，这是后台系统里最高频的体验缺陷。
- 陷阱：错误提示用模态框加"确定"。用户点完仍然不知道怎么办，只是被动接受了失败。

### Q26 新手引导怎么做才不惹人烦？A/B 测试怎么用来做体验决策？

**考察点**：考引导的触发策略与数据驱动决策的纪律，重点是"别一进门就全屏遮罩"和"实验要有假设与护栏指标"。

**参考答案**：

> **一句话结论**：引导按需触发、可跳过、别一上来就铺满屏；体验决策要"先有可证伪的假设和唯一主指标，再定样本量与实验周期，最后按事先写好的规则执行"，而不是看着曲线好看就上线。

1. 引导触发：首次进入且有真实数据时再引导（空数据时引导"创建第一个项目"更有意义）；高价值但难发现的功能（拖拽排序、批量操作、快捷键）用一次性气泡或行内提示，不做全屏遮罩式多步教程。
2. 引导承载：用真实界面上的高亮加一两句文案（比截图教程更耐用），做多步时给进度与"跳过"，并把"是否已看过"持久化，避免重复打扰。
3. 引导的无障碍与健壮性：引导本身也要能用键盘关闭；高亮依赖 DOM 结构，选择器要稳定（用 `data-guide="export"` 而不是 `nth-child`），否则改版后引导全崩。
4. 实验纪律：先写假设（"把提交按钮从底部移到表单顶部，能提升提交转化"）、定一个主指标（提交成功率）加若干护栏指标（表单报错率、客服工单量），避免同时改多处导致无法归因。
5. 分流与判定：同一用户稳定分组并持久化；样本量要事前估算，跑满一个完整周期（含周末与月末）再判定，禁止看到显著就提前停止（会导致假阳性），也不要在结果不显著时反复调参"调到显著"。
6. 决策与回滚：数据不达标就下线，不要因为"设计师觉得好看"而保留；实验结论要沉淀为可复用的设计规范，避免同一个问题反复实验。

**追问与易错点**：

- 追问：为什么不能只看点击率？答：点击率可能被诱导性文案刷高而实际转化下降，所以必须同时看主指标与护栏指标，防止"提升了 A 却毁掉了 B"。
- 追问：埋点章节已经讲过数据采集，这里讲什么？答：这题讲的是决策流程——假设、指标选择、样本量、判定规则、下线与沉淀，采集本身是它的输入。
- 陷阱：一进首页就弹三步引导遮罩。用户还没建立任务目标，看完就忘，还会挡住真实内容，中断率极高。

### Q27 怎么做体验度量？HEART 框架和 NPS 分别解决什么问题？

**考察点**：考能否区分"态度指标"与"行为指标"，并说出各自能回答和不能回答的问题，很多人会把 NPS 当成万能指标。

**参考答案**：

> **一句话结论**：HEART 框架把体验拆成愉悦度、参与度、接受度、留存、任务完成度五个维度，每个维度配目标、信号与线上指标，用来定位"哪一环差"；NPS 只是一个整体口碑的态度指标，能量化好感但定位不了问题。

1. HEART：Happiness（愉悦度，满意度/主观评分）、Engagement（参与度，使用频次与深度）、Adoption（接受度，新功能采用率）、Retention（留存率，回访）、Task Success（任务完成度，成功率、耗时、出错率）。其中任务完成度与前端技术最直接相关。
2. 指标分层：目标（如"表单要能顺畅填完"）→ 信号（用户反复修改、放弃离开、报错次数）→ 指标（表单完成率、平均完成耗时、单次提交失败率），这样指标才有解释力，不会变成一堆数字。
3. 行为优先于态度：优先采行为数据（埋点漏斗、RUM 的 P75/P95 与 INP、错误率、任务成功率），态度数据（问卷、NPS）作为补充。因为用户说的和做的经常不一致。
4. NPS：只问"你有多大可能推荐给朋友"（0-10 分），推荐者减贬损者得到净值。它适合横向对比与长期趋势，但样本偏差大、对具体问题没有定位能力，不能用来指导某个页面的改版。
5. 前端可落地的度量：接口耗时 P95、首屏与核心指标（LCP、INP、CLS）、关键路径埋点漏斗（进入表单 → 提交 → 成功）、错误率与告警，这些都能自己采集，不需要等用户调研。
6. 度量纪律：指标定义与统计口径必须先写进文档（"完成率"的分母到底是进入页面的人还是点了提交的人），否则团队各算各的，数据无法比较。

**追问与易错点**：

- 追问：怎么用数据说服上级做一个体验改造？答：先给出当前任务完成率、失败率、耗时分布，说明"损失了多少次提交"，再给改造预期与验证方式，用可比较的口径说话，而不是说"体验不好"。
- 追问：RUM 为什么看 P75/P95 而不是平均值？答：平均值会被少数极快或极慢的样本拉平，掩盖长尾用户的糟糕体验；分位数能直接暴露"有一部分用户很难受"。
- 陷阱：把 NPS 下降直接归因到某个页面改动。NPS 受品牌、价格、客服等非前端因素影响，缺因果链时不能归因。

### Q28 用户说"这个页面好卡"，你怎么把它定位到具体的技术问题？

**考察点**：考从模糊反馈到具体技术根因的完整排查链路，这是体验类题里最能体现工程能力的一题。

**参考答案**：

> **一句话结论**：先把"卡"翻译成可测量的三类问题——主线程被长任务占满、资源与请求慢、渲染过重，再用 Performance 面板录制、Network 瀑布图与 RUM 分位数逐个验证，最后用同一路径复测证明修好了。

1. 澄清与复现：问清"哪个页面、什么操作、什么机型、是否必现"，拿到最短复现路径后再动手；"一直卡"和"某操作后卡"是两类不同问题（前者多为资源与渲染量，后者多为主线程长任务）。
2. 长任务排查：Performance 面板录制操作过程，找超过 50ms 的长任务（尤其超过 200ms 的），看火焰图里是谁在占时间——同步大循环、深层 `watch`、大表格 `v-for` 全量重建、频繁触发重排。
3. 交互指标：看 INP（Interaction to Next Paint）与掉帧（Frames 视图出现红条），把"卡"量化为"某次点击到下一帧花了 800ms"，而不是感觉描述。
4. 网络排查：切到 Network 面板看瀑布图，找串行请求、大体积资源、未压缩的图片、未分包的 JS，关注 TTFB 与是否存在被阻塞的渲染请求。
5. 机型与数据分层：中低端安卓与旧 iPhone 是体验问题的高发区（通常是高端机 3-5 倍耗时），因此必须用 RUM 按机型、版本、页面看 P75/P95，而不是只在自己电脑上试。
6. 修复与验证：定位到根因后（常见为列表未虚拟化、`v-if` 切换重建大组件树、`watch` 里做重计算、图片未压缩、请求串行），改完要用同样的录制方式和同样的路径复测，给出长任务数量与 INP 的前后对比数据。

**追问与易错点**：

- 追问：用户反馈无法复现怎么办？答：看 RUM 数据里受损用户的机型与网络分布，同时在监控里加上长任务与 INP 采集（第 20 章），用数据代理复现，而不是靠猜。
- 追问：怎么区分是前端渲染慢还是接口慢？答：Performance 面板里看请求返回时间与主线程活动的时间段是否重叠——长时间没主线程活动说明在等接口，主线程饱和则说明是渲染与计算问题。
- 陷阱：直接回答说"优化一下代码、加点缓存"。没有测量步骤的方案无法证伪，也无法说服别人这是有效修复。

## 本章小结

- 体验优化的落点永远是具体手段：骨架屏、乐观更新、任务分片、防重复提交、焦点管理、`aria-live`，说清取舍比说清原则更重要。
- 等待体验等于"真实耗时减去预期管理"，先给反馈、再给进度、最后给可取消，比单纯压缩耗时更容易被用户感知到。
- 任何异步操作都要有 idle / loading / success / error 四态，缺 success 与 error 反馈是最常见也最廉价的失分点。
- 用户已填的数据永远不能丢：草稿自动保存、提交失败保留输入、`beforeunload` 提示，是长表单的三条底线。
- 无障碍不是附加题：语义化标签、对比度 4.5:1、键盘可达、`prefers-reduced-motion`，同时也是弱网、中低端机与自动化测试的收益。
- 弹窗、手势、滚动这三个高频交互区最容易出事，分别对应焦点陷阱与滚动锁、`passive` 与 `touch-action`、恢复时机与固定头部遮挡。
- 体验决策要讲纪律：先有假设与唯一主指标，再有样本量与完整周期，最后按事先定好的规则上线或下线。
- 用户说"卡"时要翻译成可测量的问题（长任务、请求耗时、渲染量），用 Performance 录制与 RUM 分位数定位，并用同一路径复测证明修好了。
