## 第 25 章 场景设计题与开放题

### Q1 让你设计一个弹窗组件，API 你会怎么定？

**考察点**：考组件 API 设计能力：受控与非受控怎么选、组合优于配置怎么落地、命令式调用与无障碍边界。能说出"状态归谁管"就算入门，能说出代价才算过关。

**参考答案**：

> **一句话结论**：弹窗 API 的核心是"状态归谁管"——`open` 做成受控与非受控都能用，内容用插槽（slot）组合而不是堆布尔 props，再补一个 `Modal.confirm()` 式命令式入口覆盖"随手弹一下"的场景。

1. 需求澄清：先问清谁控制开关、要不要嵌套弹窗、要不要拖拽与最大化、是否 SSR、无障碍要求（焦点陷阱、Esc 关闭、`aria-modal`）到什么程度。
2. 状态设计：`open` 受控 + `defaultOpen` 非受控，组件内部只在非受控时维护状态；关闭动作只对外抛事件（Vue 用 `v-model:open` 或 `update:open`，Vue2 用 `.sync`，React 用 `open`/`defaultOpen`/`onOpenChange`），绝不偷偷改 prop。
3. 结构设计：除 `title`、`footer` 外一律用插槽或 `children`，而不是 `showFooter`、`footerText`、`hasCloseIcon` 这类布尔配置——每来一个需求加一个 prop，API 一定会爆炸。内容、触发器都用组合方式表达。
4. 关键难点：渲染位置要挂到 body（Vue `Teleport`、React `createPortal`），否则会被父级 `overflow: hidden`、`transform` 裁掉或被 `z-index` 层级压住；打开时锁 body 滚动并补偿滚动条宽度，避免页面抖动。
5. 取舍与边界：命令式 `Modal.confirm()` 上手快，但脱离组件树，拿不到全局状态（Context/Provide）且 SSR 下要额外处理，所以只用于"确认框"这类简单场景，复杂内容一律走声明式。
6. 如何验证：单测覆盖受控/非受控切换、Esc 与遮罩点击、焦点还原（关闭后焦点回到触发按钮）；监控弹窗打开耗时与内部组件报错，避免弹窗成为错误高发区。

```js
// 非受控内部状态的写法（Vue3 思路）
const props = defineProps({ open: { type: Boolean, default: undefined }, defaultOpen: Boolean });
const emit = defineEmits(['update:open']);
const inner = ref(props.defaultOpen);
const isControlled = computed(() => props.open !== undefined);
const visible = computed(() => (isControlled.value ? props.open : inner.value));
function close() {
  if (!isControlled.value) inner.value = false;
  emit('update:open', false); // 受控方自己去改，子组件不改 prop
}
```

**追问与易错点**：

- 追问：受控和非受控能混用吗？答：同一次渲染里不能既传 `open` 又让内部改状态，会出现 UI 与数据不一致；判据就是"传了受控 prop 就只读"。
- 追问：为什么不用 `v-if` 直接包一层？答：会丢掉过渡动画与内部状态（比如已填写的表单），通常用 `v-show` + 过渡；接受重新挂载就必须在文档里写明。
- 陷阱：只说"用个 `visible` 变量控制显示"就结束了，完全没有受控/非受控、插槽、无障碍的意识，这是初级 API 设计的典型答案。
- 陷阱：忘记焦点管理，键盘用户 Tab 会跑到弹窗背后的页面上，面试官会顺势追问无障碍与"弹窗关不掉"的处理。

### Q2 表格组件的 API 怎么设计才经得起需求折腾？

**考察点**：考配置式与插槽式（render）的边界划分、受控状态设计、大数据量下的性能处理。答出"配置是骨架、插槽是逃生口"就基本合格。

**参考答案**：

> **一句话结论**：表格 API 用 `columns` + `dataSource` + `rowKey` 描述"是什么"，用 `render`/具名插槽解决"长什么样"，把排序、分页、选择做成可受控的独立状态，业务逻辑不写进组件。

1. 需求澄清：数据量级（要不要虚拟滚动）、是否固定表头/固定列、列宽能否拖拽、服务端分页还是前端分页、单元格是否要自定义渲染与合并。
2. 技术方案：核心 props 只有三个——`columns`、`dataSource`、`rowKey`；列配置形如 `{ key, title, width, align, fixed, sorter, render }`。`render`（Vue 用 `#bodyCell` 插槽）负责展示，列配置负责列行为，两者不要混。
3. 受控设计：排序、分页、选中行都给"非受控默认值 + 受控回传"两条路（`sortOrder`/`onSortChange`、`pagination`/`onPageChange`），服务端分页必须完全受控，否则数据与页码会打架。
4. 关键难点是性能：大表格靠虚拟滚动 + 固定表头（表头容器与内容容器分离并同步横向滚动）；`render` 里不做重计算，行组件要缓存（React `memo`、Vue 稳定 `key`）；`rowKey` 必须稳定，用索引当 key 会导致选中态错行。
5. 取舍与边界：配置式上手快但表达力有限，纯插槽式灵活但用起来啰嗦，主流是"配置为骨架 + 插槽为逃生口"；列宽拖拽、合并单元格、树形展开这些能力按需加，不要预置一堆没人用的开关。
6. 如何验证：单测覆盖排序、分页、多选三个高频交互与"数据变更后选中态"这类边界；监控首屏渲染耗时与滚动帧率，列数超过阈值时提示业务方收敛列。

**追问与易错点**：

- 追问：虚拟滚动和固定列能同时用吗？答：可以，但要保证表头、固定列、主体三块用同一套列宽计算结果，否则会横向错位；实现上常见"一个横向滚动容器 + 多块 `sticky` 区域"。
- 追问：选中行受控时怎么处理翻页？答：受控态由父级 `selectedRowKeys` 管理，跨页保留与否要显式配置，组件不该替业务决定。
- 陷阱：把业务字段判断（比如"状态是 1 显示绿色"）写进表格组件内部，组件立刻失去通用性，也会被追问"复用性怎么保证"。

### Q3 表单组件的 API 怎么设计？受控、校验、联动怎么放？

**考察点**：考表单的分层设计（Form 管校验与时机、FormItem 管字段注册与错误展示）、异步校验竞态、以及"复用组件做业务编排"的边界感。

**参考答案**：

> **一句话结论**：表单 API 分两层——`Form` 管校验与提交时机，`FormItem` 管字段注册与错误展示；值统一放在一个 `model` 对象里按路径读写，规则统一用一份 schema，不要让每个子组件自己维护状态。

1. 需求澄清：字段数量、是否动态增减、校验时机（失焦/变更/提交）、是否需要联动、是否有服务端校验回显、是否要支持嵌套对象与数组。
2. 技术方案：`Form` 通过 `provide/inject`（Vue）或 `Context`（React）下发注册表，`FormItem` 用 `name`/`path`（如 `user.tags[0].name`）注册自己，值统一从 `model` 读写；对外只暴露 `validate`、`resetFields`、`setFieldsValue`、`submit` 这几个命令式入口。
3. 关键难点是异步校验的竞态：连续输入触发两次请求，先发后回的旧结果会覆盖新结果，必须给每次校验打序号（token）或用 `AbortController` 取消旧请求，同时输入变化要防抖。
4. 校验时机要可配：默认"提交时全量校验 + 失焦校验该字段 + 变更后清除已有错误"，双侧校验（前后端同一套规则）时把服务端错误按字段路径回填才不丢信息。
5. 取舍与边界：组件只做"收集 + 校验 + 错误展示"，不做业务编排；复杂联动交给动态表单引擎（见 Q7），`Form` 提供命令式 API 作为逃生口即可。
6. 如何验证：单测覆盖必填、自定义规则、异步规则、动态增删字段后的校验顺序；埋点统计校验失败字段 TOP N，反推哪些表单项设计有问题。

**追问与易错点**：

- 追问：为什么错误展示放在 `FormItem` 而不是 `Form`？答：错误是字段级信息，放在字段旁才能与输入框绑定（`aria-describedby`）并支持局部重渲染，全放 `Form` 会导致整表刷新。
- 追问：动态增减字段为什么要重新注册？答：组件卸载后注册表要清理，否则会出现"已删除字段仍参与校验"的幽灵错误。
- 陷阱：把 `rules` 写成函数却依赖外部可变变量，React 里会踩闭包陷阱、Vue 里会丢响应式；正确做法是把依赖显式声明出来。

### Q4 上传组件的 API 怎么设计？

**考察点**：考"选、传、验、删"的状态拆分、受控文件列表、自定义传输的注入点，以及对浏览器文件安全限制的了解。

**参考答案**：

> **一句话结论**：上传组件的核心不是"选文件"，而是把"选、传、验、删"拆成独立状态：`fileList` 受控、传输过程用 `customRequest` 注入、拦截逻辑用 `beforeUpload`，组件只负责 UI 与状态机。

1. 需求澄清：单文件还是多文件、要不要裁剪与压缩、是否支持拖拽与粘贴、并发与限速、类型与大小限制、要不要进度与取消、失败重试策略。
2. 技术方案：`fileList` 受控（Vue `v-model:file-list`，React `fileList` + `onChange`）；自定义上传通过 `customRequest`/`http-request` 注入，组件不绑死任何请求库；`beforeUpload` 返回 `false` 拦截、返回 `Promise` 做异步校验（如读文件头判断真实类型）。
3. 关键难点是列表项状态机：每一项要有稳定 `uid` 与状态（`ready → uploading → done / error`），否则删除、重试、排序会错乱；本地 `File` 对象不可序列化，列表回显只能靠服务端返回的 id 与 url。
4. 传输细节：并发数要限流（比如 3 个），进度应该是"已传字节/总字节"而不是分片计数；取消要用 `AbortController` 真正中断请求，只清 UI 不中断会浪费流量。
5. 取舍与边界：不用受控列表最省事，但表单重置、多组件联动做不到；`customRequest` 把传输交给宿主，代价是错误处理与重试策略也要宿主兜。
6. 如何验证：覆盖类型/大小拦截、并发、中途取消、失败重试、表单重置；监控上传成功率、P95 耗时、分片重试次数。

**追问与易错点**：

- 追问：为什么不用 `input` 的 `value` 回显已选文件？答：出于安全，程序无法给 `file` 类型的 input 赋值（只能置空），浏览器也不允许脚本伪造用户选择。
- 追问：`accept` 属性够不够做类型校验？答：不够，`accept` 只是给系统的选择提示，用户可以改成"所有文件"，真实校验要用扩展名 + 文件头（magic number）。
- 陷阱：把 `fileList` 直接 `push` 修改父级传进来的数组，Vue/React 都可能不触发更新，正确做法是始终保持不可变更新。

### Q5 如果让你从 0 搭一个组件库，你怎么做？

**考察点**：考组件库的工程全景：目录与产物、按需引入、主题定制、文档、版本与发布。只答"写几个组件 + 打包"就偏了。

**参考答案**：

> **一句话结论**：组件库的成败不在组件写得多好，而在"三个产物 + 一条流水线"——ESM/CJS/类型声明与独立样式、按需引入、主题 token，加上语义化版本与自动化发布。

1. 需求澄清：自用还是开源（决定投入）、要不要支持多技术栈（Vue2/3、React）、设计稿是否统一、SSR 与主题定制要求、谁长期维护。
2. 目录与构建：用 `pnpm` workspace 的 monorepo 分包——`components`、`theme`、`utils`、`playground`、`docs`；构建产物 ESM + CJS + `.d.ts`，样式单独产出（`dist/style/index.css` 与每组件样式）以便按需引入。
3. 按需引入与主题：ESM + `sideEffects` 声明正确即可被 tree-shaking，Vite 下通常不需要 `babel-plugin-import`（Webpack + Babel 场景仍可保留）；主题用 CSS 变量 + design token 三层结构，改 token 就能换肤，避免 Sass 变量在编译期写死。
4. 关键难点是版本与破坏性变更：SemVer + changesets 自动生成版本与 changelog、提供 codemod 降低升级成本、文档与示例可运行（VitePress + 示例即测试）、包体积门禁（每次 PR 报告体积 diff），否则组件库会越用越不敢升级。
5. 取舍与边界：不要一上来做全量组件，先做业务真正复用的 5-8 个；Table、DatePicker、富文本这类重组件优先基于成熟库二次封装，把精力放在设计规范与主题上。
6. 如何验证：CI 跑单测 + 视觉回归（截图对比）+ 体积检查，发布后按组件与版本维度看错误率。

**追问与易错点**：

- 追问：按需引入到底靠什么生效？答：靠 ESM + 正确的 `sideEffects` 字段（样式文件不能被标记为无副作用），打包器才能安全的只保留用到的模块。
- 追问：为什么样式不建议用 Sass 变量做主题？答：Sass 变量在编译期就固化了，运行时切换主题必须重新编译；CSS 变量才能在运行期覆盖。
- 陷阱：为了"通用"给每个组件加一堆 props（`size`、`type`、`shape`、`bordered`……），结果是没人能记住 API，这也是"组件库设计"最常被追问的点。

### Q6 设计一个前端权限系统，从登录到按钮级控制怎么做？

**考察点**：考权限的分层（菜单/路由/按钮/接口）、动态路由实现细节与越权边界认知。能主动说"前端权限只是体验优化"是加分项。

**参考答案**：

> **一句话结论**：权限的本质是后端下发"能力清单 + 菜单/路由树"，前端只做映射与展示控制——路由权限管"能不能进"，按钮权限管"能不能点"，而真正的越权边界永远在后端。

1. 需求澄清：角色制（RBAC）还是细粒度权限码、菜单由后端下发还是前端写死、是否需要按钮级与字段级、是否多租户、无权限时如何提示。
2. 技术方案：登录后拿到 `permissions: string[]`（如 `user:add`）与菜单树；路由分静态（登录、404）与动态两类：静态路由先注册，动态路由在登录后按权限过滤再 `router.addRoute`。
3. 动态路由三个坑：刷新丢路由（必须在全局守卫里"先拉权限再注册，注册完再放行"）、通配 404 必须最后注册（否则动态路由永远匹配不到）、登出要能移除已加路由（记录并逐个 `removeRoute`）。
4. 按钮与菜单：按钮用 `v-permission="'user:add'"` 指令或 `hasPermission()` 函数控制显隐（不是禁用）；菜单由后端下发树，前端按 `path` 映射到本地组件，做不出匹配要降级到 404 并上报，避免"菜单点了白屏"。
5. 取舍与边界：前端隐藏按钮不等于安全，接口权限必须后端校验，前端要做的是"按 401/403 统一处理 + 友好提示"；隐藏太多功能会让用户以为系统缺功能，必要时用禁用 + 原因提示。
6. 如何验证：单测覆盖无权限跳转、重复注册、登出清理；监控 403/401 次数——如果前端可见按钮点进去大量 403，说明前后端权限码没对齐。

**追问与易错点**：

- 追问：为什么不把权限判断写进每个页面的 `created` 里？答：散落判断无法统一维护，新增角色要改 N 个页面；收口到路由守卫 + 指令 + 权限函数三处才是可维护的做法。
- 追问：同一个路由多个角色怎么处理？答：路由的 `meta.roles` 做并集判断（有的命中即放行），更细的字段级差异放在页面内部按权限码控制。
- 陷阱：说"前端拿到全部路由再按权限过滤显示菜单"就以为安全，只要用户改 localStorage 里的权限就能看到路由，这个回答会被当场追问穿。

### Q7 设计一个动态表单引擎，Schema 应该长什么样？

**考察点**：考 Schema 驱动架构的三层解耦（描述、渲染、运行时）、联动依赖处理、表达式安全边界。能讲清"联动为什么不能靠 N 个 watch"是分水岭。

**参考答案**：

> **一句话结论**：动态表单 = Schema（可序列化的描述）+ 渲染器（把 Schema 变成组件树）+ 运行时（值、校验、联动），三者解耦，Schema 必须是纯数据。

1. 需求澄清：Schema 由后端配置产出还是前端手写、字段类型有多少、联动复杂度（显隐/改值/异步取选项）、是否要自定义组件、是否需要多端渲染。
2. Schema 设计：用 JSON Schema 风格子集，形如 `{ type, key, label, props, rules, showWhen, options }`，其中 `type` 是字符串标识而不是组件实例，`key` 是路径（支持 `a.b[0].c`）；渲染器维护 `type → component` 注册表，业务通过 `registerComponent('richText', Comp)` 扩展，引擎不认识具体组件。
3. 运行时设计：所有值放一个 `formData`，按 key 路径读写；显隐、禁用、选项都从 `formData` 派生（`computed`/选择器订阅），字段级订阅避免"一个字段变全表重渲染"。
4. 关键难点是联动依赖图：A 变要影响 B 的显隐与选项，直接写 watch 会成环并形成 N² 关系；正确做法是把联动声明式化（依赖 + 表达式），构建依赖图后做拓扑排序，变更只重算受影响的字段，并检测循环依赖直接报错。
5. 取舍与边界：表达式求值不要用 `eval`/`new Function`（XSS 风险且会撞 CSP 的 `unsafe-eval`），用受限 DSL 解析器或沙箱；复杂业务逻辑保留"自定义组件 + 事件回调"这个逃生口，别把引擎做成编程语言。
6. 如何验证：Schema 需要版本与静态校验（key 冲突、类型不支持、循环依赖要在配置时而非运行时发现）；监控渲染耗时与校验失败率，字段过多时提示拆页。

**追问与易错点**：

- 追问：字段很多时怎么保证性能？答：字段级 `memo`/`shallowRef`，每个字段只订阅自己依赖的值，并把校验与联动计算放到微任务批量执行。
- 追问：Schema 存数据库要注意什么？答：只存纯 JSON，组件与回调不能进 Schema，否则无法序列化也无法跨端；自定义组件的映射关系放在前端注册表里。
- 陷阱：把"联动"实现成一堆 `watch` 互相调用，面试官会立刻追问"如果 A 和 B 互相影响会怎样"，此时必须答出依赖图与环检测。

### Q8 设计一个埋点 SDK，怎么做到不丢不重不卡？

**考察点**：考采集、队列、上报时机、采样去重、异常隔离与体积控制。考察的是 SDK 作者视角，而不是"调个 track 方法"。

**参考答案**：

> **一句话结论**：埋点 SDK 的关键是"不丢、不重、不卡、不炸"——本地队列 + 批量上报 + 采样去重 + 全链路异常隔离，任何情况下都不能影响业务主流程。

1. 需求澄清：埋点类型（PV/点击/曝光/自定义）、量级与 QPS 上限、字段规范归属、是否跨端复用、合规与隐私边界（用户标识、脱敏规则）。
2. 对外 API：只暴露 `init / track / pageView / setUserId / setCommonParams`，采集层统一补公共字段（时间戳、页面路径、版本、设备、userId、sessionId），业务只关心事件名与属性。
3. 队列与上报时机：内存队列 + 三重触发（定时如 5s、积压阈值如 20 条、页面隐藏 `visibilitychange`）；通道优先 `navigator.sendBeacon`，退化为 `fetch` 带 `keepalive`，再退化为 1×1 GIF；失败按指数退避重试，容量不够时写入 IndexedDB 兜底。
4. 去重与采样：每条事件自带唯一 `eventId`（重试可能重复发，服务端也要按它幂等）；高频低价值事件（曝光、滚动）按比例采样，错误类不采样，否则数据量和成本会失控。
5. 取舍与边界：体积控制在几 KB（不做全量无埋点采集）；SDK 内部所有逻辑（含序列化与上报）用 try/catch 包住，绝不向上抛；不做业务侧数据加工，不做跨域重逻辑。
6. 如何验证：SDK 自身要有上报成功率与丢队列的自诊断日志；发布时灰度对比新旧口径，先双写一段时间再切换，避免数据断层。

**追问与易错点**：

- 追问：`sendBeacon` 有什么限制？答：只支持 POST、不能自定义请求头（受 CORS 简单请求限制）、有约 64KB 的体积上限、拿不到响应结果，所以适合"发出去即忘"的场景。
- 追问：为什么用 `visibilitychange` 而不是 `beforeunload`？答：移动端 `beforeunload` 经常不触发，`visibilitychange` 进入 hidden 是更可靠的最后上报时机，`pagehide` 也可作为补充。
- 陷阱：把每个点击都立即发一条请求，既卡又容易丢；另一种极端是只在 `beforeunload` 发，页面崩溃就全丢——两个极端都会被追问。

### Q9 设计一个前端监控平台，前端侧要做什么？

**考察点**：考从采集到"能定位"的闭环设计，重点是数据可用性（source map、release、面包屑）而非罗列指标。

**参考答案**：

> **一句话结论**：前端侧只做四件事——采集、聚合、上报、可定位；能定位的关键是"统一 ID + release 版本 + source map + 用户操作面包屑"，缺一样，监控就只是日志堆积。

1. 需求澄清：要监控什么（错误/性能/接口/白屏/卡顿）、采样率与成本、是否私有化部署、告警给谁、定位粒度要求（能否还原到某行代码）。
2. 采集：错误类用 `onerror`、`unhandledrejection`、资源错误捕获、框架错误钩子（Vue `app.config.errorHandler`、React 错误边界）；性能类用 `PerformanceObserver` 采 LCP/INP/CLS 与长任务；接口类包装 `fetch`/XHR；行为类记录路由与最近点击作为面包屑。
3. 上报：队列 + 采样 + 批量发送，字段用短名压缩；错误全量、性能与行为采样；页面卸载用 `sendBeacon`（细节见第 20 章）。上报要做限流与去重，避免一个死循环错误把后端打挂。
4. 难点一：错误还原。source map 必须私有上传并绑定 release 版本，否则堆栈只能看到压缩后的列号；跨域脚本要在 `<script crossorigin="anonymous">` 且 CDN 返回 CORS 头时才拿得到详情，否则只有 `Script error.`。
5. 难点二：聚合与定位。同一问题按"错误信息 + 首帧堆栈 + release"聚合成 issue，附上用户操作面包屑（哪一步点了什么、哪个接口失败）才可复现；只按 message 聚合会把不同代码位置的问题混在一起。
6. 取舍与边界：采样率按类型分级（错误 100%、性能 10%、行为按需），不要为"全都要"把页面拖慢；手机号、密码、Token 这类敏感字段必须在上报前过滤和脱敏。验证方式是故障注入（脚本抛错、接口 500、资源 404）走通告警链路，并定期核对采集量与后端接收量。

**追问与易错点**：

- 追问：为什么不直接买 Sentry？答：能用就用，但面试考的是"你配了什么"——release、source map 上传、采样、脱敏、告警规则、issue 分派流程，说不出这些等于没接入。
- 追问：监控 SDK 自己出错怎么办？答：所有采集入口包 try/catch，上报失败只降级不抛出，SDK 加载失败不能阻塞业务（异步加载 + 超时兜底）。
- 陷阱：只答"接了监控平台，有看板"，说不出采集了哪些字段、怎么把一条错误定位到版本和用户操作，会被判定为没真正参与过。

### Q10 长列表几万条数据，虚拟滚动方案怎么设计？

**考察点**：考虚拟滚动的核心算法（定高与不定高）、滚动定位与跳动问题、与表格结合的复杂度。能区分两种场景是及格线。

**参考答案**：

> **一句话结论**：虚拟滚动的本质是"只渲染可视区 + 缓冲区（buffer）的节点"：定高用 `scrollTop / itemHeight` 直接算，不定高必须靠"估算高度 + 已渲染项实测缓存 + 偏移量校正"。

1. 需求澄清：数据量、是否定高、是否要滚动定位与跳转（如"回到第 5000 条"）、是否动态加载、是否与表格结合、兼容性要求。
2. 定高方案：外层容器 `overflow: auto`，内部放一个撑起总高的占位元素（`total * itemHeight`），内容区用 `transform: translateY(startIndex * itemHeight)` 定位；监听滚动并用 `requestAnimationFrame` 节流，只重算可视区间。
3. 不定高方案：维护 `estimatedHeight` 与实测高度缓存，滚动时先按估算定位，渲染后用 `ResizeObserver` 实测回写并修正总高与偏移；需要定位到某条时用前缀和 + 二分查找找起始索引。
4. 关键难点是"跳"与白屏：上下各留 2-3 项缓冲，快速滚动时用骨架占位；节点高度变化会触发浏览器的滚动锚定（scroll anchoring），导致视口跳变，需要手动记录并补偿 `scrollTop`。
5. 取舍与边界：与表格结合时，表头、固定列、主体必须共用同一套列宽与偏移计算，否则横向错位；万级以内且交互简单时，分页比虚拟滚动更省事，不要为了技术而技术。
6. 如何验证：单测给定 `scrollTop` 断言渲染区间与总高；用性能面板测滚动时的帧率与长任务；监控滚动卡顿率，卡顿高的页面通常伴随复杂单元格渲染。

```js
// 定高虚拟滚动的核心计算
const start = Math.max(0, Math.floor(scrollTop / itemHeight) - buffer);
const end = Math.min(total, Math.ceil((scrollTop + viewportH) / itemHeight) + buffer);
const offsetY = start * itemHeight; // 内容区整体位移
```

**追问与易错点**：

- 追问：为什么用 `transform` 而不是改 `top`？答：`transform` 走合成层，不触发重排；每帧改 `top` 会引发 layout，滚动重列表时差别很明显。
- 追问：不定高为什么不干脆渲染两次测量？答：两次渲染会有可见闪动且复杂度高，业界做法是"估算 + 滚动中修正"，先保证可用再追求精确。
- 陷阱：缓冲区设成 0，滚动稍快就白屏；或者每次滚动都 `setState` 全量重渲染，性能反而比不分页还差。

### Q11 大文件上传（比如 2G 视频）怎么做？

**考察点**：考分片、秒传、断点续传、并发控制、进度与失败重试的完整链路，以及 hash 计算的性能代价。属于高频场景设计题。

**参考答案**：

> **一句话结论**：大文件上传 = 分片 + 并发控制 + 断点续传 + 秒传校验；核心思路是"每次上传前先问服务端要什么、传完让服务端校验合并"。

1. 需求澄清：文件大小上限、多文件是否并发、网络环境（弱网/内网）、是否直传对象存储、是否支持暂停与刷新后续传、进度按字节还是分片。
2. 流程设计：① 用 `File.slice` 按 2-5MB 切片；② 计算文件 hash（大文件建议首尾 + 中间抽样 + 分片 hash 合并的方式提速，或用 `crypto.subtle.digest('SHA-256')` 在 Worker 里算——注意它是**一次性**接口，需把整块数据读进内存，只适合中小文件，几十 G 的必须走分片 hash 合并）；③ 用文件 hash 询问服务端是否已存在（秒传）与已上传分片列表（断点续传）；④ 用并发池上传（3-5 个并发）；⑤ 全部完成后请求合并，服务端按整体 hash 校验。
3. 关键难点：进度与取消要精确到分片状态，暂停时 `abort` 正在飞行的请求并保留已完成分片；刷新后续传靠"文件 hash + 后端分片记录"；失败分片单独指数退避重试，不要整体重传。
4. 性能与体验：hash 计算会吃满 CPU，几十 G 的文件必须在 Web Worker 里算，否则主线程卡死；上传中要支持取消与"离线上传队列"，弱网下要能自动降并发。
5. 取舍与边界：秒传依赖服务端有历史记录，命中率不高时不要把它当主卖点；直传对象存储要注意签名有效期、CORS 与分片上传接口（如 S3 Multipart）的差异；分片不能太小（请求数爆炸）也不能太大（重传代价高）。
6. 如何验证：模拟弱网、断网恢复、页面刷新、重复上传验证幂等；监控分片失败率、平均上传速率、秒传命中率。

**追问与易错点**：

- 追问：为什么分片都传完了还要整体校验？答：分片可能丢、可能顺序错乱或被篡改，整体 hash 校验既保证完整性，也是"重复上传同一文件"幂等判断的依据。
- 追问：同一文件重复上传怎么处理？答：服务端以文件 hash 为唯一键，已存在直接返回已有记录（秒传），并让前端跳过全部分片。
- 陷阱：在主线程用 `spark-md5` 一次性读完 2G 文件，页面直接卡死；被追问"hash 怎么算"时答不出 Worker 与抽样策略就是硬伤。

### Q12 设计一个 IM 前端，消息不丢不重不乱怎么保证？

**考察点**：考实时通信前端的可靠性工程：连接管理、消息状态机、有序性、多端同步与未读数一致性。

**参考答案**：

> **一句话结论**：IM 前端要解决"连得上、不丢、不重、有序、多端一致"，WebSocket 只是通道，真正的工程量在心跳重连、消息状态机与本地会话数据的一致性。

1. 需求澄清：消息类型（文本/图片/音视频）、是否要离线消息、多端同账号在线怎么处理、已读回执与撤回、历史漫游范围、是否需要端到端加密。
2. 连接层：`WebSocket` + 心跳（如 30s 一次 ping，连续两次无响应主动重连）+ 指数退避重连（上限如 30s）+ `online`/`visibilitychange` 事件触发立即重连；重连成功后按上次同步位点拉取增量消息。
3. 消息可靠性：客户端生成 `clientMsgId`，服务端返回 `serverMsgId` 与递增 `seq`；本地先乐观插入状态 `sending`，收到 ACK 改 `sent`，超时标 `failed` 允许重发；去重同时按 `clientMsgId` 与 `serverMsgId`，并做幂等处理（重发同一条不会产生两条）。
4. 有序与未读：排序以服务端 `seq` 为准，不能用本地时间戳（多端时钟不一致）；未读数按会话维护，"已读到某个 seq"的上报要幂等，并定期与服务端对账修正漂移。
5. 取舍与边界：历史消息与待发队列存 IndexedDB；多标签页会重复建连，用 `BroadcastChannel` 或 SharedWorker 收敛为一条连接；消息列表要虚拟滚动 + 反向滚动加载，且不能因插入新消息而跳动。
6. 如何验证：手工 + 自动化覆盖弱网、断网、切后台、多端同时在线；监控连接成功率、重连次数、消息端到端延迟 P95 与发送失败率。

**追问与易错点**：

- 追问：为什么不用轮询？答：轮询延迟高、请求量大、耗电，实时性要求高的场景必然选长连接；但弱网兜底可以用低频率轮询补拉。
- 追问：消息发送失败后自动重发会不会重复？答：会，所以必须有 `clientMsgId` 去重与服务端幂等，重发只改状态不改内容。
- 陷阱：只答"用 WebSocket 然后 `onmessage` 追加到列表"，被追问断线期间的消息、重复消息、乱序消息时全部答不上来。

### Q13 在线文档协同编辑，OT 和 CRDT 有什么区别？前端要做什么？

**考察点**：考协同编辑的基础理论差异与前端职责边界，重点是"前端不做权威仲裁"这个判断。

**参考答案**：

> **一句话结论**：OT（Operational Transformation）靠中心服务器按序变换操作，成熟但强依赖服务端；CRDT（Conflict-free Replicated Data Type）靠数据结构自带可交换性，天然支持离线与去中心，代价是元数据膨胀与垃圾回收复杂。前端无论选哪种，都要做乐观应用 + 远端回放 + 光标同步。

1. 需求澄清：是否需要离线编辑、协作人数上限、是否多人编辑同一段落、文档规模、是否需要历史版本回放、自研还是接现成方案（Yjs、Automerge、ShareDB 等）。
2. 选型对比：OT 需要中心服务器保证顺序，实现难点是 transform 函数的收敛性（多端并发操作要能变换到同一结果）；CRDT 无中心、可离线，但删除会产生墓碑（tombstone）导致文档膨胀，需要垃圾回收与压缩快照。
3. 前端要做什么：把编辑器的变更转成操作/更新，本地先应用（乐观 UI），通过 WebSocket 发出；收到远端更新时用编辑器的事务 API 应用，并标记为 remote，避免再次触发本地上报形成回环。
4. 关键难点：光标与选区同步，远端插入删除后本地光标位置必须做位置变换，否则会错位；并发编辑同一段的视觉抖动；断线重连后的状态收敛，要按状态向量（state vector）做增量或全量同步。
5. 取舍与边界：冲突收敛的最终判据在服务端或 CRDT 数据结构本身，前端不做权威仲裁；文档很大时要按块（block）同步 + 快照 + 增量，而不是每次传整篇。
6. 如何验证：用多个客户端自动化回放并发操作，断言最终内容一致（收敛性测试）；监控同步延迟、重连次数、文档首屏加载耗时。

**追问与易错点**：

- 追问：为什么收到远端更新后不能再上报一次？答：会形成回环放大（A 的更新发给 B，B 又当成本地操作发回 A），消息量指数增长。
- 追问：离线编辑怎么合并？答：CRDT 天然支持，OT 需要服务端保存操作历史再做变换；离线时间越长，重连时同步的数据量与冲突概率越高。
- 陷阱：回答停留在"用 WebSocket 广播对方的修改"，没有提操作变换、版本号、状态向量，会被认为完全没做过协同。

### Q14 设计一个低代码/可视化搭建平台，难点在哪？

**考察点**：考物料协议、画布方案、撤销重做、状态管理这些"平台级"设计，而不是拖拽本身。

**参考答案**：

> **一句话结论**：低代码平台的三根支柱是"物料协议、画布、运行时（出码/渲染）"；先把协议定死再写画布，否则物料一多就要推倒重来。

1. 需求澄清：面向谁（运营搭页面还是研发搭中后台）、是"配置即页面"还是"生成代码"、是否支持自定义组件与逻辑编排、多端要求、数据源如何绑定。
2. 物料协议：每份物料声明 `name`、`propsSchema`（驱动属性面板）、`defaultProps`、`events`、`slots`，并做版本化与校验。属性面板由 `propsSchema` + 表单引擎（见 Q7）自动生成，这是整个平台最贵也最值得投入的接口。
3. 画布方案：DOM 渲染（真实组件、所见即所得、样式准确，拖拽时用 iframe 或严格的作用域样式隔离）对比 Canvas 自绘（性能好但保真差、要自己实现文本与滚动）。主流选 DOM + 绝对/栅格布局 + 拖拽库。
4. 关键难点：撤销重做要用不可变状态 + 操作栈（command），记录可反演的 patch 而不是整棵树的快照；画布、属性面板、图层面板共享单一 store 并保证事务性更新；嵌套容器的落点判定与层级管理。
5. 取舍与边界：状态管理不能对整棵树做深度监听，节点一多必卡；出码只能限定在受控子集（组件白名单 + 受限模板），不要承诺"任意 JS 逻辑"；低代码不等于零代码，必须留代码逃生口与自定义组件接入方式。
6. 如何验证：搭建产物要有渲染回归（schema JSON → 渲染快照比对）；线上按 schema 版本聚合错误率，支持一键回滚到上一版 schema。

**追问与易错点**：

- 追问：为什么撤销重做不存整树快照？答：内存随操作次数线性增长，节点多时很快爆掉；存 patch 并支持反向应用才是可持续做法。
- 追问：出码和运行时渲染怎么选？答：出码交付物可读、可脱离平台继续开发，但要维护代码生成模板；运行时渲染迭代快、依赖平台，适合运营页。
- 陷阱：把重点全放在"拖拽怎么实现"，却答不出物料协议、状态管理与出码，会被判定为只做过 demo。

### Q15 国际化（i18n）方案怎么设计？

**考察点**：考文案抽取、语言包加载、格式化与布局适配四条线，很多人只答"用 vue-i18n"。

**参考答案**：

> **一句话结论**：国际化的工程问题只有四个：文案怎么抽、语言包怎么加载、格式怎么本地化、布局怎么适配（含 RTL）；落地顺序是集中管理 + 按需加载 + `Intl` 格式化 + 布局留白。

1. 需求澄清：支持多少语言、是否会动态新增、是否按语言拆分产物、是否有 SSR/SEO 要求、日期数字货币如何格式化、是否需要 RTL（阿拉伯语、希伯来语）。
2. 文案抽取：源码里只写 key（`t('user.login')`）不写中文硬编码，key 用命名空间规范；用脚本或 lint 规则禁止裸文案，缺失翻译时兜底默认语言并在开发环境告警，避免线上出现 key 原文。
3. 加载策略：语言包按 chunk 拆分，首屏必需的内联进主包（否则闪文案），其余在切换语言时懒加载；按语言多份产物时要注意 CDN 缓存与回滚。
4. 格式化与布局：日期数字用 `Intl.DateTimeFormat`、`Intl.NumberFormat`，不要手写 `toLocaleString` 的魔法参数；复数、货币、性别用 ICU MessageFormat；布局不能用固定宽度，德语等语言比英语长约 30%，会撑破按钮。
5. 取舍与边界：RTL 用 `dir="rtl"` + CSS 逻辑属性（`margin-inline-start`、`inset-inline-end`）实现，不要写两套样式；语言选择持久化到 Cookie/localStorage，并用 `Accept-Language` 兜底，切换后不刷新页面也要能热更新。
6. 如何验证：开发环境跑伪本地化（pseudo-localization，把文案加长加括号）提前暴露布局问题；监控语言包加载失败率与缺失 key 数量。

**追问与易错点**：

- 追问：为什么不把全部语言包一次引入？答：主包体积随语言数线性增长，首屏成本翻倍；只有默认语言才有资格进主包。
- 追问：后端返回的文案（如错误消息）怎么国际化？答：约定返回错误码，前端映射文案；或后端按 `Accept-Language` 返回已翻译文案，但错误码更利于前端做差异化提示。
- 陷阱：把中文直接当 key（`t('登录')`），文案一改 key 就全断，且无法做缺失检测，这是最常见的踩坑点。

### Q16 主题切换（含暗色模式）怎么设计？

**考察点**：考 design token 分层、运行期与构建期方案取舍、以及首屏闪烁（FOUC）这类真实工程细节。

**参考答案**：

> **一句话结论**：主题 = 一组 design token + 一套消费方式；运行期切换用 CSS 变量 + `data-theme` 属性最省事，构建期多份 CSS 只适合固定少量主题且对首屏要求极高的场景。

1. 需求澄清：几套主题（亮/暗/品牌色）、是否允许用户自定义主色、是否跟随系统 `prefers-color-scheme`、SSR 下如何避免闪烁、组件库主题怎么对接。
2. 方案对比：CSS 变量方案支持运行期切换、无刷新、可局部覆盖，兼容性差在 IE；Sass 变量/多份 CSS 是编译期确定，切换要换 link，体积重复且无法运行时改。
3. 落地结构：三层 token——原始色板（`--blue-500`）、语义变量（`--color-bg-primary`）、组件变量（`--button-bg` 引用语义变量）；主题文件只覆盖语义层，组件只消费组件层，这样换肤不用动组件代码。
4. 关键难点是首屏闪烁：在 HTML 里内联一小段脚本，读 localStorage 或系统偏好，在样式生效前给 `html` 写上 `data-theme`；暗色适配也不是简单反色，图片、阴影、透明遮罩、代码高亮要单独处理。
5. 取舍与边界：变量挂在 `html` 上便于全局切换，但主题数量多时解析开销与调试成本上升；必须与组件库（如 Element Plus 的 CSS 变量）打通，用映射而不是维护两套变量名。
6. 如何验证：视觉回归按主题各跑一遍截图；统计主题切换的使用率（太少说明是伪需求），并用无障碍工具检查暗色下的对比度。

```css
:root { --color-bg-primary: #fff; --color-text-primary: #1f2329; }
html[data-theme='dark'] { --color-bg-primary: #1a1a1a; --color-text-primary: #e5e6eb; }
.card { background: var(--color-bg-primary); color: var(--color-text-primary); }
```

**追问与易错点**：

- 追问：第三方组件的暗色怎么改？答：把它的 CSS 变量映射到你的语义 token；缺失的用低优先级选择器（如 `:where()`）覆盖，别堆 `!important`，否则后续无法覆盖。
- 追问：用户自定义主色怎么做？答：主色作为独立 token，运行时用 JS 计算派生色（深浅变体）写到根节点，或在新浏览器用 `color-mix()` 派生。
- 陷阱：为了暗色新建一套 `.dark .card { ... }` 覆盖所有组件，样式量翻倍且必然漏掉新组件，这是最典型的不可维护方案。

### Q17 灰度发布和 A/B 实验，前端方案怎么做？

**考察点**：考分流正确性（哈希分桶）、配置下发与兜底、埋点归因、以及"前端开关能做什么、不能做什么"的边界。

**参考答案**：

> **一句话结论**：灰度是"同一份代码 + 不同配置"，A/B 是"同一份代码 + 分流 + 归因"；前端负责拿分流结果、执行开关、保证埋点能归因，分流的权威逻辑必须在服务端。

1. 需求澄清：按什么维度分流（用户/设备/地域/百分比）、前后端是否要求分组一致、实验之间是否需要互斥层、开关是否需要即时生效与一键回滚。
2. 分流方案：服务端下发配置（实验 ID + 分组 + 参数），前端 SDK 启动时拉取并缓存；本地兜底用"userId 哈希取模"保证同一用户稳定分组，`Math.random()` 会导致刷新换组、实验不可解释。
3. 前端执行：提供 `isOn('flag')` / `getVariant('exp')` 或组件包装（`<Experiment>`），所有开关必须有默认值——配置拉不到就走基线，绝不能因为开关服务挂了白屏；开关变化支持订阅以便动态生效。
4. 归因是成败关键：埋点必须带上 `experimentId` 与 `variant`，否则数据无法分析；曝光埋点要在真正渲染可见时打，进页面就打会污染指标；同时要防止用户中途换组稀释数据。
5. 取舍与边界：前端开关只能做展示层与交互层灰度，接口与数据层灰度必须后端配合；实验数量增长后要治理（过期实验下线、互斥层约束），否则组合爆炸。
6. 如何验证：上线前用假分流在沙箱环境验证；上线后看实验组与对照组的样本量、指标显著性与错误率，随时能一键回滚到基线。

**追问与易错点**：

- 追问：为什么百分比分流要用哈希而不是随机数？答：随机会让同一用户每次访问进不同组，实验结论无法归因，用户体验也会来回跳变。
- 追问：灰度到 5% 时出现报错，怎么快速止损？答：先把开关置为基线（比回滚代码快），再排查；所以开关必须支持即时下发与本地缓存兜底。
- 陷阱：把分流逻辑写在前端（比如 `if (Math.random() < 0.5)`），既无法保证一致性，也无法防止用户篡改，面试官会立刻追问安全性与数据可信度。

### Q18 前端离线与缓存方案怎么设计？Service Worker 怎么用？

**考察点**：考缓存策略的分类选择与"版本更新怎么生效"这个真正的难点，而不是背 Service Worker API。

**参考答案**：

> **一句话结论**：离线能力 = Service Worker 拦截请求 + 按资源类型选策略（HTML 网络优先、静态资源 hash 后强缓存、接口 stale-while-revalidate）；难点不在缓存，而在版本更新如何生效。

1. 需求澄清：要离线到什么程度（能打开 vs 能操作）、数据是否要离线写入并同步、资源体积与存储配额、是否需要推送、更新机制用户能否接受"提示刷新"。
2. 缓存策略：预缓存 App Shell（HTML/JS/CSS/字体，`precache` 带版本号）；带 hash 的静态资源用 `Cache-Control: immutable` 长期缓存；接口用 SWR（先返回缓存再后台更新）；HTML 绝不能长期缓存，否则用户永远拿不到新版本。
3. 更新流程：新 SW `install` 预缓存 → 进入 `waiting` → 页面提示"新版本可用" → `skipWaiting` + `clients.claim` → 刷新；要处理"旧页面还在用旧 SW"的窗口期，关键接口必须同时兼容新旧两个版本。
4. 数据同步冲突：离线写入放 IndexedDB 队列，恢复网络后按序重放，每条带客户端请求 ID 保证幂等；冲突策略必须显式约定（服务端时间优先 / 字段级合并 / 提示用户选择），不要默认后写覆盖。
5. 取舍与边界：Service Worker 只在 HTTPS 下可用、缓存了错误资源要靠版本与清理逻辑自救、iOS 上回收较积极、存储配额有限；不要把跨域的隐私接口响应塞进 Cache Storage。
6. 如何验证：用 DevTools 的 Offline/慢网模拟与 Lighthouse PWA 检查；监控 SW 安装/激活失败率、缓存命中率、更新提示点击率。

**追问与易错点**：

- 追问：为什么 HTML 不能强缓存？答：HTML 里引用的才是带 hash 的新资源，HTML 被缓存住等于整个应用停在旧版本，所以 HTML 一般用 `no-cache` 协商缓存。
- 追问：`skipWaiting` 有什么风险？答：新 SW 立即接管可能与还在运行的旧页面资源不匹配，所以要配合提示刷新并保证接口向后兼容。
- 陷阱：只说"加个 Service Worker 就能离线"，说不出缓存策略分类与更新流程，被追问"发版后用户拿到旧页面怎么办"就答不上来。

### Q19 从 0 写一个团队脚手架，你会怎么设计？

**考察点**：考 CLI 的架构拆分、交互与 CI 兼容、模板的版本化与升级路径。很多人只答"拉个 git 仓库模板"。

**参考答案**：

> **一句话结论**：脚手架要解决"新项目 5 分钟跑起来 + 团队规范内置 + 后续能升级"，架构上拆成 CLI（命令与交互）+ 模板（可版本化）+ 生成器（可组合的代码片段）。

1. 需求澄清：服务几个团队与几种技术栈、是否需要增量生成（加页面/组件/接口）、是否需要给老项目接入规范、是否使用私有 npm registry。
2. 命令设计：`create my-app`（交互选择模板、包管理器、TS、规范）、`add page xxx`（在已有项目生成文件并自动注册路由）、`upgrade`（升级规范依赖与配置）。非 TTY 环境（CI）必须有 `--template` 之类的参数兜底，否则流水线会卡在交互上。
3. 实现要点：模板不靠 `git clone`（慢且依赖网络），改为内置模板文件 + 模板引擎（`ejs`/`handlebars`）渲染变量；生成前校验目标目录是否为空；发布用 `package.json` 的 `files` 白名单控制体积。
4. 关键难点是升级路径：脚手架生成的项目本质是一次性拷贝，后续规范升级无法自动同步；解法是提供 `upgrade` 做 codemod（改配置、加依赖、改 lint 规则），并把规范抽成可独立升级的 npm 包，业务只需升级一个版本号。
5. 取舍与边界：模板越全越难维护，只预置"一定会用到"的（ESLint/Prettier、TS、目录约定、请求封装、环境变量）；目录结构这类强约定有利于协作，但要给业务留明确例外。
6. 如何验证：模板必须有冒烟测试（生成项目 → 安装依赖 → 构建跑通），并在 CI 定期执行，否则模板会静默腐坏。

**追问与易错点**：

- 追问：为什么不直接 fork 一个开源脚手架？答：起步快，但团队规范塞不进去、上游升级要不断合代码；可以用它当起点，但模板与规范包必须自己维护。
- 追问：怎么让老项目也享受规范升级？答：把规范做成独立依赖 + `upgrade` 命令做增量修改，避免让业务手工改配置。
- 陷阱：脚手架里塞满业务代码（某个项目的接口封装、埋点实现），其他团队拿去根本用不上，这是"模板即负债"的典型。

### Q20 技术选型：Vue 和 React 你怎么选？

**考察点**：考选型方法论（人、生态、场景）而不是框架优劣论。要能给出条件化的结论与迁移代价。

**参考答案**：

> **一句话结论**：两者能力上没有代差，选型看"人、生态、场景"：团队熟哪个、需要的生态组件有没有、长期好不好招人；不要用"Vue 简单、React 灵活"这种印象流回答。

1. 团队与招聘是第一位：切换框架的隐性成本（重写、踩坑、招聘门槛）远大于技术收益；在内地城市，Vue 的岗位与人才供给面更宽。
2. 技术差异用事实说话：模板 vs JSX（Vue 有编译期优化，React 靠运行时与手动 `memo`）；响应式自动依赖收集 vs 手动不可变更新；单文件组件把模板、逻辑、样式放一起，React 生态更偏函数式与组合。
3. 生态与场景：中后台表单表格两者都有成熟组件库；SSR/SSG 上 Next.js 更成熟，跨端上 React Native 更成熟；企业内网工具、需要大量中文现成组件时 Vue 更顺手。
4. 复杂状态与团队规模：大团队、复杂状态、大量自定义渲染时，React 的 hooks 组合性与生态基建（状态库、测试工具）更占优，但对团队自律要求高（依赖数组、memo、闭包陷阱）。
5. 取舍与边界：不要在一个应用里混用两套框架（除非微前端且收益明确）；已有系统迁移走"新页面用新框架 + 微前端渐进替换"，不要停机重写。
6. 面试口径：给"结论 + 理由 + 代价"三件套，例如"团队主力 Vue3，中后台继续用 Vue3 + TS + 组件库；如果要做面向 C 端的 SSR 站点，我会优先评估 Nuxt/Next 生态再决定"。

**追问与易错点**：

- 追问：Vue3 也能 SSR，为什么提 Next.js？答：Nuxt 同样成熟，这里要表达的判断是"SSR 场景看生态成熟度与团队熟悉度，而不是框架名"。
- 追问：Composition API 和 React Hooks 像不像？答：形似神不同——`setup` 只在创建时执行一次、依赖靠响应式系统自动收集，没有 Hooks 的闭包陷阱与依赖数组问题。
- 陷阱：只输出"Vue 上手快、React 生态大"这类没有条件与代价的结论，会被追问"你们项目当年为什么这么选"，答不出业务约束就露馅。

### Q21 技术选型：Vite 和 Webpack 你怎么选？

**考察点**：考对两者原理差异的真实理解（开发期机制不同）与迁移代价判断，而不是"Vite 就是快"。

**参考答案**：

> **一句话结论**：新项目默认 Vite（开发体验差距明显），但遇到"依赖 Webpack 特有 loader/plugin、必须兼容到 ES5、已有复杂构建定制"的存量项目，继续用 Webpack 更稳。

1. 原理差异：Vite 开发期用浏览器原生 ESM 按需编译，依赖用 esbuild 预构建，冷启动与 HMR 基本不随项目规模增长；Webpack 开发期全量打包进内存，项目越大启动越慢（5.x 有持久化缓存改善，但架构没变）。
2. 生产构建：Vite 用 Rollup，产物质量与 tree-shaking 好，但分包与产物定制的灵活度不如 Webpack，Module Federation 这类方案 Webpack 更成熟。
3. 选 Vite 的信号：Vue3/React 新项目、明确放弃 IE、需要快速冷启动与热更新；选 Webpack 的信号：存量巨型项目、需要自定义 loader 处理特殊文件、微前端 Module Federation、必须产出 ES5 或兼容低版本浏览器。
4. 迁移成本主要在配置重写（loader → 插件）、`require`/环境变量写法调整、产物路径与 CDN 配置核对；迁移期建议保留双构建能力以便回滚。
5. 取舍与边界：Vite 开发与构建是两套机制（esbuild vs Rollup），会出现"开发正常、构建报错"的差异，所以 CI 里必须跑真实构建；Webpack 的速度问题可以用持久化缓存 + SWC/esbuild loader 缓解，不必为了快强行迁移。
6. 面试口径：给出"默认选谁 + 什么条件下换 + 生产构建谁负责 + 怎么验证产物一致"，比单纯比较速度更有说服力。

**追问与易错点**：

- 追问：为什么 Vite 生产不用 esbuild？答：esbuild 在 CSS 处理、代码分割策略、插件生态上不如 Rollup 成熟，Vite 因此用 esbuild 做开发、Rollup 做生产。
- 追问：Vite 项目里 `require` 为什么报错？答：开发期是原生 ESM 环境，`require` 不存在；要改成 `import`，Node 侧用 `createRequire` 兜底。
- 陷阱：只说"Vite 启动快 10 倍"却答不出开发与生产的机制差异，被追问构建产物优化时就会卡住。

### Q22 团队要上 Monorepo 吗？什么时候该引入 TypeScript？

**考察点**：考架构决策的收益与代价意识，以及 TypeScript 渐进式引入的判断，两题合一考的是"决策合理性"。

**参考答案**：

> **一句话结论**：Monorepo 解决"多包共享与联动发版"，多仓解决"边界清晰与独立发布"；包之间强复用、发布节奏一致就上 Monorepo，跨部门、生命周期独立就用多仓。TypeScript 的引入时机是"团队 ≥3 人且项目预期生命周期超过半年"，从新代码渐进推进。

1. 判断依据：包之间是否有共享代码与联动改动（组件库 + 业务 + 工具）、发布节奏是否一致、CI 时长能否接受、代码所有权与权限边界是否清晰。
2. Monorepo 要解决三件事：依赖与任务编排（pnpm workspace + Turborepo/Nx）、幽灵依赖（pnpm 严格 `node_modules` 结构）、版本发布（changesets 生成版本与 changelog）。
3. Monorepo 的代价：仓库变大、CI 变慢、权限难细分、工具链复杂，一个包配错会影响所有人；没有对应收益的团队上 Monorepo 是负债。
4. 多仓的做法：共享代码发私有 npm 包并固定版本，跨仓联调用 `pnpm link`/`yalc` 或 alpha 版本，接受"发版链路长"的代价。
5. TypeScript 引入时机：新项目/新模块直接上；存量项目先开 `allowJs` + `checkJs` 做局部类型，用 `any` 兜底，再逐步开 `strict`；收益是可维护性与重构安全，代价是类型维护成本与第三方库类型缺失（`@types/*`、`declare module`）。
6. 如何验证：Monorepo 看 CI 时长、发布频率与跨包改动成本是否改善；TypeScript 看类型错误数、因类型错误导致的线上问题比例，而不是"我们用了 TS"。

**追问与易错点**：

- 追问：为什么 TypeScript 不建议一次性全量重写？答：会产生超大 PR、评审几乎不可能、业务停摆风险高；增量迁移 + 严格度分级才是可落地路径。
- 追问：Monorepo 里怎么保证只构建受影响的包？答：靠任务编排工具的文件指纹缓存与依赖图（Turborepo 的 `--filter`、Nx 的 affected），没有缓存机制的大仓 CI 会难以忍受。
- 陷阱：为了"显得先进"直接上 Monorepo + TS 全量改造，却说不清收益与代价，这类回答在面试官眼里是风险信号。

### Q23 页面偶发卡死，用户说复现不了，你怎么推进？

**考察点**：考排查方法论：先量化、再收窄、最后归因，以及"止血优先"的工程判断。这是最贴近真实工作的一道开放题。

**参考答案**：

> **一句话结论**：偶发问题的正确打法是"先量化、再收窄、最后归因"——先补数据和上下文，用数据把范围从"所有用户"收窄到某个机型/版本/页面/路径，再针对性复现。

1. 澄清定义：先问清"卡死"到底是白屏、主线程无响应，还是浏览器崩溃/页面被杀；影响面是几个用户还是批量、有无时间规律、是否集中在某浏览器/机型/版本。
2. 补数据（最重要）：加长任务监控（`PerformanceObserver` 的 longtask 与 INP）、内存采样（Chromium 的 `performance.memory`，非标准 API）、卡死前的操作面包屑与接口记录；再用看门狗（`setInterval` 心跳）检测主线程阻塞，超阈值就上报并 dump 当时的调用栈。
3. 收窄范围：按 release、机型、页面、浏览器聚合，看是否与某次发布或某接口强相关；若集中在某个页面，用性能面板 + CPU 降速 + 内存时间线复现，怀疑内存泄漏就用三次堆快照对比 detached DOM。
4. 提出假设并验证：例如"图表组件在大数据量下死循环""定时器未清理导致任务累积"，用最小复现 demo + 数据注入验证，而不是改代码试运气。
5. 止血与取舍：偶发问题不能无限投入，先设投入上限，同时上线兜底（错误边界、超时提示、限制单页数据量、降级关闭高耗组件）保证用户可用。
6. 如何验证：修复后用同一维度对比修复前后指标（卡死率、长任务数 P95），并补一条回归用例，防止同类问题再次出现。

**追问与易错点**：

- 追问：卡死时上报还能发出去吗？答：主线程被阻塞时 `fetch` 与 `sendBeacon` 也会排队，所以要尽早触发上报，或把上报放到 Worker，并在下一次启动时补报上次的异常退出。
- 追问：没有用户 ID 和时间点怎么办？答：先补 sessionId 与 release 维度，没有维度就无法聚合，这一步必须优先做。
- 陷阱：一上来就说"我去看代码找 bug"，或者把"多打点日志"当方案——面试官要看的是假设驱动的排查流程与止损意识。

### Q24 技术方案评审怎么做？代码规范怎么推动落地？

**考察点**：考工程治理能力：把方案讲清楚让别人能否决你，以及把规范从文档变成卡点。两件事本质都是"让别人愿意配合"。

**参考答案**：

> **一句话结论**：技术方案评审不是"讲一遍让大家点头"，而是拿一份有清单的文档，把目标、方案对比、风险取舍、验证方式讲清楚，让评审人能在关键决策点上否决你；规范落地靠的是工具化 + 卡点 + 低摩擦，而不是发文档。

1. 评审前：文档先行（一页纸 + 必要图示），明确这次要评审什么（选型、接口契约还是风险），提前 1-2 天发给参会人并指定必须到场的 owner。
2. 评审清单：背景与目标（做什么、不做什么）、方案与至少一个备选（及代价）、接口与数据约定、兼容与灰度、异常与回滚、可观测性、测试与验收标准、排期与人力。
3. 评审中：先讲结论再讲细节，把有争议的点显式列出并当场定责（谁在什么时间给出结论）；避免评审跑偏成风格讨论，架构决策要落成 ADR（Architecture Decision Record）存档。
4. 规范落地：ESLint/Prettier 配置抽成共享包、husky + lint-staged 卡提交、CI 卡合并、commit 规范模板；新代码必须合规，存量代码增量修复（`--fix` + 目录级白名单），不要一次性全量格式化——会污染 git blame 并引发大面积冲突。
5. 关键难点：规范推不动通常是"有成本没收益"，所以要把工具做成一键（`pnpm lint:fix`），把收益变得可见（CI 失败率下降多少、review 返工减少多少），并在周会上持续曝光豁免清单。
6. 如何验证：看合规率（lint 通过率、豁免条数）、review 中风格类评论占比、CI 失败率；每条豁免必须带原因与到期时间。

**追问与易错点**：

- 追问：老代码一堆报错，怎么让 lint 真正生效？答：先只对新增与改动文件强校验（`lint-staged` + 增量范围），配 baseline 文件忽略存量，再按模块逐步清理。
- 追问：评审时没人提意见怎么办？答：把关键决策点写成"选项 A / 选项 B + 我的建议"，明确点名请相关 owner 表态，沉默不等于同意。
- 陷阱：把评审当成"通知会"，方案已经开完发才拉大家过一遍；或者规范只发文档不设卡点，两周后回到原样。

### Q25 怎么做一次技术分享？项目做完怎么做技术复盘？

**考察点**：考知识沉淀能力：分享看"听众能带走什么"，复盘看"同类问题会不会再来一次"。两者都必须有结构化输出物。

**参考答案**：

> **一句话结论**：分享的目标是"听众带走一个可用的结论"，复盘的目标是"同类问题不再发生第二次"；共同点是要有结构化输出物，而不是讲完就散。

1. 分享选题：从听众收益出发（"上线后定位问题从 30 分钟到 5 分钟"），一次只讲一个主题，标题写结果而不是技术名词，避免"我用 XX 做了 YY"的自嗨式选题。
2. 分享结构：Why（为什么值得听）→ What（核心概念，最多 1-2 个）→ How（现场演示或代码，占一半时间）→ 坑与代价（最加分）→ 带走清单（3 条可执行结论）；总时长 30-40 分钟 + 10 分钟问答，演示要准备录屏兜底。
3. 分享执行：至少彩排一次并掐时间，准备 3 个可能被追问的答案；会后把讲稿、PPT、示例代码归档到团队知识库，并给没到场的人提供异步版本。
4. 复盘结构：时间线（几点几分发生了什么）→ 影响面（多少用户、持续多久）→ 直接原因与根本原因（用 5 Why，不要停在"某人手滑"）→ 处理过程中做对什么、做错什么 → action item（责任人 + 截止时间 + 验证方式）。
5. 关键难点：复盘要"对事不对人"，否则没人敢暴露问题、时间线永远不真实；action item 必须有 owner 与验收标准，否则复盘等于开会；结论要沉淀成 runbook 或自动化卡点（比如发布前检查、灰度门禁）。
6. 如何验证：跟踪 action item 完成率与同类事故复发率这两项指标；分享的效果看同事是否真的用上了（工具被引用、方案被复用），而不看参会人数。

**追问与易错点**：

- 追问：复盘和总结有什么区别？答：总结是"我们做了什么"，复盘是"为什么结果是这样、下次怎么做才不一样"，后者必须包含可验证的改进项。
- 追问：分享没人来听怎么办？答：先找最痛的那批人（比如天天排查线上问题的人）当听众，选题贴着他们的问题讲，而不是讲自己最熟的东西。
- 陷阱：改进项写成"加强测试意识""提高代码质量"这类无法验证的口号；或者只修 bug 不加卡点，同类问题换个形式复发。

### Q26 讲一个你最有挑战的项目难点（用 STAR 说）

**考察点**：考表达结构与技术深度的结合：能否用 STAR 讲清背景并把 70% 时间放在技术决策上，以及能否量化结果。

**参考答案**：

> **一句话结论**：用 STAR 讲，但时间分配是"S 一句、T 一句、A 占七成、R 必须量化"，最后补一句"如果重来我会怎么做"。

1. S（背景）：1-2 句交代业务、规模（用户量/数据量/团队人数）和你的角色，不要铺垫太久，面试官关心的是技术。
2. T（任务）：说清那个具体技术问题和一个可衡量目标，例如"把首屏 LCP 从 4.2s 降到 2s 以内"，避免"提升用户体验"这种无法验证的目标。
3. A（行动，讲七成时间）：按"瓶颈定位 → 方案对比 → 选型取舍 → 落地与踩坑"展开。定位必须有数据（性能面板、火焰图、监控指标），方案要有备选与为什么不选，踩的坑要说清根因与最终解法——技术深度就是从这里体现的。
4. R（结果）：给量化结果（指标前后对比、影响用户量、成本变化），并说明数据是怎么来的（同口径监控、A/B 对照）；没完全达成也要诚实说"改善了 X，因为 Y 未达预期"。
5. 技术深度怎么展开：面试官追问时按三层走——原理层（为什么会慢/会这样）、边界层（什么情况下方案失效）、泛化层（同类问题怎么套用）；举例说明比堆名词有效得多。
6. 收尾：主动说"现在回看，我会提前加监控与压测，并把这个经验沉淀成规范或工具"，体现复盘意识与方法论，而不是把难点讲成流水账。

**追问与易错点**：

- 追问：怎么证明优化效果是你的方案带来的？答：要有对照——A/B、优化前后同口径数据，并排除其他变量（版本、网络、数据量差异），不能只说"上线后感觉快了"。
- 追问：如果重来一次你会改什么？答：这是面试官在考复盘能力，必须给出具体改进（先做监控、先定验收指标、提前和后端对齐接口），不能答"没什么可改的"。
- 陷阱：选一个"团队协作很难"的软性难点全程讲沟通，技术深度为零；或者把别人的工作说成自己的，追问两层细节就崩。

### Q27 工作量怎么评估和排期？需求变更和跨部门沟通怎么处理？

**考察点**：考项目管理的工程化思路：拆解、估算方法、buffer、变更流程与跨部门沟通的"带方案沟通"原则。

**参考答案**：

> **一句话结论**：排期 = 把需求拆成可验证的任务单元再估时并留 buffer；需求变更不可怕，可怕的是"悄悄变更"，所以要用"影响清单 + 书面确认 + 优先级重排"来处理。

1. 拆解先行：拆到 0.5-2 天的颗粒度（前端常见拆法：接口联调、页面结构、组件、异常态、自测、联调、回归），颗粒太大估不准，太小管理成本高。
2. 估算方法：用三点估算（乐观/悲观/最可能）或类比历史任务；不确定的部分单独列成风险项，给出触发条件与备选方案，不要"拍脑袋给一个数字"。
3. 加 buffer 并暴露依赖：整体留 20%-30% buffer；排期是"区间 + 假设条件"，例如"如果接口 X 号前给到，Y 号能提测"，把外部依赖写进排期本身就是风险沟通。
4. 需求变更处理：先评估影响（工时、关联模块、测试范围、上线时间），再给出 2-3 个选项（延期 / 砍别的需求 / 分期做 / 加人但短期更慢），让需求方做选择；所有变更留书面记录（需求文档或群消息确认）。
5. 跨部门沟通：用对方的语言表达（对产品讲用户影响与交付风险，对后端讲接口契约与联调成本），带方案去谈而不是只提问题；分歧升级时给出"我的建议 + 依据"，让 leader 决策而不是把矛盾抛上去。
6. 如何验证：记录每次"实际 vs 预估"的偏差，在复盘中修正估算系数；一段时间后看排期准确率与需求返工率是否改善。

**追问与易错点**：

- 追问：需求临时加塞怎么办？答：不直接说不，先问"要插入它，就得砍掉哪个已有需求或延到哪一期"，把优先级决策交回需求方。
- 追问：后端接口延期导致你要空等怎么办？答：先按契约用 Mock 推进前端开发，同时把风险暴露在群里与排期表上，让延期有记录、可追溯。
- 陷阱：答"我一般多留点时间"这种只有结果没有方法的话；或者需求变更全口头答应，最后延期时说不清是谁改的范围。

### Q28 你有什么想问面试官的？

**考察点**：考候选人的关注点与主动性。反问是最后一次展示匹配度的机会，问什么暴露你在意什么。

**参考答案**：

> **一句话结论**：反问优先问团队与岗位真实情况、技术现状、你入职后前几个月的目标，其次才是福利；准备 2-3 个按轮次递进的问题。

1. 团队与业务："团队现在多少人、前端怎么分工，有没有专职产品与测试？我进来主要做哪条业务线？"——判断是不是"一个人扛全部"。
2. 技术与现状："目前技术栈和版本是什么？有没有在推进的工程化或重构计划？"——判断是救火还是建设，同时展示你关心工程质量。
3. 流程与协作："需求怎么流转、排期谁定、有没有代码评审和独立测试环境？发布节奏是多久一次？"——判断流程成熟度，也关系到你的规范能否落地。
4. 期望与考核："这个岗位前 3-6 个月最主要的目标是什么？怎么衡量做得好？"——判断对方要什么，避免入职后目标错配。
5. 成长与氛围："团队有技术分享和复盘机制吗？新人上手一般多久？"——想更直接的话可以问"上一个做这个岗位的人为什么离开"，但要看面试氛围决定要不要问。
6. 注意：第一轮别问薪资福利与加班强度（可以中性问"上线节奏和加班情况大概是怎样的"），不要问官网能查到的信息；准备 2-3 个问题并按轮次递进，反问时可以顺势补一句自己的匹配点。

**追问与易错点**：

- 追问：面试官问"你还有什么想问的"，说"没有"行不行？答：不建议，会被理解为对岗位兴趣不足；至少问一个关于团队目标或技术现状的问题。
- 追问：能问加班吗？答：可以，但要中性、具体（一周几次上线、有没有值班），别带着情绪问"你们加班严重吗"。
- 陷阱：把所有问题都集中在薪资、假期、调休上，或者问"你们公司是做什么的"这种资料里能查到的信息，会显得准备不足。

## 本章小结

- 场景设计题一律按"需求澄清 → 技术方案 → 关键难点 → 取舍与边界 → 如何验证/监控"五段答，先说结论再展开，面试官才能跟上你的思路。
- 组件 API 设计的通用原则：状态归属明确（受控与非受控并存）、组合优于配置（插槽或 children 当逃生口）、行为可受控、错误与无障碍在一开始就设计进去。
- 每个平台级设计都有"最贵的那份接口"：组件库是 design token 与主题、低代码是物料协议、动态表单是 Schema、脚手架是模板与规范包，先定它再写实现。
- 可靠性场景（埋点、IM、协同、上传、离线）的通用套路是：本地乐观 + 唯一 ID 去重 + 幂等重放 + 状态机 + 定期对账，最后都靠队列与重试收敛。
- 性能场景（虚拟滚动、大表格、大文件、低代码画布）的通用判断是：只渲染可视区、把重计算移出主线程、避免整树监听与全量重渲染。
- 任何前端权限、开关、灰度都只是体验优化，接口与数据的权威校验必须在后端，这是越权与数据可信度的底线。
- 所有方案都要回答"怎么知道它有效"：埋点指标、灰度对比、故障注入、回归用例、可观测性，答不出验证方式的方案等于没落地。
- 开放题（STAR、复盘、排期、变更、反问）都遵循"结论先行 + 结构化 + 量化结果 + 主动说代价与改进"，这比堆砌技术名词更能体现可信度。
