## 第 16 章 前端性能优化

### Q1 给你一个页面，你怎么做性能优化？完整流程说一遍

**考察点**：考方法论而不是零散技巧。答出「度量 → 定位 → 优化 → 验证」闭环，并说清每步的产出物，才算过关。

**参考答案**：

> **一句话结论**：性能优化是工程闭环，不是技巧堆砌——先定指标口径并采集数据，再定位到具体瓶颈，只改瓶颈并小步上线，最后用同一口径的前后数据证明有效。

1. 度量：先约定口径，取核心指标的 P75（75 分位）而非平均值，并区分实验室数据（Lighthouse、DevTools）与真实用户数据（RUM，Real User Monitoring）。
2. 定位：用 DevTools 的 Performance 面板看火焰图找长任务（Long Task），用 Network 瀑布图看首屏关键路径，用 Coverage 面板看未使用代码，把问题落到具体资源与函数。
3. 优化：按投入产出比排序，只动首屏关键路径上的大项，一次只改一两个变量，避免顺手重构污染前后对比。
4. 验证：在与线上接近的设备与网络条件下复测，并按版本、机型、网络分维度看灰度数据；指标回退要能回滚。
5. 沉淀：把结论写成性能预算（Performance Budget）与 CI 卡口，防止后续提交把优化成果吃回去。

**追问与易错点**：

- 追问：为什么不能用平均值？答：平均值会被大量快用户摊平，真正流失的是慢的那部分用户，所以看 P75/P95。
- 陷阱：一上来就背「合并请求、加 CDN、用缓存」，没有度量就优化属于过早优化，会被追问「你怎么知道瓶颈在这里」。
- 追问：实验室数据和真实数据不一致怎么办？答：两者口径不同（设备、网络、缓存、地理分布），实验室用于定位，RUM 用于判断真实影响，冲突时以 RUM 为准。

### Q2 FP、FCP、LCP、FID、INP、CLS、TTFB、TBT、TTI 分别是什么？达标线是多少？

**考察点**：考指标全家桶是否分得清，尤其是「加载类指标」与「交互类指标」的边界。能背出阈值并说清各自度量什么，才算过关。

**参考答案**：

> **一句话结论**：这些指标分三组——加载（FP、FCP、LCP、TTFB）、交互（FID、INP、TBT、TTI）、视觉稳定（CLS）；其中 LCP、INP、CLS 是核心网页指标（Core Web Vitals）。

1. 加载组：TTFB 是首字节时间，度量服务端与网络；FP 是首次绘制出任何像素；FCP 是首次绘制出内容（文本、图片）；LCP 是视口内最大内容元素的渲染时间，最贴近「用户觉得首屏好了」。
2. 交互组：FID 只测第一次交互的输入延迟，已被 INP 取代；INP 测整页所有交互的延迟（约 P98 的交互），包含输入延迟、处理时间、呈现延迟三段。
3. 主线程组：TBT 是 FCP 与 TTI 之间所有长任务超出 50ms 部分的总和；TTI 是主线程持续 5 秒无长任务、且未完成的 GET 请求不超过 2 个的时刻。
4. CLS 度量布局偏移总和，只统计非用户输入触发的、可见元素的位移。
5. 阈值口径（官方「好」的标准）：TTFB ≤ 0.8s，FCP ≤ 1.8s，LCP ≤ 2.5s，INP ≤ 200ms，CLS ≤ 0.1；FID ≤ 100ms（已退役），Lighthouse 移动端 TBT ≤ 200ms、TTI ≤ 3.8s。

| 指标 | 度量什么 | 好 | 需改进 | 差 |
| --- | --- | --- | --- | --- |
| LCP | 最大内容元素渲染 | ≤2.5s | 2.5-4.0s | >4.0s |
| INP | 全页交互延迟 | ≤200ms | 200-500ms | >500ms |
| CLS | 布局偏移总和 | ≤0.1 | 0.1-0.25 | >0.25 |
| TTFB | 首字节 | ≤0.8s | 0.8-1.8s | >1.8s |
| TBT | 长任务阻塞总量 | ≤200ms | 200-600ms | >600ms |

**追问与易错点**：

- 追问：为什么 TBT、TTI 不在核心网页指标里？答：它们是实验室指标，依赖模拟环境，不适合做真实用户分位数统计，但很适合定位主线程问题。
- 陷阱：把 FP 与 FCP 混为一谈。FP 可能只是背景色（白屏变灰屏），FCP 才代表有内容。
- 陷阱：说 LCP 是「首屏加载完成时间」，不对。LCP 只关心最大的那一个内容元素，页面可以 LCP 达标但内容仍在刷新（那就该看 CLS 了）。

### Q3 核心网页指标（Core Web Vitals）是哪几个？FID 为什么被 INP 取代？

**考察点**：考版本演进与设计动机。答出「三个指标 + 2024 年 3 月 FID 退役、INP 转正」并说清原因，才算过关。

**参考答案**：

> **一句话结论**：核心网页指标是 LCP、INP、CLS，分别对应加载、交互、视觉稳定；INP 在 2024 年 3 月 12 日取代 FID，因为 FID 只看第一次交互的输入延迟，漏掉了处理和渲染阶段。

1. 覆盖更全：FID 只测首次交互且只测输入延迟，页面后续卡顿、重计算导致的延迟全都不算数；INP 统计全页交互，取约 P98（交互少时接近最差那次）作为该页代表值。
2. 粒度更细：INP 把一次交互拆成输入延迟、事件处理时间、呈现延迟三段，能直接指出是主线程长任务还是渲染被拖住。
3. 口径变化：FID 是「第一次」，INP 是「最差的那次」，所以原先 FID 达标的站点换成 INP 后普遍会变差，这正是它有价值的地方。
4. 三项指标分别可被三类手段改善：LCP 靠资源与首屏路径，INP 靠拆分长任务与减少水合成本，CLS 靠预留空间与动画方式。

**追问与易错点**：

- 追问：INP 很差不一定是接口慢，怎么区分？答：看 event 条目的三个分段，输入延迟高说明主线程被长任务占着，处理时间长说明事件回调本身重，呈现延迟高说明渲染或合成被拖住。
- 陷阱：说「INP 是平均值」，不对。它取的是较差的交互，再在用户之间取 P75。
- 陷阱：以为优化了 FID 就等于优化了 INP，两者统计范围完全不同。

### Q4 RAIL 模型是什么？它给你什么指导？

**考察点**：考性能建模能力。答出四个字母各代表什么、用量级（毫秒）说话，才算过关。

**参考答案**：

> **一句话结论**：RAIL 是 Response、Animation、Idle、Load 四个环节的用户体验模型，核心是给每类工作一个时间预算，用预算反推代码该怎么写。

1. Response（响应）：用户点击到视觉反馈控制在 100ms 内，否则会被感知为「没反应」。
2. Animation（动画）：每帧预算 16.7ms（60fps），实际留给 JS 与样式计算的时间约 10ms，剩下留给浏览器渲染。
3. Idle（空闲）：把非关键工作切成不超过 50ms 的小块，用 requestIdleCallback 或主动让出主线程，避免长时间霸占。
4. Load（加载）：目标是首屏在 1s 内有内容，弱网场景放宽到 5s 内可用。
5. 用法：先确定当前问题属于哪一类（点了没反应 / 滚动掉帧 / 首屏慢），再按该类预算去度量和优化，而不是四个一起优化。

**追问与易错点**：

- 追问：为什么空闲任务要切 50ms？答：长任务（Long Task）的判定线就是 50ms，超过就会阻塞输入响应，用户可感知卡顿。
- 陷阱：把 RAIL 当成指标清单背。它是设计约束，不是测量结果，真正上报还是用 LCP/INP/CLS。
- 追问：100ms 响应怎么落地？答：先用乐观 UI 或骨架屏给出即时反馈，再把真请求放后台，别让用户等接口才看到变化。

### Q5 performance.mark 和 performance.measure 怎么用？用在什么场景？

**考察点**：考 User Timing API 的实战用法，以及它和业务埋点的关系。

**参考答案**：

> **一句话结论**：mark 打时间点、measure 算两个点之间的时长，它们把业务代码的关键阶段接入浏览器性能时间线，既能本地看，也能通过 PerformanceObserver 上报。

1. 用法：`performance.mark('start')` 记录时刻，`performance.measure('render', 'start', 'end')` 生成一条带有 duration 的测量条目。
2. 读取：`getEntriesByName` 取单条，PerformanceObserver 订阅 `measure` 类型可实时拿到。
3. 典型场景：路由切换耗时、首屏数据请求耗时、大表格渲染耗时、组件初始化耗时，这类「业务语义耗时」其他指标都测不到。
4. 注意点：测量名要带版本或模块前缀避免撞车；上报前用 `clearMarks`/`clearMeasures` 清理，避免时间线条目堆积。

```js
performance.mark('list-start');
await fetchList().then(renderRows);
performance.mark('list-end');
performance.measure('list-render', 'list-start', 'list-end');

new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    console.log(e.name, e.duration.toFixed(1) + 'ms');
  }
}).observe({ type: 'measure', buffered: true });
```

**追问与易错点**：

- 追问：为什么用 mark/measure 而不是 `Date.now()` 做差？答：前者使用高精度单调时钟，不受系统时间调整影响，且能进入 DevTools 的 User Timing 轨道与时间线对齐。
- 陷阱：忘记 `buffered: true`，导致页面早期产生的条目在观察者创建之前就丢了。
- 追问：这些数据怎么和接口耗时对齐？答：measure 的起点放在请求发出前，终点放在数据渲染完成，把网络耗时和渲染耗时拿到的是一段端到端业务耗时。

### Q6 静态资源体积怎么减？压缩、tree-shaking、依赖瘦身分别怎么做？

**考察点**：考资源体积优化的完整清单，以及「看清楚再砍」的习惯。答出体积分析工具、tree-shaking 生效条件、依赖与字体处理，才算过关。

**参考答案**：

> **一句话结论**：体积优化的顺序是先用可视化工具看清构成，再依次砍掉没用的依赖、让 tree-shaking 真正生效、按需引入大库、最后做压缩与传输压缩。

1. 问题现象：首屏 JS 包动辄 1-2MB，低端机解析执行久，LCP 与 INP 都差。
2. 定位手段：webpack-bundle-analyzer、rollup-plugin-visualizer 看包构成；DevTools 的 Coverage 面板看未使用代码比例；Network 面板看传输体积与压缩前后差距。
3. 优化手段一，让 tree-shaking 生效：用 ES Module（ESM）写法，构建工具标记 `sideEffects: false`，避免 `import _ from 'lodash'`，改为 `import debounce from 'lodash/debounce'`；`moment` 换 `dayjs`/`date-fns`；`xlsx`、`echarts`、地图 SDK 按需或按路由加载。
4. 优化手段二，压缩与传输：Terser/esbuild 压缩，CSS 用 cssnano，文本资源开 gzip/brotli，图片与字体本身已是二进制压缩格式，不再二次压缩。
5. 优化手段三，字体：中文字体动辄几 MB，必须子集化（只保留页面用到的字符集）或改用系统字体栈，配合 `font-display` 与 `preload`。
6. 预期收益与代价：首屏 JS 常能砍掉可观比例，收益直接反映在 LCP 与 INP 上；代价是改依赖引入方式需要回归测试，字体子集化要接入构建流程并维护字符来源，否则会出现缺字。

**追问与易错点**：

- 追问：为什么 lodash 明明按需引入体积还是不小？答：可能仍引入了整包或 helper 重复，检查是否走了 CJS 入口，或直接用 `lodash-es`。
- 陷阱：把「不压缩已压缩格式」说反。woff2、webp、avif、png、zip 再 gzip 基本没有收益，还浪费 CPU。
- 陷阱：只看构建产物体积，不看解析执行成本。同样 300KB，拆成 30 个小文件在 HTTP/2 下也会带来依赖瀑布，未必更好。

### Q7 代码分割和按需加载怎么做？拆到什么粒度合适？

**考察点**：考拆包策略与取舍判断，不是背 `import()` 语法。

**参考答案**：

> **一句话结论**：代码分割的核心原则是「按变更频率和访问概率拆」，首屏只加载首屏必需的代码，其余按路由、按组件、按交互时机延迟加载。

1. 问题现象：所有页面打成一个 bundle，用户只看一个页面却下载了整站代码，首屏白屏时间变长。
2. 定位手段：看产物分析图里各 chunk 体积，结合路由表判断哪些代码根本不属于当前页面。
3. 优化手段一，路由级分割：路由组件用动态 `import()`（Vue Router 与 React Router 都支持懒加载），这是收益最大也最安全的一刀。
4. 优化手段二，组件级与交互级分割：弹窗、富文本编辑器、图表、地图、Excel 导出这类「打开才用」的能力延迟到触发时再加载；配合骨架屏或加载态，避免点击后长时间无反馈。
5. 优化手段三，预取配合：对高概率跳转的下一个路由用 `prefetch` 或框架的预加载能力提前拉取，但别把带宽抢给首屏。
6. 预期收益与代价：首屏 JS 与请求数下降，LCP 改善；代价是拆得太碎会出现「点一下等一次」的体验回退，需要配合预加载与加载态，且要控制 chunk 数量避免请求瀑布。

**追问与易错点**：

- 追问：拆到每个组件一个 chunk 好不好？答：不好。请求瀑布和重复的公共依赖会抵消收益，公共依赖要用 `splitChunks` 或 `manualChunks` 抽成稳定 vendor。
- 陷阱：动态 `import()` 只写了没配 loading 与 error 处理，弱网下用户以为按钮坏了。
- 追问：怎么判断某个库该不该进首屏？答：看首屏渲染是否真的依赖它；不依赖就走懒加载，依赖则考虑换更轻的实现或服务端渲染。

### Q8 图片怎么优化？格式、压缩、加载策略分别怎么选？

**考察点**：考图片这一最大资源项的完整处理链路，图片往往是 LCP 的元凶。

**参考答案**：

> **一句话结论**：图片优化的四步是「选对格式、给对尺寸、控制优先级、延迟非关键图片」，其中首屏大图的优先级最高，绝不能懒加载。

1. 问题现象：首屏大图几百 KB 到几 MB，LCP 一直不达标，移动端弱网下更明显。
2. 定位手段：Performance 面板看 LCP 元素是谁，Network 面板看该图片的实际传输体积与显示尺寸是否匹配。
3. 格式与压缩：WebP 相比 JPEG 通常能小两三成，AVIF 更小但编码与解码更慢、兼容性更弱，实践中用 `picture` + `source` 做降级；有损质量一般压在 70-80，配合 CDN 图片服务（缩放、裁切、格式转换）自动产出多规格。
4. 尺寸与响应式：用 `srcset` + `sizes` 让浏览器按 DPR 与视口选图，避免下载 2000px 图显示在 300px 容器里。
5. 加载策略：首屏 LCP 图用 `fetchpriority="high"` 并 `preload`（响应式图用 `imagesrcset`/`imagesizes`）；首屏之外的图用 `loading="lazy"` + `decoding="async"`；宽高或 `aspect-ratio` 必须写，防止 CLS。
6. 预期收益与代价：LCP 改善明显，流量与内存占用同步下降；代价是需要图片处理服务或构建期压缩流程，AVIF 的编码耗时与兼容降级要额外维护。

**追问与易错点**：

- 追问：为什么不能给 LCP 图片加 `loading="lazy"`？答：懒加载会推迟它的发现与请求时机，直接把 LCP 推后，这是很常见的自伤式优化。
- 陷阱：只换 WebP 不改质量与尺寸，体积降幅有限，因为主要浪费在尺寸上。
- 陷阱：用 CSS 把大图缩小显示，流量与解码内存照样付出。

### Q9 防抖节流和 requestAnimationFrame 分片分别在解决什么问题？

**考察点**：考高频事件治理与主线程让出，属于最容易在项目里立刻见效的一类优化。

**参考答案**：

> **一句话结论**：防抖（Debounce）把连续触发的调用收敛到停止后一次，节流（Throttle）保证单位时间内最多执行一次，两者都是「少干活」；requestAnimationFrame 分片是把大任务切成每帧一小段，属于「分开干」。

1. 防抖适用：搜索输入、窗口 resize 结束后重算、表单实时校验，侧重「等用户停下来再做」。
2. 节流适用：滚动进度计算、拖拽跟随、mousemove 类高频事件，侧重「匀速采样」。
3. rAF 分片适用：一次渲染十万行数据、批量 DOM 操作，按每帧约 10ms 的预算切片，每片结束后主动让出，避免产生长任务拖垮 INP。
4. 分片要点：用时间戳判断本帧是否超预算，超出就 `requestAnimationFrame` 调度下一片；滚动监听加 `passive: true`，避免滚动被同步布局阻塞。

```js
function chunkedRun(items, work, budget = 10) {
  let i = 0;
  const step = (t0) => {
    while (i < items.length && performance.now() - t0 < budget) work(items[i++]);
    if (i < items.length) requestAnimationFrame(step); // 本帧超预算，下一帧继续
  };
  requestAnimationFrame(step);
}
```

**追问与易错点**：

- 追问：防抖和节流怎么选？答：只关心最终结果的用防抖，需要过程反馈（滚动位置、进度条）的用节流。
- 陷阱：给滚动监听用防抖会让滚动反馈一顿一顿，应该用节流或 rAF。
- 追问：分片和 Web Worker 怎么选？答：分片适合必须操作 DOM 或依赖主线程上下文的工作，纯计算与数据处理优先放 Worker。

### Q10 前端性能优化有哪些常见反模式？

**考察点**：考判断力与踩坑经验。能说出「过早优化、只在开发机测、盲目加缓存」这三类并给出正确做法，才算过关。

**参考答案**：

> **一句话结论**：最常见的三类反模式是没度量就优化、只在开发机上验证、把缓存当成万能药；它们的共同点是用手段代替了目标。

1. 过早优化：在没有指标与火焰图证据时就重构、上微前端、换构建工具，风险大收益不可验证。正确做法是先度量、定位到瓶颈再动手。
2. 只在开发机测：开发机是高性能处理器加高速网络，真实用户是中低端安卓机加 4G。正确做法是用 DevTools 做 CPU 降速与网络限速，并在真机与线上灰度数据上验证。
3. 盲目加缓存：给 HTML 或个性化接口加长缓存，导致发版不生效、数据陈旧甚至串号。正确做法是先设计缓存层级与失效策略，静态资源用内容哈希长缓存，HTML 与接口慎用或短缓存。
4. 只刷分数不改体验：为了 Lighthouse 分数给所有图片加懒加载、把首屏内容挪出视口，分数上涨但 RUM 没变化。优化目标是用户指标，不是分数。
5. 把技术手段当目的：无脑 `preload` 一切、无脑加 `will-change`、无脑开合成层，都会抢带宽或吃显存，反而变慢。

**追问与易错点**：

- 追问：怎么证明某次优化真的有效？答：同口径前后对比 + 分维度灰度，并观察至少一个完整发布周期的 P75 趋势。
- 陷阱：说「性能优化就是尽量减少请求数」。HTTP/2 下并发成本低，合并反而让缓存粒度变粗，请求数与体积要一起权衡。
- 陷阱：把骨架屏当成万能优化。它改善的是感知等待，不改善 LCP 指标本身，也不是白屏的遮羞布。

### Q11 Performance API 和 PerformanceObserver 怎么用？能拿到哪些数据？

**考察点**：考对浏览器性能数据来源的掌握，是自建监控的地基。

**参考答案**：

> **一句话结论**：`performance` 对象提供时间原点与各类性能条目，PerformanceObserver 是异步订阅这些条目的标准方式，`buffered: true` 能补拿观察者创建之前的记录。

1. 基础时间：`performance.now()` 是高精度单调时钟，`performance.timeOrigin` 是页面时间线起点，二者配合可换算成绝对时间戳用于上报。
2. 条目查询：`getEntries()`、`getEntriesByType()`、`getEntriesByName()`，可拿到 `navigation`（TTFB、DOM 各阶段）、`resource`（每个资源的分段耗时）、`paint`（FP/FCP）等。
3. 观察者订阅：`new PerformanceObserver(cb).observe({ type: 'largest-contentful-paint', buffered: true })`，常见类型有 `largest-contentful-paint`、`layout-shift`、`event`、`longtask`、`first-input`、`navigation`、`resource`、`mark`、`measure`。
4. 关键字段：LCP 条目的 `element`/`url`/`renderTime`、布局偏移条目的 `value`/`hadRecentInput`/`sources`、事件条目的 `processingStart`/`startTime`（用于算 INP 三段）、`resource` 的 `transferSize`/`encodedBodySize`（用于算体积与缓存命中）。
5. 兼容与限制：`supportedEntryTypes` 可做能力检测；Long Tasks API 在部分浏览器（如 Firefox）不可用，`layout-shift` 只在有布局偏移的引擎里有，报告缺失时应视为「无数据」而不是「零问题」。

**追问与易错点**：

- 追问：CLS 为什么要在页面隐藏时才算最终值？答：布局偏移在页面整个生命周期都可能发生，官方建议在 `visibilitychange` 变为 hidden 时上报最终 CLS。
- 陷阱：`layout-shift` 条目里 `hadRecentInput` 为 true 的必须剔除，用户自己操作引起的变化不算 CLS。
- 追问：`transferSize` 为 0 意味着什么？答：资源来自缓存或跨域未允许 Timing-Allow-Origin，不能当成体积为 0。

### Q12 Lighthouse 和 DevTools Performance 面板分别怎么看？火焰图要看什么？

**考察点**：考工具使用与读图能力，这是「定位」环节的核心技能。答出两者分工、火焰图读法、强制同步布局的识别，才算过关。

**参考答案**：

> **一句话结论**：Lighthouse 用来做整体体检与量化打分（实验室数据），Performance 面板用来逐个瓶颈定位（火焰图）；前者告诉你哪里疼，后者告诉你为什么疼。

1. 分工：Lighthouse 给 LCP、TBT、CLS 分数与优化建议清单，可在 CI 里跑；Performance 面板给出逐帧时间线，能精确到函数。两者都不能替代真实用户数据。
2. Lighthouse 注意点：默认移动端模拟 4 倍 CPU 降速与慢速 4G，看的是模拟值；分数受环境影响大，不要跨环境比分数，比指标趋势。
3. 火焰图读法：横轴是时间，纵轴是调用栈，块越宽代表占用越久；顶部灰色是浏览器内部工作，主线程被长任务占满时会出现又宽又长的块，直接对应 INP 与 TBT 变差。
4. 强制同步布局识别：在帧里看到 Layout 被反复触发，或在 Performance 面板里看到红色三角警告与 `Forced reflow` 提示，说明在写 DOM 后立刻读了布局属性（如 `offsetWidth`、`getBoundingClientRect`）。
5. 配合面板：Network 看关键请求链与瀑布，Coverage 看未使用 JS/CSS，Rendering 勾选 Paint flashing 与 Layout Shift Regions 直观看到重绘与偏移，Memory 看堆增长。

**追问与易错点**：

- 追问：「强制同步布局」怎么改？答：读写分离，先把所有布局属性读完缓存，再统一写 DOM；需要穿插时用 rAF 或批处理库把读写排队。
- 陷阱：只盯总耗时最短的帧，而忽略了「长任务」。性能问题的关键是单个任务是否超 50ms，而不是一帧总长。
- 追问：本地 Lighthouse 分数 100 就没事了吗？答：不一定，本地环境、缓存与内容是理想化的，必须看线上 RUM 的 P75。

### Q13 web-vitals 库怎么用？数据怎么上报和聚合？

**考察点**：考监控落地能力，「会测」比「会优化」更稀缺。

**参考答案**：

> **一句话结论**：用 `web-vitals` 订阅 LCP、INP、CLS、FCP、TTFB，在页面隐藏或指标就绪时通过 `sendBeacon` 上报，后端按用户与页面聚合出 P75 分位数。

1. 采集：v3 之后的 API 是 `onLCP`、`onINP`、`onCLS`、`onFCP`、`onTTFB`，内置了官方口径的计算逻辑（如 CLS 的会话窗口与 INP 的最差交互），不要自己手算。
2. 上报时机：LCP 与 CLS 在页面隐藏时取最终值；TTFB、FCP 在条目产生后即可上报；用 `navigator.sendBeacon` 或 `fetch(..., { keepalive: true })` 保证卸载时也能发出。
3. 维度：每条数据要带路由、页面版本、设备类型、网络类型（Network Information API）、地区、是否首次访问，否则拿到了也不知道怎么改。
4. 采样与聚合：全量上报成本高，可按用户或会话采样；后端不要算平均值，按天/版本算 P75、P95，并按维度拆开看。
5. 归因：`web-vitals` 的 attribution 构建可给出 LCP 是哪个元素、INP 是哪次交互与哪个事件，配合 `performance.mark` 能把指标落到具体代码。

```js
import { onLCP, onINP, onCLS } from 'web-vitals';

const send = (metric) => {
  const body = JSON.stringify({
    name: metric.name, value: metric.value, id: metric.id,
    route: location.pathname, nav: metric.navigationType,
  });
  navigator.sendBeacon('/rum', body);
};
[onLCP, onINP, onCLS].forEach((fn) => fn(send));
```

**追问与易错点**：

- 追问：上报数据量和精度怎么平衡？答：先降采样再降维度，别为了省流量把路由维度砍掉，否则数据不可用。
- 陷阱：在 `beforeunload` 里发普通异步请求，容易被浏览器取消，必须用 `sendBeacon` 或 `keepalive`。
- 追问：`web-vitals` 的值和 CrUX 对不上正常吗？答：正常。CrUX 是全体 Chrome 用户按周聚合的 P75，采样范围、时间窗与设备分布都不同，看趋势一致性即可。

### Q14 LCP 慢怎么优化？从哪几段下手？

**考察点**：考首屏加载的瓶颈拆解，LCP 是面试里最高频的性能问题。

**参考答案**：

> **一句话结论**：LCP 的耗时可以拆成四段——TTFB、资源加载延迟、资源加载时长、元素渲染延迟，逐段用工具定位，改掉最长的那一段。

1. 问题现象：首屏大面积白屏或图片迟到，LCP 在 4G 与中端机上远超 2.5s。
2. 定位手段：DevTools 里选中 LCP 条目看是文字还是图片；看 Network 瀑布里 LCP 资源的发现时间与下载时间；Performance 面板看渲染是否被长任务阻塞。
3. TTFB 段：上 CDN、做好缓存与预压缩、服务端渲染或边缘渲染、减少串行接口与回源次数。
4. 资源段：LCP 图片用 `preload` + `fetchpriority="high"`，转 WebP/AVIF 并给对尺寸；关键 CSS 内联，阻塞脚本用 `defer`，字体子集化并 `preload`。
5. 渲染段：减少首屏水合工作量、避免让大组件树同步渲染、把非关键工作切分或延后，别让长任务卡住首帧内容绘制。
6. 预期收益与代价：四段中改掉最长的一段收益最大；代价是 SSR/边缘渲染带来基建与运维复杂度，内联关键 CSS 会让 HTML 变大并影响缓存粒度。

**追问与易错点**：

- 追问：LCP 元素是文字时怎么优化？答：文字 LCP 主要受 TTFB 与字体阻塞影响，优先解决服务端响应和 `font-display`，而不是去压图片。
- 陷阱：给 LCP 图加懒加载或放在轮播第二帧。元素发现不了，后面做什么都白搭。
- 陷阱：以为把 LCP 元素挪出视口就算优化。指标口径只统计视口内元素，属于自欺。

### Q15 CLS 是怎么产生的？怎么修？

**考察点**：考布局偏移的成因与修复手段，重点在「为什么会抖」而不是背工具。

**参考答案**：

> **一句话结论**：CLS 来自元素在渲染后位置被改变，主要成因是「没预留空间」和「渲染后动态插入内容」，修复靠预留尺寸、约束插入位置、用 transform 做动画。

1. 问题现象：图片加载完把下方文字顶下去、广告位撑开、字体替换导致文字重排、接口返回后才插入提示条，用户正在点击时页面跳了。
2. 定位手段：Performance 面板勾选 Layout Shift Regions 看哪里闪蓝框，或订阅 `layout-shift` 条目读 `sources`，直接定位到偏移元素。
3. 修复一，预留空间：图片与视频写 `width`/`height` 或 `aspect-ratio`，iframe 给固定高度，字体用 `font-display: optional` 或 `size-adjust` 减少替换落差。
4. 修复二，约束动态内容：把新插入的提示条、错误信息放在不会推动已有内容的位置（如覆盖层、预留给它的容器），或先用固定高度占位。
5. 修复三，动画方式：位移与缩放只用 `transform` 与 `opacity`，不要动画 `top`/`left`/`width`/`height`。
6. 预期收益与代价：CLS 通常能压到 0.1 以内；代价是预留空间需要设计稿与内容长度配合，`font-display: optional` 可能让用户看不到自定义字体。

**追问与易错点**：

- 追问：用户自己点击导致的偏移算不算？答：不算。`hadRecentInput` 为 true 的条目会被剔除，但「等待接口 500ms 后才插入内容」在统计上仍可能算入，所以别赌这 500ms。
- 陷阱：只看首屏 CLS，忽略滚动后才出现的偏移。CLS 统计整个生命周期，长页面尤其要看滚动过程。
- 陷阱：用绝对定位把内容挪走以规避偏移，结果小屏或超长文案下重叠，属于把问题藏起来。

### Q16 INP 差是哪里的问题？长任务怎么治理？

**考察点**：考交互延迟拆解与主线程调度，这是 2024 年后最容易被追问的指标。

**参考答案**：

> **一句话结论**：INP 由输入延迟、事件处理时间、呈现延迟三段组成，根因通常是主线程被长任务占满或渲染量过大，治理手段是拆任务、减渲染、让出主线程。

1. 问题现象：点击按钮要等一两秒才有反应，输入框打字卡顿，滚动时点击不灵。
2. 定位手段：Performance 面板看长任务（超过 50ms 的任务）与 `event` 条目的三段耗时；Lighthouse 的 TBT 可视为 INP 的实验室代理指标；`event` 观察者能定位到具体元素与事件类型。
3. 拆任务：把大循环、大 JSON 解析、复杂计算切成小块，用 `setTimeout`、`requestAnimationFrame`、`scheduler.yield`（可用时）或 `isInputPending` 主动让出主线程，让输入事件插进来。
4. 减渲染：大数据列表虚拟化、减少首屏水合（hydration）的组件量、避免在事件回调里做同步布局读写、合并连续的 DOM 写入。
5. 降优先级：非关键任务（埋点、预取）用低优先级调度或 `requestIdleCallback`，别和用户交互抢主线程。
6. 预期收益与代价：长任务被切开后输入延迟与呈现延迟都会下降；代价是拆分增加代码复杂度，过度让出会拉长总耗时，需要按 RAIL 的 50ms 预算权衡。

**追问与易错点**：

- 追问：TBT 和 INP 是什么关系？答：TBT 是实验室里主线程阻塞总量，与 INP 强相关但不是同一个指标，TBT 好不代表 INP 一定好（还要看渲染与事件回调本身）。
- 陷阱：只优化首次交互。INP 统计最差的那次交互，滚动后的一次笨重点击就可能把指标拖垮。
- 陷阱：把长任务都塞进 `setTimeout(fn, 0)` 就认为拆完了，其实回调仍是一个宏任务（只有嵌套超过 5 层才会被钳到 4ms），真正的关键在于单任务不超 50ms。

### Q17 gzip 和 brotli 怎么选？压缩还有哪些坑？

**考察点**：考传输层压缩的实际配置与边界，属于低成本高收益项。

**参考答案**：

> **一句话结论**：文本资源一律启用压缩，优先 Brotli（同级别比 gzip 通常再小一到两成），对老客户端保留 gzip 兜底；已压缩的二进制格式不要再压。

1. 动态压缩：Brotli 用较低级别（约 4-5）避免占用过多 CPU；静态资源（JS/CSS/HTML）在构建期预压缩成 `.br` 与 `.gz`，Nginx 配 `brotli_static`、`gzip_static` 直接吐文件，运行时零成本。
2. 内容协商：必须带 `Vary: Accept-Encoding`，否则 CDN 或代理可能把 br 版本发给不支持它的客户端，直接白屏。
3. 压什么：HTML、CSS、JS、JSON、SVG、字体里的 TTF/OTF 可压；webp/avif/png/jpg/mp4/woff2 已压缩，压了浪费 CPU 还可能变大。
4. 阈值：太小的资源（1KB 以下）压缩收益不够抵消头部开销，可以设最小体积阈值跳过。
5. 新变化：Chrome 从 123 起支持 `Content-Encoding: zstd`，压缩率与速度介于 brotli 与 gzip 之间，可按 CDN 支持情况作为补充，但主流仍以 br + gzip 兜底。

**追问与易错点**：

- 追问：为什么预压缩比动态压缩好？答：高级别 Brotli（如 11）压缩率高但很慢，放在请求链路里会拖高 TTFB，构建期做一次最划算。
- 陷阱：只在 Nginx 配了 gzip，却把 HTML 也设成强缓存。压缩与缓存是两件事，HTML 的长缓存会引发发版不生效。
- 追问：怎么确认线上真的生效了？答：看响应头 `content-encoding` 与 `content-length`，再对比 `transferSize` 与解码后体积。

### Q18 HTTP/2、CDN 和缓存怎么配合？请求数和体积到底怎么权衡？

**考察点**：考网络层优化的整体判断，重点是「不要机械地减少请求数」。

**参考答案**：

> **一句话结论**：HTTP/2 的多路复用让单域名并发不再是瓶颈，所以优化重点从「减少请求数」转向「控制关键路径长度与体积」；CDN 负责把内容放到离用户最近的地方，缓存负责让第二次访问不再下载。

1. HTTP/2 影响：一个连接多路复用、头部压缩（HPACK）、不再需要域名分片与雪碧图；服务端推送已被主流浏览器移除，改用 `preload` 与 `103 Early Hints` 提升关键资源发现速度；HTTP/3 基于 QUIC，进一步消除 TCP 层队头阻塞并支持 0-RTT。
2. CDN 影响：静态资源就近分发、边缘缓存与回源控制、图片处理、边缘渲染。要关注缓存命中率、回源量与预热策略，别让 CDN 变成一层透明的转发。
3. 请求数与体积的取舍：HTTP/1.1 时代合并是为了绕开每域名 6 个连接限制；HTTP/2 下过度合并会让缓存粒度变粗（改一行代码整包失效），过度拆分会产生依赖瀑布。判断标准是「按变更频率拆分、按首屏必需性排序」。
4. 缓存策略：带内容哈希的静态资源用 `Cache-Control: public, max-age=31536000, immutable` 长缓存；HTML 用短缓存或 `no-cache` 以便发版生效；接口按数据时效性选择，配合 `stale-while-revalidate` 兼顾新鲜度与速度。
5. 预期收益与代价：CDN + 正确缓存通常能把重复访问的 TTFB 与资源耗时压到很低；代价是缓存失效与灰度策略更复杂，发版流程必须配套刷新 CDN 与回滚方案。

**追问与易错点**：

- 追问：HTTP/2 下还需要雪碧图吗？答：基本不需要，小图合并反而拖慢关键 CSS 并让缓存粒度变差；但图标字体与内联 SVG 的取舍仍要看场景。
- 陷阱：给 `index.html` 配一年强缓存又用文件名不变的 JS，导致线上出现新旧资源不匹配的诡异问题。
- 追问：为什么灰度发布容易踩缓存坑？答：新旧版本资源并存，HTML 指向的哈希必须与 CDN 上的文件一致，需要按版本化目录或原子发布来解决。

### Q19 preload、prefetch、preconnect、dns-prefetch 有什么区别？怎么用才不反噬？

**考察点**：考资源提示的语义与优先级，用错方向会直接拖慢首屏。

**参考答案**：

> **一句话结论**：它们都在提前做网络工作，区别在于「提前多少」和「为谁准备」——preconnect 提前建连，dns-prefetch 只提前解析，preload 预取当前页关键资源，prefetch 预取下一次导航要用的资源。

| 提示 | 提前做什么 | 典型场景 | 代价 |
| --- | --- | --- | --- |
| dns-prefetch | 只做 DNS 解析 | 大量第三方域名的兜底 | 很小 |
| preconnect | DNS + TCP + TLS | 确定要用的第三方源 | 占连接与 CPU，不宜过多 |
| preload | 以高优先级下载当前页资源 | 首屏字体、LCP 图片、关键 CSS | 抢带宽，用错会拖慢其他关键资源 |
| prefetch | 空闲时低优先级下载 | 下一个路由、下一屏 | 耗尽流量与带宽，可能白下 |
| modulepreload | 预加载模块及其依赖图 | ESM 入口 | 配置错误会重复下载 |

1. 使用要点：`preload` 必须写 `as` 才能正确参与优先级与缓存复用；字体还要加 `crossorigin`，否则会重复下载两次。
2. 数量控制：`preconnect` 一般只保留少量最关键的第三方源，不用的要尽早断开；`preload` 只给首屏关键资源，多了等于没有优先级。
3. 动态注入：真正由 JS 决定的关键资源（如路由确定后才知的大图）可用 `document.head.appendChild` 动态 preload，但要注意注入时机不能太晚。
4. 验证：在 Network 面板看提示项的发起时间与实际使用时间，若下载完很久才被使用，说明这条提示是浪费。

**追问与易错点**：

- 追问：preload 的资源没用上会怎样？答：浏览器会警告并在一定时间后丢弃，期间白占了带宽与优先级，可能反而推迟 LCP。
- 陷阱：把 `prefetch` 用在首屏资源上。`prefetch` 优先级低，救不了首屏，还会与关键资源争抢。
- 陷阱：漏写 `crossorigin` 导致字体被下载两次，这是非常常见的一处浪费。

### Q20 怎么减少重排重绘？content-visibility、contain、will-change 怎么用？

**考察点**：考渲染层优化的手段与副作用认知，尤其是「提升是有限资源」。

**参考答案**：

> **一句话结论**：重排重绘的治理原则是「少触发、批处理、提升到合成层」，而 content-visibility、contain、will-change 都是工具，用对省时间，用错吃内存。

1. 问题现象：滚动或输入时掉帧，Performance 面板里 Layout 与 Recalculate Style 频繁出现，伴随大量 Paint。
2. 定位手段：Rendering 里打开 Paint flashing 看重绘区域，打开 Frame Rendering Stats 看掉帧，Performance 里看 Layout 是否被读操作反复触发（强制同步布局）。
3. 减少触发：批量读写分离；用 DocumentFragment 或先 `display: none` 再改样式，最后一次性恢复；动画只用 `transform` 与 `opacity`；避免用 JS 频繁改 `class` 触发整棵子树样式重算。
4. content-visibility 与 contain：`content-visibility: auto` 让屏幕外的子树跳过渲染，必须配 `contain-intrinsic-size` 给出估算高度，否则滚动条会跳动并引发 CLS；`contain: layout paint size style` 把元素的布局与绘制影响限制在自身，减少浏览器的工作范围，对组件化列表很有效，副作用是要自己保证尺寸稳定。
5. will-change 与合成层：`will-change: transform` 会提前提升为合成层，能避免动画首帧闪动，但层过多会占显存、在移动端引发掉帧甚至崩溃；只在动画开始前加、结束后移除，或改用 `translateZ(0)` 临时提升。
6. 预期收益与代价：掉帧与长任务下降，滚动更顺。代价是内存占用上升，`contain` 与 `content-visibility` 对尺寸与无障碍有一些隐含约束，需要逐页验证。

**追问与易错点**：

- 追问：为什么说「合成层不是越多越好」？答：每层都要占用显存与合成开销，移动端层数一多更容易爆内存，反而导致掉帧。
- 陷阱：给页面上所有列表项都加 `will-change: transform`，本想提性能，结果是层爆炸。
- 追问：`contain: size` 为什么危险？答：它告诉浏览器这个元素的尺寸不受子元素影响，如果实际布局依赖子元素，就会出现错位与截断。

### Q21 虚拟列表的原理是什么？自己实现要注意什么？

**考察点**：考长列表渲染的核心方案，能否说清原理并指出落地难点。

**参考答案**：

> **一句话结论**：虚拟列表只渲染可视区域（加少量缓冲区）的列表项，用占位高度或 transform 偏移把可视项放在正确位置，从而把 DOM 数量与渲染成本从「数据量」解耦为「视口大小」。

1. 问题现象：上千行列表一次性渲染，首屏卡死数秒，滚动掉帧，内存居高不下，DOM 节点数触发 Lighthouse 警告（其参考线约为总节点数 1400、层级 32、单节点子元素 60）。
2. 定位手段：Performance 面板看首次渲染的长任务与 Layout 次数，Elements 面板看 DOM 节点总数，Memory 面板看渲染后堆占用。
3. 基本实现：监听滚动计算 `startIndex = floor(scrollTop / itemHeight)`，`endIndex = startIndex + ceil(viewportHeight / itemHeight) + buffer`；容器用一个总高度的占位元素撑开滚动条，可视项用 `transform: translateY(offset)` 定位。
4. 落地难点：不定高需要先估算再实测并缓存修正值，滚动中会在快速滚动时出现白屏（靠 overscan 与骨架占位缓解）；滚动监听用 `passive: true` 并在 rAF 中计算，避免滚动中触发同步布局。
5. 取舍：固定高度最简单，动态高度、分组、吸顶表头、键盘与无障碍（`aria-setsize`/`aria-posinset`）都会显著增加复杂度；成熟方案如 vue-virtual-scroller、react-window、TanStack Virtual 能省掉大量边界处理。
6. 预期收益与代价：DOM 数量从数据量级降到几十，首屏与滚动指标大幅改善；代价是打印、Ctrl+F 查找、无障碍与截图类需求会受影响，需要额外兜底。

**追问与易错点**：

- 追问：为什么自研虚拟列表常在快速滚动时白屏？答：滚动事件与渲染不同步，缓冲不够或渲染本身耗时导致本帧来不及，需要增大 overscan 并让单帧渲染量可控。
- 陷阱：把总高度写死导致滚动条与内容不符，最后一屏滚不到底。
- 追问：虚拟列表能解决数据计算慢吗？答：不能。渲染少了但排序、过滤、聚合仍然在主线程，重计算要放 Web Worker 或做分页。

### Q22 动画优化：CSS 动画和 JS 动画怎么选？FLIP 是什么？

**考察点**：考动画性能的判断，重点是「动画跑在哪条线程上」。

**参考答案**：

> **一句话结论**：能用 CSS 声明式动画且只改 `transform`/`opacity` 时优先 CSS（交给合成器，不占主线程）；需要按数据动态控制时用 JS，但要跑在 rAF 里；布局变化的动画用 FLIP 把布局成本转成合成成本。

| 维度 | CSS 动画 | JS 动画 |
| --- | --- | --- |
| 执行线程 | 合成器线程（改 transform/opacity 时） | 主线程（rAF） |
| 主线程压力 | 低 | 高，易被长任务打断 |
| 控制能力 | 弱，靠类名与事件 | 强，可动态计算与中断 |
| 适用 | 悬停、加载、入场退场 | 拖拽、跟随、物理效果 |

1. 属性选择：只动画 `transform` 与 `opacity` 可以跳过布局与绘制，直接进合成阶段；动画 `width`、`height`、`top`、`left`、`box-shadow` 会触发重排或重绘。
2. JS 动画要点：用 `requestAnimationFrame` 而不是 `setInterval`，每帧只做一次样式写入，读取与写入分离，避免强制同步布局。
3. FLIP（First-Last-Invert-Play）：先记录元素初始位置（First），改变布局后读取最终位置（Last），用 `transform` 把它「反推」回初始位置（Invert），再在下一帧把 transform 过渡到 0（Play）。这样布局只发生一次，动画交给合成器。
4. 合成提示：需要提前提升时可临时加 `will-change: transform`，动画结束移除，避免长期占显存。
5. 预期收益与代价：掉帧明显减少，低端机收益更大；代价是 FLIP 需要额外一次布局读取，频繁触发时要合并计算，且 CSS 动画的中断与同步控制比 JS 弱。

**追问与易错点**：

- 追问：为什么 `transform` 动画比 `left` 快？答：`left` 改变几何属性需要重新布局与绘制，`transform` 只影响合成阶段的图层变换。
- 陷阱：用 `setInterval(16)` 做动画，掉帧且与刷新率不同步，还会在后台标签页被节流。
- 追问：什么时候必须用 JS 动画？答：需要根据滚动位置、鼠标轨迹或数据实时计算插值时，CSS 无法表达，只能用 rAF 驱动。

### Q23 首屏优化：CSR、SSR、SSG、预渲染、流式渲染怎么选？水合怎么优化？

**考察点**：考渲染架构与首屏体验的关系，能从指标与成本两侧权衡。

**参考答案**：

> **一句话结论**：渲染方式的选择本质是在「首屏内容出现时间、交互就绪时间、基建与运维成本」之间取舍：内容型页面用 SSG/SSR，交互型后台可用 CSR，首屏与交互都要好则用 SSR 配合流式渲染与更轻的水合。

1. 方式对比：CSR 首屏要等 JS 下载执行后才有内容，LCP 与白屏风险最大，但基建最简；SSR 服务端直接输出 HTML，LCP 明显改善，但 TTFB 受服务端渲染耗时影响；SSG 在构建期生成静态页，TTFB 最优，适合内容变更不频繁；预渲染（Prerender）在构建期把指定路由渲染成静态 HTML，适合少量营销页。
2. 流式渲染：服务端边渲染边发送（如 Node 的 `renderToPipeableStream`、`renderToReadableStream`），让浏览器更早拿到并解析首屏 HTML，缩短 FCP/LCP，同时把慢数据用 Suspense/异步边界推后。
3. 骨架屏与关键 CSS：骨架屏改善感知等待但不改变 LCP 口径；关键 CSS 内联进 `<head>`，其余样式异步加载，避免 CSSOM 阻塞首帧；脚本用 `defer` 或 `async`，不要让首屏 HTML 等 JS。
4. 水合（Hydration）优化：水合是「HTML 已可见但不可交互」的窗口期，成本来自组件树遍历与事件绑定。手段包括缩小客户端组件边界（服务端组件、`use client` 粒度）、选择性水合（React 18 的 Suspense 优先级水合）、岛屿架构（只水合交互岛屿，如 Astro）、以及延迟非关键组件的水合。
5. 预期收益与代价：SSR/SSG 通常能显著改善 LCP 与 FCP；代价是服务端算力、缓存与降级方案、SSR 与客户端渲染不一致（hydration mismatch）的排查成本，以及 SEO 之外的运维复杂度。

**追问与易错点**：

- 追问：SSR 之后 TTFB 变慢了怎么办？答：TTFB 与 LCP 要一起看，若服务端渲染本身慢，可用缓存、边缘渲染、流式返回先吐首屏骨架，而不是回退到 CSR。
- 陷阱：把「首屏有 HTML」当成优化完成。水合不结束，点击没反应，INP 会很差。
- 陷阱：SSR 里直接使用浏览器 API（window、document）导致报错或降级为客户端渲染，必须做环境判断或在生命周期后再用。

### Q24 一个页面首屏 3s，怎么降到 1s？给出可落地的清单

**考察点**：考系统化落地能力与优先级排序，是本章的压轴实战题。

**参考答案**：

> **一句话结论**：先把 3s 拆成「服务端响应 + 资源加载 + 渲染」三段各自量化，再按投入产出比逐段砍；没有定位就动手，等于把 3s 变成 3.2s。

1. 第一步，量化并定位三段占比：先定指标口径（是 LCP 还是 FCP、什么设备与网络、取 P75），再用 RUM 与 Lighthouse 拿基线；TTFB 段看服务端与网络（首个 HTML 字节时间、回源与缓存命中），资源段看关键路径长度与体积（瀑布图、Coverage），渲染段看长任务与首屏 DOM 规模（Performance 火焰图）。
2. 第二步，TTFB 段：上 CDN 与边缘缓存、开静态资源预压缩、减少串行接口与回源、必要时用 SSR 或边缘渲染、给接口加缓存（注意数据时效性）。
3. 第三步，资源段：路由级代码分割只加载首屏必需 chunk、LCP 图转 WebP/AVIF 并给对尺寸且高优先级、字体子集化加 `preload`、非关键第三方脚本（地图、客服、埋点）延后加载。
4. 第四步，渲染段：内联关键 CSS、脚本 `defer`、减少首屏组件树与水合量、把大数据渲染放进虚拟列表、把重计算移到 Worker、长任务切片。
5. 第五步，验证与守门：用相同条件复测，上线后按版本看 P75 趋势，并把 bundle 体积、LCP 阈值写进性能预算与 CI 卡口，防止回退。
6. 预期收益与代价：每一段都可能有可观收益，具体幅度取决于基线分布，必须先测才能承诺；代价是流程与基建投入，以及缓存与懒加载带来的数据一致性、首屏可用性权衡。

**追问与易错点**：

- 追问：时间不够，只做一件事选哪个？答：先看基线哪一段占比最大；若不确定，先做「路由级代码分割 + LCP 图优化 + CDN 缓存」这三件低风险高收益的事。
- 陷阱：把第三方脚本全删了换分数，业务埋点与转化受损，要按业务价值排序而不是一刀切。
- 陷阱：只在本地和开发环境验证，上线后真实用户没变化。必须用 RUM 的 P75 收尾。

### Q25 长列表和大数据表格怎么优化？

**考察点**：考复杂场景的工程解法，重点是分场景判断而不是套一个万能方案。

**参考答案**：

> **一句话结论**：长列表靠虚拟滚动控制 DOM 数量，大数据表格还要额外解决「重计算」与「列渲染」两件事：计算下放给 Worker，列按需渲染并冻结表头。

1. 问题现象：几万行数据一次渲染导致页面假死，排序筛选时尤其明显；横向滚动列多时更卡。
2. 定位手段：Performance 火焰图区分是渲染耗时还是数据计算耗时；Elements 看 DOM 节点数；Memory 看数据是否被长期持有。
3. 渲染侧：虚拟滚动（行与列都可虚拟化），表头用 `position: sticky` 冻结，固定列用绝对定位或独立滚动容器同步偏移。
4. 计算侧：排序、过滤、聚合、格式化放到 Web Worker（大数组用 TypedArray 与 Transferable 减少拷贝），主线程只做渲染；导出 Excel 等重活同样放 Worker。
5. 交互侧：搜索输入防抖，滚动监听 passive，滚动中的批量渲染用 rAF 分片，避免在滚动里读布局属性。
6. 取舍：虚拟滚动牺牲了打印、查找与无障碍体验，超大表格也可以直接分页或服务端分页，用产品交互换性能，往往比自己硬扛更划算。

**追问与易错点**：

- 追问：为什么虚拟列表做完还是卡？答：往往瓶颈已经从 DOM 转移到数据处理，检查是否还在主线程对大数组做 `sort`/`filter`。
- 陷阱：把数据全量存在组件状态里并做深监听，深层响应式代理本身就很贵，应该浅层化或标记为不可变。
- 追问：DOM 节点数有没有参考线？答：Lighthouse 会对总节点数过多、嵌套过深给出警示，其参考线约为总节点 1400、深度 32、单节点子元素 60，超过就该考虑虚拟化。

### Q26 运行时能做什么优化？Web Worker 和 OffscreenCanvas 用在哪？

**考察点**：考「加载完成后」的持续性能，很多人只会优化加载不会优化运行。

**参考答案**：

> **一句话结论**：运行时优化的主线是「少算、算一次就缓存、能不阻塞就不阻塞、能搬走就搬走」——把纯计算搬进 Worker，把 Canvas 绘制搬进 OffscreenCanvas，把重复计算变成记忆化。

1. 少算：避免在渲染函数或 `computed`/`useMemo` 里做重计算；列表项的格式化、正则、深拷贝都要评估成本；大数据用 TypedArray 而不是对象数组。
2. 缓存：用记忆化（Memoization）缓存昂贵计算结果，并给缓存设上限或用 WeakMap 让对象可回收；接口层做请求去重与结果缓存，但要考虑数据时效性。
3. 懒执行：路由、弹窗、图表、地图、Excel 导出、埋点 SDK 都延迟到真正需要时；`requestIdleCallback` 可在空闲期跑非关键任务，但要特性检测与降级。
4. 组件层：`memo`/`useMemo`/`useCallback` 只在能减少真实重渲染时使用，滥用反而增加比较成本；更有效的是减少状态提升、拆小订阅范围、列表项用稳定 key。
5. Worker 与 OffscreenCanvas：JSON 解析、加密、图像处理、Excel 生成、复杂排序聚合适合搬进 Web Worker，注意通信本身有序列化成本，小任务别搬，必要时用 Transferable 转移所有权实现零拷贝；Canvas 绘制可通过 `transferControlToOffscreen()` 把上下文交给 Worker，主线程只负责交互，代价是调试更麻烦、部分 API 在 Worker 中不可用。
6. 预期收益与代价：主线程长任务减少，INP 与滚动流畅度改善；代价是代码复杂度与调试成本上升，Worker 与主线程的数据同步需要额外设计。

**追问与易错点**：

- 追问：所有计算都放 Worker 好不好？答：不好。每次通信都要序列化，小任务搬过去反而更慢，通常只搬超过几毫秒的重活。
- 陷阱：Worker 里访问 `document`、`window` 直接报错，DOM 相关只能回主线程。
- 陷阱：把 `useMemo` 当银弹。依赖每次变化时它照旧重算，还会多一次缓存比较，先确认重渲染与重算真的存在再上。

### Q27 构建时能做哪些性能优化？splitChunks、externals、sourcemap 怎么配？

**考察点**：考工程化视角，构建决定了产物形态，是很多性能问题的源头。

**参考答案**：

> **一句话结论**：构建期优化的目标是「产物更小、缓存更稳、分析更快」：拆包按变更频率、外部依赖别为了省体积牺牲可靠性、sourcemap 只在需要的地方产出。

1. 拆包：webpack 的 `splitChunks`（`chunks: 'all'`，用 `cacheGroups` 把框架、UI 库、工具库分组）或 Vite/Rollup 的 `manualChunks`，把变更频率低的依赖抽成稳定 chunk，配合 `runtimeChunk: 'single'` 让业务代码变更不污染 vendor 哈希。注意拆得过多会产生请求瀑布和重复依赖。
2. externals：把 React/Vue 等依赖交给 CDN 能减小自己的包，但多一次跨域连接、依赖外部可用性与版本一致性，HTTP/2 下收益有限，新项目一般不值得。
3. sourcemap：生产用 `hidden-source-map`（产物里不引用注释，只上传到监控平台），既保留排查能力又不把源码暴露给用户；开发用 `eval-cheap-module-source-map` 求快；不要再生成体积巨大的全量 map 并公开暴露。
4. 持久化与增量：webpack 5 的 `cache: { type: 'filesystem' }`、Vite 的依赖预构建、增量编译都能缩短构建时间——构建时间本身也是研发性能的一部分。
5. 编译目标与 polyfill：按 `browserslist` 定目标，避免为老浏览器打包大量语法转换与 polyfill；`sideEffects: false` 配合 ESM 让 tree-shaking 真正生效；压缩换用 esbuild/swc 可明显加速。
6. 校验与守门：用 bundle 分析工具（webpack-bundle-analyzer、rollup-plugin-visualizer）看产物，并在 CI 里用体积预算卡住增量。

**追问与易错点**：

- 追问：为什么 vendor 拆开了业务包哈希还是变？答：常见原因是 module id 或 runtime 不稳定，需要固定 `moduleIds` 并单独抽 runtime chunk。
- 陷阱：为了减小体积把所有依赖都 externals 到 CDN，结果弱网下多域名连接拖慢首屏，还埋下版本不一致的隐患。
- 陷阱：生产直接开 `source-map` 且公开访问，等于把源码交给对手，应该用 hidden 并限制上传平台访问。

### Q28 内存泄漏怎么排查？常见泄漏有哪些？

**考察点**：考内存维度的问题定位，长时间运行的后台页面尤其会考。

**参考答案**：

> **一句话结论**：内存泄漏的本质是「本该被回收的对象仍被引用」，排查用堆快照三次对比法定位引用链，修复靠管好监听、定时器、全局引用与缓存上限。

1. 常见泄漏：未清理的定时器与 rAF 循环；未移除的事件监听与 Observer 未 `disconnect`；闭包长期持有大对象；全局数组/Map 当缓存且无上限；Detached DOM（节点已从文档移除但 JS 仍引用）；未关闭的 WebSocket、未 `revokeObjectURL` 的 Blob URL；第三方 SDK 的内部缓存。
2. 问题现象：页面用久了越来越卡，任务管理器内存持续上涨，切走再回来标签页被系统回收甚至崩溃（移动端尤其明显）。
3. 定位手段：Memory 面板拍三张堆快照（初始、操作若干次后、手动 GC 后）做对比，看哪种对象数量不回落在增长；用 Allocation instrumentation on timeline 看持续分配；用 Performance monitor 看 JS 堆趋势；Chromium 下可用 `performance.memory.usedJSHeapSize` 做粗略上报。
4. 修复手段：组件卸载时统一清理（Vue 的 `onUnmounted`、React 的 effect 清理函数），把定时器与监听注册封装成可销毁的；缓存用 WeakMap/WeakRef 或加 LRU 上限；大对象用后置空，避免挂在模块作用域。
5. 预期收益与代价：内存曲线趋于平稳，长会话稳定性提升；代价是生命周期管理更严格，WeakRef 等 API 需要特性兼容判断。

**追问与易错点**：

- 追问：Detached DOM 是什么？答：元素已从文档树移除，但 JS 变量仍持有引用，导致它与子树无法回收，在快照的 detached 分类里能看到。
- 陷阱：只看内存总量不看对象类型。总量高可能只是缓存策略，泄漏要看「操作后不回落」的对象。
- 陷阱：用 `addEventListener` 绑在 window 上的监听在组件卸载时不清理，页面切换多次后触发次数成倍增长，既是性能问题也是逻辑 bug。

### Q29 性能监控怎么做？性能预算和 CI 卡口怎么落地？

**考察点**：考持续优化的机制建设，答出「分位数、实验室与现场的分工、预算守门」才算过关。

**参考答案**：

> **一句话结论**：监控看分位数不看均值，实验室数据用于定位、现场数据（RUM）用于决策；把指标与体积写成预算放进 CI，优化成果才不会被后续提交吃掉。

1. 分位数：核心指标用 P75 作为达标口径，同时关注 P95 的尾部用户；按版本、路由、机型、网络、地区拆维度，否则平均值与总分都会骗人。
2. 实验室与现场分工：Lighthouse、DevTools 可复现、能定位到函数，适合研发阶段与回归；CrUX 与自建 RUM 反映真实分布，适合判断上线效果与业务影响。两者不一致时以 RUM 为准。
3. 上报架构：前端用 `web-vitals` 采集，`sendBeacon` 发送，后端做聚合与看板，配合告警（如某版本 LCP P75 回退超阈值）。
4. 性能预算：给 bundle 体积（如入口 JS 的 gzip 体积）、关键指标阈值、请求数、图片体积设定上限，超出即失败。
5. CI 卡口：用 Lighthouse CI 跑关键路由并断言指标，用 size-limit 或 bundlesize 卡体积增量，配合 PR 评论让提交者自己看到代价；对不可避免的增长走显式例外审批。
6. 持续优化：把性能纳入常规迭代（每次发版看板对比），而不是发布前临时运动式优化；对第三方脚本也要计入预算。

**追问与易错点**：

- 追问：为什么实验室分数高但用户投诉卡？答：实验室环境理想、缓存命中、内容确定，真实用户的设备、网络与数据量都更差，必须看 RUM 分维度数据。
- 陷阱：只看 P75 不看分布。P75 达标但 P95 很差，说明还有一批用户完全不可用。
- 陷阱：性能预算只在文档里写，没进 CI，等于没有预算。

### Q30 移动端性能有哪些专项问题？弱网、图片、滚动分别怎么处理？

**考察点**：考移动端场景的具体经验，面试官常用来区分「只在电脑上做优化」的候选人。

**参考答案**：

> **一句话结论**：移动端的三个放大器是「弱网延迟、CPU 弱、内存小」，同一份代码在移动端的问题会被放大数倍，优化要围绕减少请求与体积、降低主线程负担、控制内存占用。

1. 弱网：4G 下 RTT 常在几十到数百毫秒，串行请求与多域名连接代价被放大。手段是减少关键请求数量、合并首屏接口、用 CDN 与缓存、开 HTTP/2 或 HTTP/3、给首屏数据做预取或离线包（Hybrid 场景预置静态资源）。
2. 图片：按 DPR 与视口下发合适尺寸，优先 WebP/AVIF 并做好降级，首屏图不走懒加载；列表图用占位色块或 LQIP 防止跳动。
3. CPU：中低端安卓机型的主线程执行能力远弱于开发机，长任务与 JS 执行时间被放大。手段是代码分割、减少首屏水合、虚拟列表、计算进 Worker、动画只用 `transform`/`opacity`；测试时用 DevTools 的 CPU 降速（Lighthouse 默认 4 倍）逼近真机。
4. 滚动流畅度：滚动监听加 `passive: true`，滚动过程中不读布局属性、不做同步样式计算；避免在滚动里频繁改 DOM；注意 `will-change` 与合成层数量，层太多会吃显存并导致掉帧。
5. 内存：iOS Safari 对单标签页内存有较严限制，大图、长列表、Canvas 与未释放的定时器都会推高占用；及时释放、虚拟化、限制缓存条数，是避免标签页被回收的关键。
6. 预期收益与代价：移动端指标改善通常比桌面更显著；代价是维护多套图片规格与降级逻辑、离线包与预取带来更新一致性成本。

**追问与易错点**：

- 追问：怎么在没有真机的情况下逼近移动端体验？答：DevTools 里做 CPU 降速与网络限速（如慢速 4G），并用 Lighthouse 移动端配置；但这只是模拟，最终要用真机与 RUM 验证。
- 陷阱：只在 WiFi 与旗舰机上验证就上线，中低端安卓机上首屏卡顿投诉不断。
- 追问：Hybrid 里离线包值得做吗？答：首屏强依赖、更新频率可控的业务收益明显；代价是需要版本管理与回退机制，否则会出现新旧资源不一致。

## 本章小结

- 性能优化是「度量 → 定位 → 优化 → 验证 → 沉淀」的闭环，先有数据再动手，改完必须用同一口径复测。
- 指标看分位数：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1 是核心网页指标的好线，TTFB ≤ 0.8s、TBT ≤ 200ms 用于辅助定位。
- 实验室数据用于定位，RUM 用于决策；两者冲突时以真实用户数据的 P75 为准。
- 首屏优化的顺序是 TTFB、关键资源、渲染三段拆解，LCP 图与字体永远不要懒加载。
- 交互卡顿的根因通常是主线程长任务（超过 50ms），治理靠拆任务、减水合、虚拟化、把重活搬进 Worker。
- CLS 的本质是「没预留空间 + 渲染后插入内容」，用尺寸占位与 transform 动画解决。
- 体积优化的顺序是分析产物、砍依赖、让 tree-shaking 生效、按变更频率拆分、最后压缩与 Brotli 传输。
- 性能要靠预算与 CI 卡口持续守门，一次性运动式优化必然回退。
