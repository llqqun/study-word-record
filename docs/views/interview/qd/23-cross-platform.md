## 第 23 章 小程序、跨端与 Hybrid 开发

### Q1 小程序为什么要把逻辑层和渲染层拆成两个线程？这样设计牺牲了什么？

**考察点**：基础题。考底层架构，能不能说清「为什么小程序里不能操作 DOM」，以及双线程的代价。

**参考答案**：

> **一句话结论**：小程序把跑 JS 的逻辑层（App Service）和负责画界面的渲染层（WebView）分成两个线程，中间由微信客户端（Native）转发通信，换取的是安全可控和多页面并行，代价是拿不到真实 DOM、且通信有延迟。

1. 分层职责：逻辑层运行在 JavaScript 引擎里（iOS 是 JavaScriptCore，Android 是 V8），负责业务逻辑、状态和调用 `wx.*` 接口；渲染层是 WebView，只负责把 WXML/WXSS 渲染出来。
2. 为什么要隔离：渲染层被限制成「只能按数据描述来画」，开发者拿不到 `document`，就堵死了 XSS 直接改页面、绕过审核远程下发代码的通路。
3. 通信方式：两层的所有交互都由 Native 中转，`setData` 就是把数据序列化后从逻辑层送到渲染层，本身是异步的，这是性能瓶颈的根源。
4. 代价一：没有 DOM/BOM，所有视图更新只能走 `setData`，不能像 H5 那样直接改节点或挂事件。
5. 代价二：每次更新都多一次跨线程通信与序列化，高频、大数据量更新会明显掉帧。

**追问与易错点**：

- 追问：渲染层就是 WebView，那为什么不直接让 JS 跑在 WebView 里？答：跑进去就回到了「页面能操作自身 DOM」的老路，安全与管控能力全部失效，小程序的存在意义也就没了。
- 陷阱：说成「小程序是原生渲染所以比 H5 快」——传统小程序的渲染层就是 WebView，真正自绘的是 Skyline。
- 追问：iOS 和 Android 的逻辑层引擎一样吗？答：不一样，iOS 用 JavaScriptCore，Android 用 V8，个别语法和性能表现会有平台差异。

### Q2 App、Page、自定义组件的生命周期分别有哪些？执行顺序是什么？

**考察点**：基础题。考有没有真正写过小程序，而不是只会写页面逻辑。

**参考答案**：

> **一句话结论**：App 管全局、Page 管页面、组件管自身挂载，冷启动顺序固定为 `App.onLaunch` → `App.onShow` → `Page.onLoad` → `Page.onShow` → `Page.onReady`，记住这条链就够口述了。

1. `App` 的生命周期：`onLaunch`（全局只触发一次，适合取启动参数、初始化）、`onShow` / `onHide`（前后台切换）、`onError`（脚本错误）、`onPageNotFound`（页面不存在兜底）。
2. `Page` 的生命周期：`onLoad`（只触发一次，最常用来接收路由参数）、`onShow`（每次显示都触发，含从其他页返回）、`onReady`（首次渲染完成，此后才能拿节点）、`onHide`、`onUnload`（页面销毁）。
3. `Page` 的交互回调：`onPullDownRefresh`（下拉刷新）、`onReachBottom`（上拉触底）、`onShareAppMessage`（转发）、`onPageScroll`（滚动，慎用）。
4. 自定义组件的生命周期：`created`（不能 `setData`）、`attached`（进入节点树，常用）、`ready`（布局完成）、`moved`、`detached`（移除，用来清定时器）。
5. 易错点：`onLoad` 只跑一次，从 B 页返回 A 页只会走 `onShow`，所以「返回后刷新列表」要写在 `onShow` 里，而不是 `onLoad`。

**追问与易错点**：

- 追问：`onReady` 和 `onShow` 谁先？答：首次进入是 `onShow` 先、`onReady` 后；之后返回页面只有 `onShow`。
- 陷阱：在 `attached` 里就调 `createSelectorQuery` 拿节点尺寸——此时布局未完成，要放到 `ready` 里。
- 追问：小程序切后台会走什么？答：页面走 `onHide`、App 走 `onHide`，不会走 `onUnload`，回到前台是 `onShow`，这也是「切后台超过一定时间算热启动失效」的原因。

### Q3 `navigateTo`、`redirectTo`、`switchTab`、`reLaunch` 有什么区别？页面栈有上限吗？

**考察点**：基础题。这是真实开发每天都在用的东西，答不利落直接暴露经验不足。

**参考答案**：

> **一句话结论**：四个接口的差别只在「当前页留不留」和「页面栈怎么变」，其中 `switchTab` 和 `reLaunch` 会清掉非 tabBar 页面；微信小程序页面栈上限是 10 层，超过后 `navigateTo` 直接失败。

1. `navigateTo`：保留当前页、新页入栈，最常用；不能跳到 tabBar 页面，跳转后栈深加一。
2. `redirectTo`：关闭当前页再打开新页，栈深不变；适合「登录页 → 首页」这种不该留在栈里的场景。
3. `switchTab`：只能跳 `tabBar` 页面，并且会关闭所有非 tabBar 页面，是底部导航的专用接口。
4. `reLaunch`：关闭所有页面再打开任意页面，等于重启到某页；适合退出登录、异常兜底。
5. 页面栈上限 10 层：层级过深时 `navigateTo` 会静默失败（`fail` 回调），必须先 `redirectTo` 或 `navigateBack` 腾位置；栈信息用 `getCurrentPages()` 读。

| 接口 | 当前页 | 页面栈变化 | 目标页限制 |
| --- | --- | --- | --- |
| `navigateTo` | 保留 | 入栈，深度 +1 | 不能是 tabBar 页 |
| `redirectTo` | 关闭 | 替换栈顶，深度不变 | 不能是 tabBar 页 |
| `switchTab` | 保留 | 关闭所有非 tabBar 页 | 只能是 tabBar 页 |
| `reLaunch` | 关闭 | 清空后重开 | 任意页面 |
| `navigateBack` | 关闭 | 出栈，深度 -1 | 回上一页或多级 |

**追问与易错点**：

- 追问：商品详情来回点十几次会不会崩？答：不会崩，第 11 次 `navigateTo` 会失败；正确做法是详情页复用一个实例、或在 `onLoad` 里判断栈深改用 `redirectTo`。
- 陷阱：用 `navigateTo` 去跳 tabBar 页面，失败还不报错，这是最常见的低级 bug。
- 追问：`switchTab` 跳过去后原来页面还在吗？答：不在，非 tabBar 页面全部被关闭，传参只能靠全局变量或缓存。

### Q4 小程序和 H5 到底差在哪？从 H5 转小程序最容易踩哪些坑？

**考察点**：基础题。考知识迁移能力，也是面试官判断「你能否快速接手小程序」的常见问题。

**参考答案**：

> **一句话结论**：小程序不是「跑在微信里的 H5」，它是一个没有 DOM/BOM、视图靠 `setData` 驱动、网络靠域名白名单、尺寸靠 rpx 的独立运行时。

1. 没有 DOM/BOM：拿不到 `document`、`window`、`location`，不能 `querySelector`、不能 `addEventListener`；要拿节点得用 `wx.createSelectorQuery`。
2. 结构不同：WXML 是模板语法不是 HTML，WXSS 只支持部分选择器（不支持 `*`、部分伪类和属性选择器），也没有 `<div>` 这类标签，全部换成 `view`、`text`、`image` 等内置组件。
3. 本地存储不同：`localStorage` 不存在，改用 `wx.setStorageSync` / `wx.getStorageSync`；Cookie 也不可用，登录态只能自己存 token 并在请求头带上。
4. 事件不同：`bindtap` / `catchtap` 靠 `bind`、`catch` 前缀区分冒泡，事件对象结构也和 DOM 事件不一样，没有事件委托这一套。
5. 网络与路由不同：`wx.request` 要先在小程序后台配置合法域名，没有同源策略也就没有跨域问题；路由只能用 `wx.navigateTo` 这类接口，`history` 不能直接玩。
6. 渲染与单位不同：视图更新只能 `setData`；尺寸单位用 rpx（750rpx 等于屏幕宽度），写死 px 在大屏上会偏小。

**追问与易错点**：

- 追问：那小程序里怎么操作 DOM？答：操作不了，所有变化都要变成数据再 `setData`，这是思维方式的根本转换。
- 陷阱：把 H5 的第三方库（依赖 DOM 的图表库、jQuery 类库）直接搬进小程序，必然跑不起来，要换成小程序专用版本（如 `echarts-for-weixin`、`f2-canvas`）。
- 追问：小程序有跨域问题吗？答：没有浏览器的同源限制，但域名必须提前在后台配置并在真机校验，开发工具里可以临时勾选「不校验合法域名」。

### Q5 订阅消息、模板消息、服务通知是什么关系？小程序消息推送怎么落地？

**考察点**：基础题。考对微信消息能力的现状是否清楚，很多人还停留在模板消息的说法上。

**参考答案**：

> **一句话结论**：小程序模板消息已经在 2020 年初下线，官方方案是订阅消息：用户必须主动点击授权（一次性订阅授权一次只能下发一条），前端拿授权、后端拿 `access_token` 调发送接口，最终以「服务通知」形式出现在微信里。

1. 三种命名的关系：模板消息是已下线的老方案；订阅消息是现方案，分一次性订阅与长期订阅；「服务通知」是用户最终看到的消息形态，不是接口名。
2. 长期订阅只对政务民生、医疗、交通、金融、教育等特定行业开放，普通小程序只能用一次性订阅，用户授权几次就能下发几条。
3. 授权流程：在用户点击事件的同步调用链里调 `wx.requestSubscribeMessage({ tmplIds })`，用户勾选同意后后端记录，再由服务端调订阅消息发送接口。
4. 下发流程：后端用 `access_token` + 用户 `openid` + 模板 ID + 模板数据调发送接口，可带 `page` 指定点击后跳转的页面。
5. 兜底手段：用户和客服有过交互后 48 小时内可以下发客服消息；短信、公众号消息是另一条链路，不能混为一谈。

```js
// 必须在用户 tap 的同步调用链里发起，异步之后调会被拒
onTapPay() {
  wx.requestSubscribeMessage({
    tmplIds: ['TEMPLATE_ID'],
    success: (res) => { if (res['TEMPLATE_ID'] === 'accept') this.reportSubscribe() }
  })
}
```

**追问与易错点**：

- 追问：能查到用户还剩几次订阅额度吗？答：官方没有查询接口，只能自己在下发时记账并扣减，这也是实践中最容易出问题的地方。
- 陷阱：把「用户同意授权」等同于「一定能收到」——拒绝授权、授权次数用尽、模板被下架都会导致收不到。
- 追问：为什么支付成功的通知不建议只靠订阅消息？答：因为它依赖用户授权、不可控，关键业务通知必须叠加短信或 App 推送做兜底。

### Q6 混合开发（Hybrid）怎么调试？真机、抓包、白屏问题分别怎么查？

**考察点**：基础题。考工程实践能力，面试官想知道你遇到问题时手里有没有工具。

**参考答案**：

> **一句话结论**：三条并行手段——用远程调试看 JS 与 DOM、用抓包看请求与离线包加载、用 `vConsole` 或日志上报看真机现场；Hybrid 特有的问题（JSBridge 未注入、离线包版本不对）只能靠前两条组合定位。

1. 远程调试：Android 用 `chrome://inspect`（App 需打开 WebView 调试开关），iOS 用 Safari 的开发菜单；小程序用微信开发者工具的真机调试与预览二维码。
2. 页面内调试面板：H5 在测试环境按开关注入 `vConsole` 或 `eruda`，可在真机上直接看 console、网络和存储。
3. 抓包：用 Charles、Whistle 或 Fiddler 做代理，HTTPS 需要安装并信任根证书；Android 7 以上默认不信任用户证书，需要 root 装系统证书或让客户端配置 `networkSecurityConfig`。
4. 小程序侧调试：用自定义编译模式指定启动页面与参数（比如带 `scene` 值的扫码场景），模拟分享、扫码进入等入口。
5. 白屏排查顺序：先看 WebView 是否创建成功与 URL 是否正确，再看离线包/资源是否 404，再看 JS 是否报错（`window.onerror` + 日志上报 + sourcemap 还原），最后看 JSBridge 注入时机是否早于页面脚本执行。

**追问与易错点**：

- 追问：为什么测试环境好好的，真机白屏？答：最常见是证书不被信任（用户证书）、域名不在白名单、离线包版本与页面不匹配。
- 陷阱：只靠 `alert` 或肉眼观察调试，线上问题没有日志与 sourcemap，等于盲查。
- 追问：小程序里的 `web-view` 内的 H5 怎么调？答：开发者工具可直接调，真机上要么给 H5 注入 `vConsole`，要么抓包，且要先在小程序后台把 H5 域名配成业务域名。

### Q7 小程序和 Web（公众号 H5）的登录态怎么打通？

**考察点**：基础题。考账号体系理解，是电商、会员类项目的必答题。

**参考答案**：

> **一句话结论**：打通的唯一钥匙是 unionid——同一个微信开放平台账号下，同一个人在小程序和公众号里的 openid 不同，但 unionid 相同；业务上用 unionid 把两端账号映射到同一个用户，再把登录态用一次性票据互相传递。

1. 前提条件：小程序和公众号必须绑定在同一个微信开放平台账号下，`code2Session` 返回里才会带 `unionid`。
2. 映射关系：`openid` 是「用户 + 应用」维度的 ID，`unionid` 是「用户 + 开放平台账号」维度的 ID，做用户中心只能用 `unionid`。
3. 小程序 → H5：小程序内嵌 `web-view` 打开 H5 时在 URL 上带一次性票据（如 `ticket` 或 `code`），H5 拿票据调后端换取自己的登录态，用完即废。
4. H5 → 小程序：H5 里引入微信 JSSDK，用 `wx.miniProgram.navigateTo` / `switchTab` 跳回小程序页面并带参数；`postMessage` 只在后退、组件销毁、分享等特定时机才触发，不适合做实时通信。
5. 存储边界：两端存储互相隔离，小程序 `Storage` 与 `web-view` 的 `localStorage`、Cookie 都不共享，登录态必须各自持有、各自续期。

**追问与易错点**：

- 追问：为什么不能直接用 openid 打通？答：H5 走网页授权拿到的 openid 属于公众号应用，与小程序 openid 是两个值，只有 `unionid` 一致。
- 陷阱：把登录 token 直接明文拼在 `web-view` 的 URL 上——URL 会被日志、Referer 记录，正确做法是一次性票据加短有效期。
- 追问：`web-view` 里的 H5 能直接调小程序 API 吗？答：不能。只能通过 JSSDK 的 `navigateTo`、`switchTab`、`reLaunch` 等有限接口与小程序交互，还要先把域名配成业务域名。

### Q8 `setData` 到底做了什么？为什么它被叫做小程序的性能瓶颈？

**考察点**：基础题。这是小程序最核心的一道原理题，答不出机制就说明只会写业务。

**参考答案**：

> **一句话结论**：`setData` 是把数据从逻辑层序列化后经 Native 转发到渲染层、再由渲染层 diff 后更新视图的过程，它跨线程、要序列化、还要等渲染层处理，所以数据量越大、调用越频繁就越卡。

1. 完整链路：逻辑层发起 `setData` → 数据序列化为字符串 → 通过 Native 桥传给渲染层 WebView → 渲染层 `evaluateJavascript` 注入 → 视图层对比新旧数据并更新节点。
2. 瓶颈一：序列化与跨线程通信是固定开销，一次调用就有成本，所以「频繁调用」比「数据大」更致命。
3. 瓶颈二：单次传输的数据量有上限（官方限制约 1MB 级别），超大数组直接传会报错；同时数据要常驻逻辑层内存，影响内存占用。
4. 瓶颈三：`setData` 是异步的，回调 `success` 之后渲染层才更新完，连续依赖上一步结果的逻辑容易拿到旧值。
5. 哪些东西不能放进去：函数、DOM 节点、不可序列化的对象实例传过去没意义（表现为 `undefined`），应该用普通属性挂在 `this` 上而不是 `data` 里。

**追问与易错点**：

- 追问：`setData` 是同步还是异步的？答：API 层面异步，所以有 `success` 回调；逻辑层 `this.data` 会立刻更新，渲染层则要等通信完成。
- 陷阱：把整个大列表每次全量 `setData`，还辩解「小程序有 diff」——diff 在渲染层发生，序列化和传输的成本已经付出去了。
- 追问：`data` 里放的东西越多越好还是越少越好？答：越少越好，`data` 里每个字段都会被序列化和参与 diff，不需要渲染的数据放 `this` 上。

### Q9 rpx 是怎么换算的？小程序适配和 H5 的 rem、vw 方案有什么区别？

**考察点**：基础题。考移动端适配基本功，能不能一句话讲清换算依据。

**参考答案**：

> **一句话结论**：rpx 是相对屏幕宽度的单位，规定屏幕宽永远是 750rpx，所以 1rpx 等于「屏幕宽度 / 750」个物理像素；在 375px 宽的机型上 1rpx 等于 0.5px。

1. 换算规则：设计稿按 750px 宽出图时，量出来多少 px 就直接写多少 rpx，不用换算，这是 rpx 最大的价值。
2. 与 rem 的区别：rem 的基准是根元素字号，需要 JS 或媒体查询动态设置根字号才能适配；rpx 由运行时按屏幕宽度自动换算，不需要额外脚本。
3. 与 vw 的区别：vw 是纯 CSS 单位，1vw 等于视口宽度的 1%，H5 里可以直接用；小程序里同时支持 rpx 和 vw，但不要混用两套基准。
4. 什么时候不该用 rpx：边框、分隔线、图标线条这类要保持物理观感的尺寸用 px；大屏设备（平板、iPad）上 rpx 会把元素等比放大得很夸张，需要限制最大宽度或按断点改用 px。

| 单位 | 基准 | 是否需要脚本 | 适用场景 |
| --- | --- | --- | --- |
| rpx | 750rpx = 屏幕宽 | 不需要，运行时换算 | 小程序、uni-app 多端 |
| rem | 根元素 `font-size` | 需要设置根字号 | 兼容旧项目的 H5 |
| vw | 100vw = 视口宽 | 不需要 | 现代 H5、大屏适配 |
| px | 逻辑像素 | 不需要 | 边框、小图标、固定尺寸 |

**追问与易错点**：

- 追问：设计稿是 375px 宽怎么办？答：把量到的尺寸乘以 2 再写 rpx，或者直接按 750 稿换算，保持团队统一约定。
- 陷阱：所有尺寸一律用 rpx，包括 1px 边框，结果在高倍屏上边框粗细不一。
- 追问：uni-app 编译到 H5 时 rpx 怎么处理？答：编译期会把 rpx 换算成 vw 或 rem 输出，最终效果仍以 750 为基准。

### Q10 `setData` 和长列表渲染怎么优化？说一套能落地的方案。

**考察点**：进阶题。考优化是否成体系，而不是只会背一句「减少 setData」。

**参考答案**：

> **一句话结论**：优化分三条线——减少传输量（只传变化的字段和必要数据）、降低调用频率（合并、节流、移出滚动回调）、控制渲染量（虚拟列表 + 分页 + 懒加载），长列表优先上虚拟列表而不是调参数。

1. 精准更新：用数据路径写法只改变化的字段，例如 `this.setData({ 'list[3].status': 1 })`，避免整个 `list` 重新序列化。
2. 合多次为一次：把同一轮逻辑里的多次 `setData` 合并成一次调用，在 `onPageScroll`、定时器、输入联想这类高频场景必须加节流。
3. 数据分离：不需要渲染的数据不要放进 `data`，挂在 `this` 上；页面本身不需要响应的字段可以用纯数据字段（`pureDataPattern`）声明，减少 diff 开销。
4. 长列表虚拟化：只渲染可视区加缓冲区的节点，小程序侧可用官方 `recycle-view` / `recycle-item` 组件，或自己算 `scrollTop` 控制渲染区间。
5. 分页与懒加载：触底加载下一页、图片 `lazy-load`、首屏用骨架屏；纯展示的大列表可以交给 `wxs` 或 Skyline 的 worklet 在渲染层直接响应滚动，避免把滚动事件抛回逻辑层。

```js
// 只更新变化的那一项，而不是整体重设
this.setData({ [`list[${index}].like`]: true })

// 高频更新合并：只保留最后一次
this.timer && clearTimeout(this.timer)
this.timer = setTimeout(() => this.setData({ scrollTop: top }), 100)
```

**追问与易错点**：

- 追问：虚拟列表在小程序里最大的难点是什么？答：小程序拿不到 DOM 尺寸，得靠 `wx.createSelectorQuery` 或固定行高来算可视区间，行高不固定时实现成本会明显上升。
- 陷阱：一边说优化一边把滚动位置实时 `setData` 用来做吸顶——每次都触发跨线程通信，必然掉帧。
- 追问：列表项里有复杂组件怎么办？答：减少节点层级、把多次渲染合并成一次纯数据更新，或把复杂项下沉成自定义组件，减少主页面 diff 范围。

### Q11 说说小程序登录的完整链路，为什么要二次续期？

**考察点**：进阶题。考链路完整性与安全意识，能不能把「前端拿 code、后端换 openid」讲清楚。

**参考答案**：

> **一句话结论**：小程序端只负责 `wx.login` 拿临时 code，后端拿 code + appid + secret 换 `openid` / `session_key` / `unionid`，再由后端签发自己的登录态给前端；续期的本质是判断 `session_key` 有没有失效，失效就重新登录。

1. 第一步：前端在需要登录态时调 `wx.login`，拿到一个五分钟有效、一次性使用的 `code`。
2. 第二步：前端把 `code` 发给自己的后端，后端调微信的 `code2Session` 接口（带上 `appid`、`secret`、`code`）换取 `openid`、`session_key`、`unionid`。
3. 第三步：后端把三者与自己的用户体系关联，签发自定义登录态（自有 token 或 session），返回给前端；前端存进 `Storage` 并在后续请求头里带上。
4. 安全红线：`secret` 和 `session_key` 绝不能下发到前端，`code2Session` 也只能在后端调；`session_key` 是解密用户数据、校验支付签名的凭据，泄露等于账号被接管。
5. 续期机制：用 `wx.checkSession` 判断 `session_key` 是否过期，过期就让前端重新 `wx.login` 换新 code 续期；自有 token 则按有效期做双 token（访问令牌 + 刷新令牌）或过期前静默续签。

**追问与易错点**：

- 追问：`session_key` 有效期多久？答：官方不承诺固定时长，会因用户长时间未使用等原因失效，所以不能假设它长期有效，必须用 `checkSession` 或请求失败码来兜底。
- 陷阱：把 `wx.login` 拿到的 `code` 缓存起来复用——它是一次性的，第二次用必然失败。
- 追问：没有后端怎么办？答：用微信云开发的免鉴权能力可以跳过自建后端，但生产项目里涉及支付、退款的场景仍然必须有服务端。

### Q12 微信支付在小程序里的完整流程是什么？哪一步最容易出安全问题？

**考察点**：进阶题。考对资金链路的严谨程度，重点是「前端回调不算支付成功」。

**参考答案**：

> **一句话结论**：前端只做两件事——调后端下单、拿参数调 `wx.requestPayment` 拉起收银台；金额校验、签名生成、订单状态更新全在后端，最终以微信的异步支付通知为准。

1. 下单：前端把商品信息发给自己的后端，后端校验商品与金额（金额必须由服务端重新计算，不能信前端传的值），再调微信的 JSAPI 下单接口拿到 `prepay_id`。
2. 组装参数：后端用商户私钥对 `prepay_id` 等字段签名，生成 `timeStamp`、`nonceStr`、`package`、`signType`、`paySign` 一起返回前端。
3. 拉起支付：前端调 `wx.requestPayment` 并原样传入上述参数，用户完成支付后前端会收到 `success` 回调。
4. 服务端确认：微信会异步回调后端通知支付结果，后端必须验签、做幂等处理、再更新订单状态并发放权益；前端的 `success` 只用于界面反馈和轮询查询。
5. 安全重点：签名只在后端做、回调必须验签防伪造、订单状态以服务端通知为准、回调要做幂等（微信会重复通知），退款同样走后端接口。

```js
wx.requestPayment({
  timeStamp, nonceStr, package: `prepay_id=${prepayId}`,
  signType: 'RSA', paySign,
  success: () => this.checkOrderStatus(orderId),   // 只做界面反馈
  fail: (err) => this.handlePayFail(err)           // 用户取消不等于失败原因确定
})
```

**追问与易错点**：

- 追问：为什么不能在前端 `success` 里直接发货？答：回调可以被伪造，也可能因网络超时收不到，真正可信的是服务端收到的支付通知。
- 陷阱：把 `signType` 固定写死——老项目用 MD5、新接口（APIv3）用 RSA，写错会一直提示签名错误。
- 追问：用户支付中途退出怎么办？答：订单保持待支付，前端调后端主动查询订单状态（查单接口）来对账，不能凭猜。

### Q13 小程序为什么要分包？主包、分包、独立分包、预下载分别怎么用？

**考察点**：进阶题。考体积治理经验，这是小程序上线的硬门槛。

**参考答案**：

> **一句话结论**：分包是为了绕开单包体积限制、缩短首屏下载时间：主包控制在 2MB 内装启动必需资源，业务模块拆成按需下载的普通分包，能独立启动的入口拆成独立分包，再对高频路径配分包预下载来抵消首次进入的等待。

1. 体积限制：主包和单个分包各不超过 2MB，整个小程序所有分包总和不超过 30MB（服务商代开发的小程序为 20MB），超出直接无法上传。
2. 主包放什么：启动页、tabBar 页面、全局样式与公共组件必须放主包，因为启动时要直接可用；主包被限制在 2MB 是分包的根本动因。
3. 普通分包：依赖主包，进入分包页面时才下载；主包不能引用分包资源，分包之间默认也不能互相引用（较新基础库支持分包异步化，可以异步跨分包引用 JS 与组件）。
4. 独立分包：不依赖主包即可运行的入口（如活动页、广告落地页），进入时不需要下载主包；代价是不能用主包的公共样式与组件，`getApp()` 也拿不到主包实例，公共资源要复制一份。
5. 分包预下载：在 `app.json` 的 `preloadRule` 里声明「进入某页面时预下载哪些分包」，把首次进入分包的等待提前到用户还在主包操作时；预下载有独立体积限额，超额会失效。

| 类型 | 是否依赖主包 | 体积限制 | 典型用途 |
| --- | --- | --- | --- |
| 主包 | — | ≤ 2MB | 启动页、tabBar 页、公共资源 |
| 普通分包 | 依赖 | 单个 ≤ 2MB | 按业务模块按需加载 |
| 独立分包 | 不依赖 | 单个 ≤ 2MB | 广告页、活动页、独立入口 |
| 全部包合计 | — | ≤ 30MB | 整个小程序上限（服务商代开发为 20MB） |

**追问与易错点**：

- 追问：分包就是把代码挪个目录吗？答：不只是，拆分点要按「用户路径」而不是按文件夹，公共依赖放主包还是复制到分包要做取舍。
- 陷阱：把 tabBar 页面放进分包——配置直接报错，tabBar 页必须在主包。
- 追问：拆了分包用户还是要等下载，怎么优化？答：用分包预下载 + 骨架屏 + 包内资源复用，让等待发生在用户可接受的时机。

### Q14 微信小程序的渲染引擎有哪些？WebView 渲染和 Skyline 有什么区别？

**考察点**：进阶题。考对新渲染引擎的认知，以及能不能区分「JS 引擎」和「渲染引擎」。

**参考答案**：

> **一句话结论**：逻辑层的 JS 引擎是 JSCore（iOS JavaScriptCore / Android V8），渲染层默认是 WebView；Skyline 是新渲染引擎，改用自绘方式渲染，把滚动、手势、动画等高频交互下沉到渲染层执行，性能更接近原生。

1. 默认方案：渲染层是 WebView，WXML/WXSS 最终转成 HTML/CSS 由浏览器内核绘制；逻辑层与渲染层分离，中间靠 Native 通信。
2. WebView 方案的固有成本：所有视图变化都要跨线程来一趟，滚动、动画等高频交互容易掉帧；此外原生组件（`video`、`map`、`canvas`、`input` 等）层级最高，会盖住普通元素，需要靠同层渲染（same-layer rendering）解决。
3. Skyline 的差别：不依赖 WebView，由渲染引擎直接绘制，滚动与触摸可以在渲染层闭环处理，动画走 worklet（渲染层执行的函数），不需要每次把滚动事件抛回逻辑层。
4. Skyline 的代价与限制：需要配置 `renderer: skyline` 并使用 glass-easel 组件框架；不支持 `web-view` 组件，不支持 WXS（要用 worklet 替代），部分 CSS 与老组件不兼容，迁移成本不低。
5. 怎么选：新项目、交互密集（长列表、动画、手势）且不需要内嵌 H5 的场景可以上 Skyline；存量项目、依赖第三方组件或 `web-view` 的继续用 WebView。

**追问与易错点**：

- 追问：Skyline 是「原生渲染」吗？答：更准确说是自绘渲染引擎，不是把每个节点映射成系统原生控件，所以不等同于 React Native 的思路。
- 陷阱：把 JSCore 说成渲染引擎——它只是逻辑层的 JS 运行时，负责执行 JS，不负责画界面。
- 追问：原生组件为什么要同层渲染？答：原生组件由客户端绘制、层级天然高于 WebView 内容，不同层就会出现「弹窗被视频盖住」这类问题。

### Q15 uni-app 的原理是什么？一套代码多端的能力边界在哪？

**考察点**：进阶题。考是否理解编译期与运行时的分工，而不是只会说「一套代码多端」。

**参考答案**：

> **一句话结论**：uni-app 是「编译期转换 + 运行时适配层」的组合：模板和样式在编译期转成各端的目标语法（小程序 WXML/WXSS、H5 的 DOM、App 的原生容器），API 则由统一的 `uni.*` 在运行时映射到 `wx.*`、浏览器 API 或 App 的原生能力。

1. 编译期：Vue 单文件组件被拆开转换——`template` 转成小程序模板或 H5 的渲染函数，`style` 转成 WXSS 或 CSS，同时按平台裁剪；`#ifdef MP-WEIXIN` / `#ifndef H5` 这类条件编译就是在这一步生效的。
2. 运行时：`uni.request`、`uni.getLocation` 等统一 API 由适配层分发到对应平台实现；App 端基于原生容器与原生插件体系，小程序端直接映射到 `wx.*`。
3. 组件与样式边界：小程序端没有 DOM，标签选择器和部分伪类不支持，层级选择器要慎用；`scoped` 与深度选择器的行为在各端不完全一致，样式要按小程序的能力写「最小公约数」。
4. 能力边界：依赖 DOM/BOM 的第三方库（图表、富文本、地图插件）在小程序端不可用；App 独有能力和微信独有能力必须靠条件编译加平台判断，写不了「零差异」。
5. 合适的期待：一次开发、多端运行是成立的，但「一次调试、零适配」不成立，通常要按平台单独处理 20% 的差异代码。

**追问与易错点**：

- 追问：条件编译是运行时判断吗？答：是编译期剪裁，代码在打包时就被删掉了，所以不要用它包裹必须在所有端都存在的逻辑。
- 陷阱：用 `process.env.UNI_PLATFORM` 之类的运行时判断到处写分支，最后代码里全是平台判断，可维护性反而比多套代码更差。
- 追问：uni-app 能直接转成原生 App 吗？答：默认是 H5 渲染加原生容器与插件；对性能要求高的页面可以走原生渲染方案或多端差异化实现。

### Q16 Taro、uni-app 和原生开发怎么选？给一个对照表。

**考察点**：进阶题。选型题必须有对照表，考取舍能力而不是背官网介绍。

**参考答案**：

> **一句话结论**：技术栈决定优先项——React 团队优先 Taro，Vue 团队优先 uni-app，追求极致性能或需要最新平台能力就上原生；三者不是替代关系，多数项目是「原生做核心链路、跨端框架做业务页」的混合结构。

1. Taro：支持 React（也支持 Vue），编译到各端；Taro 3 起引入运行时方案，用 BOM/DOM 模拟层让 React 生态大致可用，代价是多一层运行时开销。
2. uni-app：围绕 Vue 生态与 HBuilderX 工具链，插件市场成熟、文档中文友好、上手快，中小团队落地成本最低。
3. 原生：性能和能力上限最高，新特性第一时间可用，没有兼容与编译层黑盒；代价是双端各写一套，人力与维护成本翻倍。
4. 判断标准：看团队已有技术栈、看对性能的要求、看是否需要用到平台独有能力、看是否要长期维护；纯业务型页面走跨端，核心交互与重性能页面（地图、长列表、直播）走原生。
5. 一条现实建议：跨端框架不适合用来「赌」所有平台，先把一个端做扎实，再按端评估迁移收益。

| 方案 | 开发成本 | 性能 | 生态 | 适用场景 |
| --- | --- | --- | --- | --- |
| Taro | 中（React 团队低） | 中 | 较好（React 生态 + 多端插件） | React 团队、多端业务页 |
| uni-app | 中低（Vue 团队低） | 中 | 好（插件市场 + 中文文档） | 中小团队、快速多端上线 |
| 原生双端 | 高（约 2 倍人力） | 高 | 最好（官方最新能力） | 核心链路、重性能、大团队 |
| 混合（原生壳 + 跨端页） | 中高 | 中高 | 好 | 存量 App 快速扩业务 |

**追问与易错点**：

- 追问：跨端框架编译出来的包会不会更大？答：会，通常带运行时与适配层，所以对包体敏感的端仍要做差异化裁剪。
- 陷阱：只按「哪个火」来选型，忽略了团队是 Vue 还是 React，最后维护成本比收益高。
- 追问：同一个项目能混用吗？答：可以，常见做法是主链路原生、运营页跨端，代价是构建与发布链路要统一治理。

### Q17 WebView 的性能怎么优化？离线包和预加载怎么配合？

**考察点**：进阶题。考 Hybrid 首屏优化的完整套路，能否把「创建、缓存、预加载」串起来。

**参考答案**：

> **一句话结论**：WebView 的首屏时间等于「实例创建 + 资源下载 + JS 执行」三段之和，优化就是三段一起压——提前创建并复用实例、把资源缓存或预置成本地离线包、把数据请求提前或并行。

1. 初始化时机：不要等用户点了才创建 WebView，启动时或空闲时预创建实例池（预热），打开页面时直接复用，省掉内核初始化那几百毫秒。
2. 实例复用：维护一个 WebView 池，页面关闭后回收而不是销毁；同时要在复用前重置 URL、清理 Cookie 与 JS 全局状态，否则会串数据。
3. 缓存策略：静态资源走 HTTP 强缓存加文件内容哈希；更彻底的是离线包——把 H5 资源打包预置到本地或提前下载，客户端拦截资源请求直接返回本地文件，版本由服务端下发控制。
4. 预加载：进入某个原生页面前预加载下一页的 WebView 与首屏数据，DNS 预解析、资源预取并行做；配合骨架屏让等待可感知地变短。
5. 安全与稳定：所有打开的 URL 走白名单校验，禁止外部自由跳转；离线包要校验签名与版本、失败时回退到线上资源，避免「离线包坏了直接白屏」。

**追问与易错点**：

- 追问：离线包更新怎么保证不白屏？答：版本灰度下发、下载完成校验通过后才切换，保留上一版本兜底，出问题能一键回退。
- 陷阱：WebView 复用后忘记清理历史状态，导致 A 页面看到 B 页面的登录态或表单数据。
- 追问：预加载会不会浪费资源？答：会，所以要按用户路径预测（只在进入列表页时预加载详情页），并限制并发数与内存水位。

### Q18 React Native 的通信原理是什么？Bridge 为什么慢？

**考察点**：进阶题。考对 RN 老架构的理解，这是承接新架构问题的前置知识。

**参考答案**：

> **一句话结论**：RN 老架构里 JS 线程和原生线程通过桥（Bridge）做异步消息通信，所有指令都要序列化成 JSON 再批量投递，所以慢在「异步 + 序列化 + 批量排队」，需要同步返回的能力根本做不到。

1. 三个线程：JS 线程跑 React 与业务逻辑，Shadow 线程用 Yoga 做布局计算，UI/Main 线程负责真正的原生视图创建与绘制。
2. 一次更新的链路：JSX 变化后 React 做 diff，生成「创建/更新原生视图」的指令，序列化后通过 Bridge 交给 Shadow 线程算出布局，最后在 UI 线程设置原生组件属性。
3. 为什么慢：每次通信都要序列化与反序列化；Bridge 是异步批处理的，指令要排队；高频更新（滚动、动画、手势跟随）会把队列打满，表现为掉帧。
4. 能力限制：Bridge 天然不支持同步调用，所以早期要同步拿原生值的场景（如精确测量布局）只能绕路，这也是新架构要解决的痛点。
5. 常见的规避手段：动画用 `useNativeDriver` 让驱动跑在原生侧，手势用原生手势系统，列表用虚拟化的 `FlatList`，尽量减少跨桥次数。

**追问与易错点**：

- 追问：Bridge 是同步还是异步？答：异步，且批量投递；所以 JS 里改完状态不能假设原生立刻就更新完了。
- 陷阱：把 RN 的渲染说成 WebView 渲染——RN 渲染的是真正的原生组件，这一点和 Hybrid 有本质区别。
- 追问：为什么说列表滚动是最容易暴露 Bridge 瓶颈的场景？答：滚动会产生大量连续更新，跨桥队列排不上就会卡顿。

### Q19 Hybrid 里 H5 和原生怎么通信？H5 能调用哪些原生能力？

**考察点**：进阶题。JSBridge 是 Hybrid 的核心，考通信方式的演进与能力清单。

**参考答案**：

> **一句话结论**：H5 调原生有 URL 协议（Scheme）跳转、注入 API、拦截 `prompt`/`console`、`WKWebView` 的 `messageHandler` 与自定义 Scheme 拦截这几条路；原生调 H5 则是注入脚本执行 JS 回调，成熟方案会把这些封装成统一的 JSBridge。

1. URL 协议（URL Scheme）：H5 用隐藏 `iframe` 或改 `location.href` 触发 `myapp://action?params`，原生拦截该请求；兼容性最好，但参数长度受限、无法直接拿返回值，且页面可能被跳转打断。
2. 注入 API：原生启动时通过 `addJavascriptInterface`（Android）或 `WKUserContentController`（iOS）向 `window` 注入对象，H5 直接调用并拿到同步或异步结果；Android 上要注意注入对象的方法可被反射调用带来的安全风险。
3. 拦截 `prompt` / `console`：利用 H5 调用 `prompt` 时同步阻塞的时机，原生在 `onJsPrompt` 里解析并返回结果，从而获得**同步返回值**，这是老方案里少数能同步的手段。
4. `WKWebView` 的 `messageHandler` 与自定义 Scheme：iOS 上用 `postMessage` 异步通信更安全，配合 `WKURLSchemeHandler` 拦截自定义协议可避免真实网络跳转；`UIWebView` 已废弃，不要再基于它设计。
5. 原生调 H5：调用 `evaluateJavaScript` 执行预先挂到 `window` 上的回调函数，形成「H5 发请求带回调 ID → 原生执行完回调 H5」的完整闭环。
6. H5 可调用的原生能力清单：拍照与相册、扫码、定位、分享、支付、文件选择与上传下载、通讯录、剪贴板、蓝牙、NFC、拨号、系统导航、震动、屏幕常亮、推送与角标、设备与网络信息。

| 能力 | 微信小程序对应 API | 通用 Hybrid 封装 |
| --- | --- | --- |
| 拍照/相册 | `wx.chooseMedia` | `bridge.invoke('camera')` |
| 扫码 | `wx.scanCode` | `bridge.invoke('scan')` |
| 定位 | `wx.getLocation` | `bridge.invoke('location')` |
| 分享 | `onShareAppMessage` | `bridge.invoke('share')` |
| 支付 | `wx.requestPayment` | `bridge.invoke('pay')` |
| 文件 | `wx.chooseMessageFile`、`wx.downloadFile` | `bridge.invoke('file')` |

**追问与易错点**：

- 追问：为什么 URL Scheme 拿不到返回值？答：它本质是一次导航请求，原生只能拦截，无法把结果同步回页面，所以必须配回调机制。
- 陷阱：在 iOS 上直接依赖 `prompt` 拦截——`WKWebView` 需要实现 `WKUIDelegate` 的对应回调才能拿到 `prompt` 内容，而且它会同步阻塞等待原生返回，新项目更适合用 `messageHandler` 做异步通信。
- 追问：注入 API 有什么安全风险？答：Android 的 `addJavascriptInterface` 若暴露了危险方法，被注入的恶意页面可反射调用原生能力，所以必须校验来源 URL 并只暴露白名单方法。

### Q20 Electron 和 Tauri 怎么做桌面端？和前端技术栈怎么衔接？

**考察点**：进阶题。考桌面端方案视野，很多前端只听过 Electron。

**参考答案**：

> **一句话结论**：Electron 自带 Chromium 与 Node.js，渲染进程写前端、主进程管窗口与系统能力，靠 IPC 通信，生态成熟但体积与内存大；Tauri 用 Rust 做后端、复用系统 WebView，体积小、内存低，但跨平台一致性依赖系统内核与插件生态。

1. Electron 的架构：主进程（Main）管理窗口、菜单、托盘、文件系统，渲染进程（Renderer）就是网页；两者通过 `ipcMain` / `ipcRenderer` 通信。
2. 安全实践：必须开 `contextIsolation`、关 `nodeIntegration`，通过预加载脚本（preload）+ `contextBridge` 只暴露白名单方法，不要把整个 Node 能力暴露给页面。
3. Tauri 的架构：前端仍是 Web，系统能力由 Rust 侧通过 `invoke` 暴露命令（command），Windows 用 WebView2、macOS 用 WKWebView、Linux 用 WebKitGTK。
4. 关键取舍：Electron 体积通常上百 MB 但渲染完全一致、生态和调试体验好；Tauri 安装包可小到几 MB、内存占用低，但不同系统内核版本差异要自己兜。
5. 选型建议：需要复杂系统集成、稳定一致的行为、成熟生态（如 VS Code 类工具）选 Electron；追求包体积与内存、功能相对聚焦选 Tauri。

| 方案 | 运行时 | 体积 | 跨端一致性 | 生态 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| Electron | Chromium + Node.js | 大（百 MB 级） | 好（自带内核） | 成熟 | 复杂桌面工具、需一致体验 |
| Tauri | 系统 WebView + Rust | 小（几 MB 级） | 依赖系统内核 | 成长中 | 轻量工具、体积敏感 |
| PWA/桌面封装 | 系统浏览器内核 | 最小 | 差 | 受限 | 轻量、可联网场景 |

**追问与易错点**：

- 追问：桌面应用为什么不能直接开 `nodeIntegration`？答：页面一旦被注入脚本就能直接读写文件系统，等于把用户机器交给远程代码。
- 陷阱：把 Tauri 当成「Electron 的轻量版」——Rust 侧的能力要自己写，和 Node 生态不可直接复用。
- 追问：前端代码能原样迁移吗？答：界面层基本可以，但涉及文件、窗口、系统托盘的能力必须改用各自的 IPC 接口。

### Q21 一套代码多端，最容易踩哪些坑？怎么治理？

**考察点**：进阶题。考真实的跨端落地经验，答得越具体越可信。

**参考答案**：

> **一句话结论**：坑集中在样式差异、API 兼容、生命周期差异和平台判断滥用四类；治理思路是「把差异收敛到一处封装」，而不是让平台判断散落在业务代码里。

1. 样式差异：小程序不支持标签选择器、部分伪类与属性选择器，`position: fixed` 在原生组件旁的表现不同，各端默认字号与行高基线不一致；对策是采用统一的设计规范与基础样式变量，复杂样式做端内差异化文件。
2. API 兼容：同名 API 在各端参数与返回结构可能不同（定位精度、权限流程、支付、分享），必须封成一层 `platform/` 适配层，业务只调平台无关接口。
3. 生命周期差异：小程序页面有 `onLoad` / `onShow`，H5 只有组件挂载与路由钩子，App 还可能有页面保活；用跨端框架时要按框架约定的生命周期写，不要写只有一端会触发的钩子。
4. 平台判断滥用：`if (isWeixin) {}` 撒满业务代码后，新增一个端就是灾难；正确做法是按能力而不是按平台判断（如「是否支持扫码」），并把判断收敛到适配层。
5. 其他高频坑：包体超限（小程序 2MB 主包）、字体与图标不显示（字体文件需转 base64 或换图标组件）、键盘弹起遮挡输入框、长按与点击事件的端间差异、真机与开发工具的渲染差别。

**追问与易错点**：

- 追问：怎么在 CI 里提前发现多端问题？答：各端都跑一遍构建与冒烟用例，把端差异写成配置化的检查项，而不是靠人工点。
- 陷阱：用「先按一端开发完再适配其他端」的方式排期——差异代码永远是补丁，成本会随端的数量指数上升。
- 追问：平台判断一点都不能写吗？答：能写，但要写在适配层或按能力判断，业务层不允许出现平台字符串。

### Q22 React Native 新架构解决了什么？JSI、Fabric、TurboModules、Hermes 分别是什么？

**考察点**：深挖题。考是否了解 RN 近年最大的架构演进，而不是停留在 Bridge 时代。

**参考答案**：

> **一句话结论**：新架构用 JSI 取代 Bridge 作为 JS 与原生之间的统一接口，在此基础上把原生模块换成 TurboModules、把渲染器换成 Fabric，并用 Hermes 作为默认 JS 引擎，最终目标是同步调用、按需加载和可并发渲染。

1. JSI（JavaScript Interface）：一层 C++ 抽象，让 JS 引擎能直接持有并调用 C++ 对象，可以同步调用原生方法、不必序列化，也让 JS 引擎可替换。
2. TurboModules：基于 JSI 的原生模块系统，模块按需懒加载而不是启动时全量初始化，降低启动耗时，并支持同步方法调用。
3. Fabric：新渲染器，把影子树（Shadow Tree）与布局计算搬到 C++ 层，支持同步布局测量和并发渲染（配合 React 18 的并发特性），跨线程跳转更少。
4. Hermes：为 RN 优化的 JS 引擎，构建时把 JS 预编译成字节码，显著缩短启动时间并降低内存占用，已成为默认引擎。
5. Codegen：根据 TypeScript 类型定义静态生成 JS 与原生之间的胶水代码，减少手写桥接代码，同时带来类型安全。
6. 落地节奏：新架构从 RN 0.76 起默认开启，历史项目迁移的主要成本在第三方原生库是否已适配。

| 维度 | 老架构 | 新架构 |
| --- | --- | --- |
| 通信 | Bridge 异步、JSON 序列化 | JSI 直接调用，可同步、免序列化 |
| 原生模块 | `NativeModules` 启动即加载 | TurboModules 按需懒加载 |
| 渲染 | Shadow 线程布局，异步提交 | Fabric C++ 影子树，支持同步布局与并发渲染 |
| JS 引擎 | JSC 为主 | Hermes 默认 |
| 类型衔接 | 手写桥接代码 | Codegen 依据类型自动生成 |

**追问与易错点**：

- 追问：新架构是不是就没有 Bridge 了？答：通信不再依赖 Bridge 的 JSON 通道（无桥模式），但「JS 与原生分离」的模型仍然存在，只是接口换成了 JSI。
- 陷阱：把 Hermes 说成渲染器——它是 JS 引擎，负责执行 JS，不负责画界面。
- 追问：新架构对业务代码有侵入吗？答：业务层基本无感，主要影响自研原生模块与第三方库的适配，迁移前要先梳理依赖库的支持情况。

### Q23 RN 应用卡顿一般卡在哪？怎么系统优化？

**考察点**：深挖题。考性能定位能力，能不能区分「JS 线程忙」和「UI 线程忙」。

**参考答案**：

> **一句话结论**：先定位是 JS 线程被长任务占住（表现为点击无响应、逻辑延迟）还是 UI 线程/桥排队跟不上（表现为滚动与动画掉帧），再分别减少 JS 工作量或减少跨线程更新次数。

1. 定位手段：开启性能监视器看 JS 与 UI 帧率，用 Systrace / Perfetto 或 React DevTools Profiler 找长任务与多余渲染。
2. 减少重渲染：列表项用 `React.memo`，回调用 `useCallback`，计算用 `useMemo`，避免在渲染里创建内联对象与函数，避免在父组件频繁改导致整棵子树重渲染。
3. 列表优化：`FlatList` 要给稳定的 `keyExtractor`、能用就配 `getItemLayout` 省掉测量，调整 `windowSize`、`initialNumToRender`、`maxToRenderPerBatch`，必要时开 `removeClippedSubviews`。
4. 动画与手势：能用原生驱动的就用 `useNativeDriver`，复杂交互用 Reanimated 把动画逻辑放到 UI 线程执行，避免每帧回 JS 线程。
5. 启动与内存：Hermes 加预编译字节码缩短启动，非首屏模块懒加载；图片按需尺寸加载并复用，避免大数组常驻内存与定时器泄漏。
6. 调度策略：把非紧急任务用 `InteractionManager` 或空闲回调推后，避免与动画、手势抢 JS 线程。

**追问与易错点**：

- 追问：为什么 `useNativeDriver` 不能用在所有动画上？答：它只支持布局属性之外的变换与透明度类动画，涉及宽高、边距等布局属性的动画无法完全下沉到原生。
- 陷阱：一上来就换新架构或加库，而不先量出瓶颈在 JS 还是 UI 线程。
- 追问：滚动掉帧一定是桥的问题吗？答：不一定，也可能是列表项渲染太重、图片解码在主线程，要分场景实测。

### Q24 JSBridge 的回调管理怎么做？怎么防回调丢失、超时和多次回调？

**考察点**：深挖题。考工程严谨性，这是 Hybrid 项目线上事故的高发区。

**参考答案**：

> **一句话结论**：核心是「一次调用一个唯一 ID + 一张回调表 + 超时兜底 + 拿到就删」，用 Promise 包一层保证只 settle 一次，并在页面卸载时统一清理，才能同时防丢失、防超时、防重复回调。

1. 唯一 ID：每次调用生成自增或随机 ID，把 `resolve` / `reject` 存进 `callbacks` 表，原生回调时带上同一个 ID 找回。
2. 防丢失：都有超时兜底（如 3 至 10 秒），超时后 reject 并从表中删除；原生侧崩溃、handler 不存在、参数非法都会表现为没有回调，绝不能让它永远 pending。
3. 防多次回调：`resolve` 之后立刻 `delete callbacks[id]`，回调表里查不到就忽略后续调用；Promise 本身只接受首次 settle，但基于 callback 的老实现必须自己判断。
4. 内存与生命周期：页面卸载、路由切换时批量 reject 未完成回调并清空表，否则回调闭包持有页面引用会造成泄漏。
5. 顺序与安全：原生回调是异步的，不要假设多路回调的顺序；同时对调用方做来源白名单校验（域名、页面），对敏感能力（支付、通讯录、文件）做二次确认，Scheme 与注入 API 都要收敛到白名单。

```js
const callbacks = new Map()
let seed = 0

function invoke(action, params = {}, timeout = 5000) {
  const id = `${action}_${++seed}`
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => { callbacks.delete(id); reject(new Error('bridge timeout')) }, timeout)
    callbacks.set(id, {
      resolve: (res) => { clearTimeout(timer); callbacks.delete(id); resolve(res) },
      reject: (err) => { clearTimeout(timer); callbacks.delete(id); reject(err) }
    })
    sendToNative(action, { ...params, callbackId: id })
  })
}
```

**追问与易错点**：

- 追问：原生侧应该怎么回调用？答：通过注入脚本调用约定的全局函数并传 `callbackId` 与结果，同时保证同一个 `callbackId` 只回调一次。
- 陷阱：只在「原生没实现」时才 reject，其它异常路径直接不回调，前端页面就会一直转圈。
- 追问：为什么回调必须带 ID 而不是按调用顺序回？答：原生异步执行、可能乱序返回，靠顺序匹配必然错位。

### Q25 跨端渲染方案有哪几类？Flutter 的自绘渲染和 WebView、原生渲染怎么选？

**考察点**：深挖题。选型题必须给对照表，考的是把「渲染方式」与「成本、性能、一致性、动态化」联系起来的能力。

**参考答案**：

> **一句话结论**：跨端渲染无非三条路——WebView 渲染（H5/Hybrid）、原生渲染（RN 这类用原生组件拼界面）、自绘渲染（Flutter 用 Skia 之类引擎自己画），前者成本最低但性能与体验上限最低，原生渲染居中，自绘渲染一致性最好但生态与包体代价最大。

1. WebView 渲染：写的是网页，跑在 WebView 里，可动态下发、可热更新、生态最全；代价是首屏慢、滚动与动画受限于浏览器内核，与原生体验有割裂感。
2. 原生渲染：JS 描述界面、映射成真实原生组件（RN 用 Bridge/JSI 通信），性能与手感接近原生；代价是需要一套跨语言通信机制，且组件能力受原生平台与第三方库适配度约束。
3. 自绘渲染：Flutter 用 Dart 编写，release 走 AOT 编译，通过自绘引擎（Skia，新版本 iOS 与 Android 已默认 Impeller）把整棵 UI 树自己绘制出来，不依赖平台控件。
4. Flutter 的取舍：优点是跨端像素级一致、动画性能好、热重载体验佳；缺点是包体积明显更大、与原生混合开发（add-to-app、PlatformView）成本高、Dart 生态与前端生态不互通、动态化能力弱。
5. 选型结论：要动态化和快速迭代选 WebView/Hybrid；要接近原生的性能且团队是前端技术栈选 RN；要极致一致的 UI 与动画、且能接受新增一套技术栈就选 Flutter。

| 方案 | 代表 | 开发成本 | 性能上限 | 跨端一致性 | 动态化 | 适用场景 |
| --- | --- | --- | --- | --- | --- | --- |
| WebView 渲染 | H5、Hybrid、小程序默认 | 低 | 低 | 中 | 强（可热更新） | 运营页、内容页、迭代快的业务 |
| 原生渲染 | React Native | 中 | 高 | 中高 | 中（受审核约束） | 主 App 业务、交互较复杂 |
| 自绘渲染 | Flutter | 中高（需学 Dart） | 高 | 最好 | 弱 | UI 一致性要求高、动画密集 |
| 全原生 | Swift/Kotlin | 最高 | 最高 | — | 无 | 核心链路、平台新特性首用 |

**追问与易错点**：

- 追问：小程序属于哪一类？答：默认是 WebView 渲染加原生组件同层渲染，Skyline 则走向自绘渲染，所以它是混合形态。
- 陷阱：认为 Flutter 性能一定全面超过 RN——静态复杂动画和一致性好，但涉及原生控件、地图、视频时混合成本可能反超。
- 追问：Flutter 为什么动态化弱？答：release 走 AOT，产物是机器码，无法像 JS 那样下发即执行，热更新能力受平台政策限制。

### Q26 新项目要求同时上小程序、H5 和 App，你怎么做跨端选型并保证发布可控？

**考察点**：深挖题。综合选型题，考决策框架的完整性，以及能不能把「发布与灰度」一并纳入方案。

**参考答案**：

> **一句话结论**：按团队、成本、性能、生态、发布五个维度逐项打分，多数业务型项目用「uni-app 或 Taro 做多端 + 原生壳承载重能力」的组合，核心链路保留原生实现，并从一开始就设计好分端发布与灰度回滚机制。

1. 团队维度：看现有技术栈是 Vue 还是 React（决定 uni-app 还是 Taro）、看有没有原生开发资源（决定能否做混合方案）、看人力能否长期维护多端。
2. 成本维度：算清一次开发多端节省的人力，也要算上适配、端内差异测试与后续每次发版的多端回归成本，跨端不等于零成本。
3. 性能维度：区分页面类型——列表、详情、表单类页面跨端即可；地图、直播、长列表、复杂动画这类重交互页面用原生实现，避免后期重构。
4. 生态维度：检查关键依赖（图表、富文本、地图、音视频、埋点、支付 SDK）是否各端都有可用实现，缺口决定要不要自研。
5. 发布维度：小程序走平台审核与分阶段发布、H5 走版本目录加重定向、App 走应用商店与热更新兜底；灰度按用户或设备维度放量，先小流量验证再全量，必须有一键回滚（配置回滚而非重新发版），各端版本号与接口兼容策略要显式约定。
6. 落地节奏：先做一个端的完整闭环，再按端扩展；差异代码进适配层，业务层不出现平台判断，保证新增一个端时的改动可控。

| 方案 | 开发成本 | 性能 | 生态 | 适用场景 |
| --- | --- | --- | --- | --- |
| uni-app | 低 | 中 | 好（插件市场） | Vue 团队、多端业务快速上线 |
| Taro | 中 | 中 | 较好（React 生态） | React 团队、多端业务 |
| RN / Flutter | 中高 | 高 | 中 | App 为主、体验要求高 |
| 混合（原生壳 + 跨端页） | 中高 | 中高 | 好 | 存量 App 快速扩端、分阶段迁移 |

**追问与易错点**：

- 追问：小程序审核周期怎么纳入发布计划？答：小程序和 App 商店都有审核不确定性，所以活动类需求要预留提前量，H5 用它来做紧急兜底与后置降级。
- 陷阱：承诺「一套代码零适配覆盖三端」——实际总有 20% 左右的差异代码，承诺越高后期打脸越狠。
- 追问：灰度出问题怎么快速止损？答：优先用配置中心关闭入口或切回旧版本资源，App 侧配合热更新或强制更新，避免依赖重新提审。

## 本章小结

- 小程序的双线程架构决定了「没有 DOM、只能 `setData`」两条铁律，跨线程通信与序列化是所有性能问题的根源；优化牢记只传变化字段、合并调用降频率、长列表上虚拟化。
- 页面栈上限 10 层，`switchTab` 与 `reLaunch` 会清掉非 tabBar 页面，`navigateTo` 不能跳 tabBar 页。
- 登录链路的红线是 `secret` 与 `session_key` 绝不下发；`code` 一次性、五分钟有效；续期靠 `checkSession` 加自有双 token。
- 小程序模板消息已下线，现在只有订阅消息：用户主动授权、授权几次发几条，关键通知必须叠加短信等兜底。
- 分包记住三组数字：主包与单个分包各不超过 2MB、总包不超过 30MB（服务商代开发为 20MB），独立分包不依赖主包但拿不到主包公共资源。
- 跨端只有三条渲染路线：WebView 渲染（成本低、动态化强）、原生渲染（RN，性能与成本居中）、自绘渲染（Flutter，一致性最好但包体与生态代价大）；选型按团队、成本、性能、生态、发布五维打分。
- JSBridge 的回调必须「一次调用一个 ID、超时兜底、拿到即删」，否则线上一定会出现永久 loading 与重复回调。
- 一套代码多端成立但零适配不成立：差异收敛到适配层、按能力而非平台判断，并从一开始设计分端发布与灰度回滚。
